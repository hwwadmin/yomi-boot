# 基础库优先使用规则

---

## 核心原则

凡涉及 **Go 基础设施能力**（装配、HTTP、DB、缓存、锁、限流、RPC、消息、鉴权、加解密、对象存储、ID、错误模型、定时任务、测试辅助等）的设计、实现、改造、巡检或方案评审，**必须优先复用 yomi-boot 已有基础库**。禁止在能力已覆盖且能满足需求时，另行引入同类第三方库或在业务仓/本仓平行实现。

本规则对 `_prompts/agent/` 下全部 Agent，以及 `_prompts/doc/skills/` 下全部 Skill **一律强制生效**（含后续新增）。Agent 在执行任务前已要求阅读 `_prompts/rules/` 全部规则；Skill 在涉及基础设施选型与编码时同样必须遵守本规则，不得以「Skill 未写明」为由绕过。

---

## 1. 索引文档

基础库能力索引位于：`_prompts/doc/基础库能力索引.md`

该索引包含：
- 各能力库的简要职责描述
- 对应仓库目录 / import 落位（`yomi-boot/{包}`）
- 常见场景速查

架构职责细则仍以知识库 [Go架构规范](../doc/knowledge/go/Go架构规范.md) §3.3 为准；本规则约束的是**是否优先使用**与**决策流程**。

---

## 2. 强制决策流程

在编写或评审任何可能触达基础设施的方案 / 代码前，按下列顺序执行：

```
阅读基础库能力索引
  → 判断是否存在相同或相近能力
    → 有候选：阅读对应库源码（含 plugin / 导出 API / 配置段）
      → 能满足需求：必须使用该库（或在其扩展点上扩展）
      → 不能满足：说明缺口后，强制选择新增方式（见 §2.5），再实现
    → 无候选：强制选择新增方式（见 §2.5），再实现
```

### 2.1 优先阅读索引

1. **必须先阅读** `_prompts/doc/基础库能力索引.md`。
2. 对照任务关键词（如幂等、限流、分布式锁、Saga、对象存储、雪花 ID、Encoder、Consul 等）在索引中匹配候选库。
3. 禁止跳过索引、凭印象直接引入第三方同类库或手写平行实现。

### 2.2 有类似能力时必须读源码

当索引中存在相同或相近能力时：

1. **必须阅读**对应库目录下的公开 API、包注释、`plugin`（若有）及关键配置结构。
2. 思考是否已覆盖当前需求（功能边界、错误语义、配置开关、生命周期、扩展点）。
3. 仅凭包名或索引一行描述就判定「不能用」——禁止。

### 2.3 满足需求则强制使用

若对应库**能够满足**（含通过配置启用、实现接口、注册插件、组合已有 API 等方式满足）：

- **必须使用**该 yomi-boot 能力库。
- **禁止**在业务仓再封装一套同职责组件。
- **禁止**直接依赖与 yomi-boot 已封装能力重复的第三方库（例如已有 `cronjob` 时禁止业务直引 `robfig/cron`；已有 `distlock` 时禁止另写 Redis 锁等——具体以各库约定与知识库为准）。
- 需要定制时：优先走库提供的扩展点（如 `AddCustomPlugin`、`Encoder` 注册、接口实现），而不是复制源码到业务仓。

### 2.4 有候选但不满足时的处理

仅当阅读源码后确认**确实无法满足**时，才允许进入新增：

1. 在方案/对话中说明：已对照的库路径、不满足点（缺口清单）。
2. **必须**按 §2.5 完成「新增方式」强制选择后，方可编码或写方案落位。
3. 业务仓仅保留业务特有逻辑，不得以「先在业务仓实现再说」绕过基础库演进。

### 2.5 无候选 / 需新增时：强制选择新增方式

当索引中**无候选**，或有候选但确认不满足而需要新增能力时：

1. **禁止**直接开始写代码或默认落在业务仓。
2. **必须先**向开发者（用户）列出可选新增方式，并**等待或确认其明确选择**其一后，再继续设计/实现。
3. Agent / Skill **不得**自行默认一种方式并默默落地；未得到明确选择时，任务停在「待选择新增方式」。

#### 2.5.1 可选新增方式（必须择一）

| 选项 | 含义 | 适用倾向 |
| ---- | ---- | -------- |
| **A. 扩展既有 yomi-boot 包** | 在已有能力包内增 API / 配置 / plugin 行为，不新建顶层包 | 与某现有包职责相邻、可自然收口 |
| **B. 新增 yomi-boot 顶层包** | 在 yomi-boot 新建独立能力包（及按需 `*/plugin`） | 独立基础设施能力、可被多业务仓复用 |
| **C. 业务仓特例实现** | 仅在当前业务仓实现，不进入 yomi-boot | **仅当**能力强绑定单一业务域、确认无跨仓复用价值；必须写明理由 |

选择优先级默认：**A → B → C**。选 C 时必须额外说明：为何不进 yomi-boot、复用预期、后续是否回迁。

#### 2.5.2 选择输出格式（强制）

在继续实现前，方案或对话中必须出现类似段落（字段齐全）：

```text
【基础库新增方式选择】
- 索引结论：无候选 / 有候选但不满足（列出已对照路径与缺口）
- 请选择其一：A 扩展既有包 | B 新增 yomi-boot 包 | C 业务仓特例
- 已确认选择：（待用户确认 / A|B|C）
- 落位说明：（包名或业务仓路径；选 A/B 时同步更新基础库能力索引的计划）
```

用户确认选择后：

- 选 **A/B**：在 **yomi-boot** 落地，并同步更新 `_prompts/doc/基础库能力索引.md`（及必要时 Go架构规范 §3.3）。
- 选 **C**：仅在业务仓落地，且不得引入与 yomi-boot 未来可能冲突的「伪基础库」公共包名；文档中保留回迁条件。

## 3. 适用范围

### 3.1 必须遵守

- 业务工程中基于 yomi-boot 的 Go 服务设计与编码（BFF / 领域 / 其他可部署单元）
- yomi-boot 本仓内新增能力、重构、缺陷修复（避免重复包、重复抽象）
- 需求显化、显化审核、代码开发、代码巡检等会产出或检查基础设施选型的 Agent / Skill 任务

### 3.2 可不强制套用本流程

- 纯前端（React）任务且不涉及 Go 基础设施选型
- 纯文档润色、与基础设施无关的文案修改
- 已明确范围且不触及任何基础能力的局部改动（若执行中发现触及，立即补跑本流程）

---

## 4. 禁止行为

| 禁止 | 说明 |
| ---- | ---- |
| 绕过索引 | 未读 `_prompts/doc/基础库能力索引.md` 即做基础设施选型或编码 |
| 凭印象否定 | 未读候选库源码就认定「不好用 / 不够用」并平行实现 |
| 跳过新增方式选择 | 无候选或需新增时，未按 §2.5 列出 A/B/C 并获得明确选择就开始实现 |
| 默认落业务仓 | 无候选时未经选择、擅自在业务仓实现可复用基础设施 |
| 业务仓造轮子 | 基础库已满足需求时，在业务仓再写一套 DB/锁/限流/幂等/RPC/存储等 |
| 重复依赖 | 引入与 yomi-boot 已封装能力重复的第三方库替代基础库 |
| 复制粘贴库代码 | 把 yomi-boot 源码拷到业务仓改一改当「自有实现」 |

---

## 5. 执行检查清单

涉及 Go 基础设施时，Agent / Skill 执行前必须确认：

- [ ] 已阅读 `_prompts/doc/基础库能力索引.md`
- [ ] 已根据任务匹配候选能力库（或确认索引中无候选）
- [ ] 对候选库已阅读源码并完成「是否满足」判断
- [ ] 满足需求时已选用 yomi-boot 对应库，未平行实现
- [ ] 无候选或需新增时：已按 §2.5 列出 A/B/C，并已获得开发者明确选择
- [ ] 已确认选择后才开始编码；选 A/B 时已规划同步更新基础库能力索引
