# spec落地执行

---

## 0. 基础信息

- **Skill 名称**: spec落地执行
- **描述**: 审核允许进入实现之后，按显化稿拆成任务，并在目标系统里把设计落地。不绑定语言、框架、目录或某一个仓库的组件。

执行前阅读《需求显化》和《显化审核》。稿要回答哪些问题、怎样才算可以开工，以那两份为准。含写路径时阅读《事务设计规范》。本次要新增或修改 Redis Key 时，再阅读《Redis设计规范》。这两份只约束事务边界和 Key 命名。

其他规范只有调用方点名，或显化稿写明「遵循某约定」时才采用，并在任务里写明条款。规范里没有的内容，不得当成必做项。

---

## 1. 目标

- **目的**：把已经允许进入实现的显化稿，变成目标系统里可验证的实现，并留下可追踪的任务记录。
- **做什么**：确认审核没有未关闭的阻塞；阅读显化稿；观察目标系统已有的写法；拆出任务清单；按任务先写验证再写实现；每完成一项就回写状态和证据。
- **不做什么**：
  - 不改显化稿，不改审核稿
  - 不重新做产品设计。稿里没有的能力不顺手补上
  - 不触发代码巡检
  - 不制定压测、部署和运维方案
  - 不规定目录名、类型名、注册方式、构建命令或组件选型。这些以目标系统里已经在用的为准

---

## 2. 输入

**必需**：

- 一份按《需求显化》写出的显化稿。常见文件名为 `spec.md`。
- 对应的审核稿。常见文件名为 `audit.md`，与显化稿放在一起。开工条件是：没有未关闭的严重问题，且结论写明可以进入实现。

另外两项以调用方为准：

- 任务清单的保存路径与文件名。调用方或所执行的 command 已指定时，按指定写入。都未指定时，写到显化稿同目录，文件名为 `tasks.md`，并在回复里给出完整路径。
- 要改动的目标系统。调用方指定了仓库、模块或目录时，只在该范围内改。未指定时，在当前工作区里找显化稿「影响范围」对应的代码。

没有审核稿，或审核结论仍是不可进入实现：停在这里，不拆任务，不写实现。向调用方指出缺什么、或未关闭的严重问题在哪。

信息不足时：目标系统里看不到同类写法、事务入口、失败出口或验证方式，就在对应任务上标 `⚠️ 待确认`，列出看到的候选，采用最贴近现有写法的一条继续。不把另一个仓库的目录或组件抄进来。需要目标系统里还不存在的基础设施时，先说明缺口和候选，得到调用方确认再写。

---

## 3. 工作立场

先看显化稿要守住什么，再看目标系统已经怎么做。分层、命名、事务入口、失败出口、测试位置，都沿用已经在用的形式。某一个现存实现刚好换了种写法，不足以成为新规范。

专门守住这几件事：

- 范围不放大。非目标里的事不做
- 流程图上的写，和事务切入点是同一段
- 接口的名称、uri、出入参、失败身份、是否幂等，和稿一致
- 只动稿里写了变动的表
- 一个任务做完并写下证据，再做下一个

实现和稿冲突时停手。把矛盾写进该任务的证据，不改稿，也不在代码里偷偷选另一边。

---

## 4. 工作流程

### 4.1 确认可以开工

读审核稿的结论。存在未关闭的严重问题，或写明不可进入实现：停止。不生成任务清单，不改代码。

结论允许进入实现后，通读显化稿。至少抓住：范围与非目标、规则与异常、表变动、领域、出入参、接口、流程图、事务切入点、第 13 章摘要。待确认项沿用稿里已经采用的假设，不另起一套。

### 4.2 观察目标系统

拆任务和写代码之前，先看这次会改到的地方已经存在的：

- 代码按什么职责分开，新代码应落在哪一种已有位置
- 事务从哪里开启，同一次提交怎样传下去
- 失败身份怎样变成调用方看到的结果
- 验证放在哪，用什么方式能跑这一处
- 已有能力能不能直接用

观察不到的项进入对应任务的待确认。不发明一套新的目录和框架用法。

### 4.3 拆任务

只写一份任务清单。任务从显化稿的范围里拆，不从某一种框架的脚手架步骤里拆。

- 一个任务是一次可以独立验证的改动
- 写清依赖：谁必须先做完
- 写清输入，以及完成时能看到什么
- 分组沿用显化稿第 13 章「适合继续拆开的方向」。该章没写清时，按领域、接口或场景选一种，在清单开头说明为何这样切
- 表结构、领域规则、接口、事务边界，都能指回稿里的章节
- 非目标不出现在任务里

清单骨架见第 5 节。任务状态和证据只写在这份清单里，不回写显化稿或审核稿。

### 4.4 按任务实现

一次只做一个任务，按依赖顺序做。每个任务内部的顺序：

1. 先写会失败的验证，覆盖这个任务对应的规则、失败身份或事务边界。验证的位置和写法，沿用目标系统已经在用的。
2. 再写让验证通过的实现。实现只服务这个任务。
3. 用目标系统已经在用的构建和验证方式跑这一处。观察不到统一入口时，跑与该任务直接相关的验证，在证据里写明用了什么、结果是什么。
4. 通过后把状态改为已完成。证据写清：改了哪些位置、跑了什么、结果。

验证要先失败，再因实现而通过。目标系统这一处确实没有验证入口，且调用方同意不做验证时，状态写「已完成（无验证）」，证据写明原因。没跑过的，不得写成已通过。

**事务**。写路径以显化稿第 11 章的切入点为准，并同时满足《事务设计规范》：

- 说得清这个事务保护哪条业务不变量
- 同一次提交里的表写入与稿一致
- 稿写在事务外的远程调用、缓存、通知、返回，不放进事务
- 已处于同一次提交中则加入并复用，不静默再开一个会独立提交的事务
- 稿写「本需求无事务切入点」时，不额外加事务

实现时才发现「先读再判断再写」、而稿没有对应切入点：停在该任务，不私自加事务，也不改稿。

**幂等**。接口列表里「是否幂等」为「是」的，重复调用和调用一次的业务结果相同。做法沿用目标系统已有的幂等写法。必须和业务写同生共死的凭证，放进同一次提交。没有现成写法时，在该任务里写明本次如何保证，并先向调用方确认，不新造一套公共组件。

**失败**。预期失败使用显化稿里的失败身份。出口形式沿用目标系统已经在用的写法。稿和现有系统都没有出口时，标待确认，先问调用方。

**表**。只落实稿里写了变动的表。无表变动则不改结构。方言、主键、审计列、命名沿用稿中已经对齐的口径。

**接口**。名称、uri、出入参、是否幂等与稿一致。格式和必填在入口校验；状态、唯一性等业务校验留在领域动作里。

**已有能力**。目标系统或它已经依赖的公共能力里，有能满足本任务的，先读实现，满足则必须使用。没有可复用能力、又需要新的公共能力时，停下来写出缺口、候选和影响，等调用方确认。不在业务路径里平行再写一份。

**Redis Key**。本次要新增或修改 Key 时，命名遵守《Redis设计规范》。不涉及 Key 则不引用该规范。

### 4.5 收束

全部任务已完成，或明确标出未做及原因。不扩大到清单之外的重构。显化稿和审核稿保持不动。

范围、规则、表、接口或事务切入点在实现中发现稿写错了：停手，在任务证据里说明矛盾。先改显化稿，再走审核，然后才继续实现。

---

## 5. 任务清单

### 5.1 唯一产物

实现之外，只新增或更新这一份任务清单。不另写验收清单，不把执行状态写回显化稿或审核稿。

调用方声明在已有清单上继续时：沿用原有任务编号；已完成的保留证据；新增任务接在后面。

### 5.2 文档骨架

```markdown
# 落地任务：{需求名称}

| 字段 | 值 |
| ---- | -- |
| 显化稿 | {路径} |
| 审核稿 | {路径} |
| 生成时间 | {日期} |
| 目标系统 | {本次改动所在的系统；调用方未指定则写观察到的位置} |
| 拆分方式 | {按领域 / 按接口 / 按场景，及原因} |

## 0. 本次不动

{非目标，以及周边存在但这次不改的部分}

## 1. 任务

### {分组名}

#### 任务 {n}：{标题}

- **对应**：{显化稿章节，或接口 / 表 / 场景}
- **依赖**：{无，或任务编号}
- **做什么**：{一句话}
- **输入**：{依赖的稿、表、接口或已有代码}
- **完成时**：{怎样算做完}
- **状态**：未开始
- **证据**：—
```

状态只用这四种：未开始、进行中、已完成、阻塞。已完成但调用方同意不做验证的，写「已完成（无验证）」。阻塞必须在证据里写明停在什么矛盾上。

---

## 6. 约束

- 落盘路径以调用方为准。未指定时，写到显化稿同目录的 `tasks.md`，并在回复中说明路径。不只在对话里输出。
- 审核不允许进入实现时，不拆任务，不写实现。
- 不改显化稿，不改审核稿。
- 不把语言、目录、组件、构建命令写成唯一做法。这些以目标系统里已经在用的为准。
- 不实现非目标，不顺手改清单以外的代码。
- 事务边界以显化稿第 11 章为准，并满足《事务设计规范》。
- 只有新增或修改 Redis Key 时，才对照《Redis设计规范》。
- 公共库里不实现某一个产品的业务域。业务规则留在拥有该领域的系统里。
- 已有能力满足需求时，不平行再实现一份。

---

## 7. 完成前自检

停笔前逐项核对。

- [ ] 已确认审核稿没有未关闭的严重问题，且结论是可以进入实现；否则没有写代码
- [ ] 任务清单与显化稿的范围一致，非目标没有变成任务
- [ ] 分组方式与第 13 章的拆分方向一致，或已说明另选一种的原因
- [ ] 每个已完成任务都有证据：改动位置、验证方式、结果
- [ ] 没跑过的验证没有写成已通过
- [ ] 写路径的事务切入点、同一次提交的表、事务外动作，与显化稿一致
- [ ] 事务内没有远程调用、缓存、通知和对外响应组装
- [ ] 接口的失败身份、出入参、是否幂等与显化稿一致
- [ ] 表结构只动了稿里写明变动的表
- [ ] 新代码落在目标系统已有的职责划分里，没有引入另一套目录或组件
- [ ] 已有能力被复用；新的公共能力经过调用方确认
- [ ] 显化稿和审核稿没有被修改
