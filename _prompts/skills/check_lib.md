# 基础库检查

---

## 0. 基础信息

- **Skill 名称**: 基础库检查
- **描述**: 对 `github.com/hwwadmin/yomi-boot` 下的单个基础库执行八维静态检查与可执行验证，按严重度输出问题清单和分包星级，落盘 `_ipc-doc/`；默认只检不修，授权修复后复审回写同一份报告
- **作者**: zwei
- **创建日期**: 2026-11-04

---

## 关联知识库

- **执行前必读**：本 Skill 自包含基础库检查口径，不依赖外部规范文档
- **按需**：
  - `knowledge/Redis设计规范.md`：检查 `component/common/redis`、`redisratelimit`、`redisstream`、`distlock`、`captcha` 等使用 Redis 的库
  - `knowledge/数据库表设计规范.md`：检查 `component/common/db/orm`、`idempotency`、`event`、`httprecord` 等带表结构的库
  - `knowledge/事务规范.md`：检查 `component/common/db/tx`、`idempotency`、`event` 等涉及事务边界的库
- **互补**：`skills/check_code.md` 负责业务工程的分层与业务域巡检；本 Skill 只检查基础库本身，不覆盖业务服务

## 1. 目标

- **做什么**：对用户指定的一个基础库，逐文件通读源码，按设计合理性、逻辑正确性、编码质量、注释规范、代码风格统一、优化空间、重复与简化、封装边界八个维度检查，并单列依赖方向结论；用可执行命令验证可疑行为，输出带文件行号、影响说明、分级与修复建议的问题清单，落盘一份可复审的 IPC 报告。
- **为什么**：基础库被业务工程广泛复用，缺陷会被成倍放大。统一检查口径可以避免“凭感觉评审”，让每个结论都能落到具体代码和可复现的验证上，也便于后续复审按同一份报告逐条回写。
- **不做什么**：
  - 不检查业务工程的分层、BFF、事务编排等业务维度（交给 `skills/check_code.md`）
  - 不做压测、渗透测试、容量规划，不承诺性能数字
  - 不以测试覆盖率数字为目标，不为了覆盖率补无意义用例
  - 不替代 `go build`、`go vet`、`golangci-lint` 等自动工具，而是在其之上做人工审查
  - 未经用户明确授权，不修改任何源码

## 3. 技术方案

### 3.1 检查单元与范围

- **一个检查单元 = 用户指定的一个库目录**。默认包含该目录及其直属子包（例如 `component/common/db` 含 `orm`、`tx`、`dbtest`）；子包按“分包星级”分别给星，问题记在归属子包，不重复计价。
- **一次只检查一个库**。用户一次指定多个兄弟库时，逐个执行、分别出报告，禁止合并成一份报告混检。
- 检查开始前先写清包含与排除范围；未明确排除的文件不得跳过。
- 检查以**当前工作区代码**为准。开始前记录 `git rev-parse --short HEAD` 与 `git status --short`，报告中注明快照；复审时先确认报告对应的是哪个快照。
- 历史报告、生成代码、第三方 vendored 代码不作为判罚对象；如果要指出第三方库行为，只把它作为影响说明的证据。

### 3.2 检查流程

```text
开始
  ↓
1. 确认检查单元、范围、是否允许修复
  ↓
2. 记录快照（commit、git status）与规模（包数、文件数、非测试行数、测试文件数）
  ↓
3. 通读 doc.go / 包注释、导出 API、配置、测试，建立事实底稿
  ↓
4. 执行 §3.13 可执行验证，记录命令与结果
  ↓
5. 按八维 + 依赖方向逐项检查，边查边记文件行号
  ↓
6. 分级、定星、整理待确认项，做 §3.17 对抗性自查
  ↓
7. 落盘 `_ipc-doc/{YYYYMMDD}_{库名}-ipc.md`
  ↓
8.（可选，需授权）修复 → 重新验证 → 复审回写同一份报告
  ↓
结束
```

规则：

- 每个维度至少产出一条结论，“未发现问题”也是结论，不得跳过。
- 发现问题必须记录到文件与行号；只写“存在风险”不算问题。
- 先取证后判断：可疑行为优先用命令、临时探针或依赖源码确认，不能只凭阅读印象。
- 修复阶段与检查阶段分开：检查阶段禁止顺手改代码。

### 3.3 事实采集

按以下顺序建立事实底稿，避免一上来就下结论：

1. **包边界**：`go list -f '{{.ImportPath}} {{.Name}}' ./<库>/...` 列出包与包名，确认检查单元。
2. **包职责**：读 `doc.go` 或包注释，确认库的职责、不变量、使用方式。
3. **导出面**：`go doc -all ./<库>` 列出全部导出符号，标出疑似内部实现泄漏。
4. **配置**：区分运行时 `Config` 与 YAML 绑定 `BootConfig`，核对默认值、必填项、`enabled` 语义。
5. **依赖**：`go list -deps ./<库>` 看依赖方向；对第三方行为有疑问时用 `go list -m` 确认版本，再读 `go env GOMODCACHE` 下的源码。
6. **测试**：读 `*_test.go`，确认覆盖了正常路径、边界、失败路径；测试是否依赖外部服务。
7. **规模**：`find <库> -name '*.go' | wc -l`、`wc -l` 统计文件与非测试行数，写进报告，避免报告数字与代码对不上。

需要实测时，探针工程放在仓库根 `.tmp/<库名>-review/`，不得放进源码树；用完清理，并确认 `git status --short` 没有残留。

### 3.4 维度一：设计合理性

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 职责边界 | 库的公开 API 是否只做能力封装，是否混入业务规则 | 基础库不得出现业务实体、业务状态机、业务错误码；不得 import 业务工程代码 |
| 分层位置 | 库所在层是否与依赖方向一致 | `component/core` 不得依赖任何兄弟 `component/*` 包；`component/common`、`component/cloud` 可依赖 `core`；`component/*` 不得 import `boot`/`plugin`；`plugin/builtin/{lib}` 可依赖 `component/*` 与 `plugin`；`plugin` 根包不得 import `plugin/builtin`；`boot` 负责编排，不得被下层反向依赖 |
| 接口粒度 | 接口方法数量与参数类型是否合理 | 接口通常 1–4 个方法；超过 8 个方法要说明理由；参数用领域概念，不用底层实现类型 |
| 抽象层次 | 是否引入无价值的间接层 | 只转发调用、无逻辑增强、无替换价值的包装函数/接口，视为多余抽象 |
| 扩展方式 | 新增能力是否需要修改现有代码 | 优先通过新增实现、配置项或 hook 扩展；需要改核心分支才能扩展时，评估是否缺少端口 |
| 零值可用 | 核心结构体是否零值可用或强制构造函数 | 零值使用会 panic 或产生静默错误时，必须提供 `New*` 并在文档写明 |
| 错误契约 | 哨兵错误、错误码、panic 边界是否清晰 | 非法入参应返回 error 而非 panic；仅启动装配类 Fail Fast 允许 panic，且必须在文档写明 |
| API 稳定性 | 是否存在兼容别名、re-export、双哨兵 | 重构应直接切换新归属，错误原样透传；不保留类型别名或转发层 |

### 3.5 维度二：逻辑正确性

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 空指针/空值 | 指针、接口、map、channel、切片是否在 nil 下安全 | 参数未判空即解引用；map 未初始化即写入；channel 未初始化即发送；nil 切片与空切片行为是否被混用 |
| 边界条件 | 空输入、长度为零、索引、循环与递归边界 | 空切片/空字符串、单元素、最大长度、负数、溢出；递归是否有终止条件 |
| 错误处理 | 错误是否被吞掉、误判或错误地转成 nil | `if err != nil { return nil }`、只打日志不返回、用 `err.Error()` 子串判断可恢复性 |
| 资源生命周期 | 文件、连接、goroutine、定时器、订阅是否正确释放 | 打开未 `defer Close()`；`Close` 不幂等；`Close` 不尊重 ctx；启动的后台任务没有退出路径 |
| 并发安全 | 共享状态是否有竞态保护，锁粒度与顺序是否合理 | 多 goroutine 读写同一变量无锁；锁内调用外部回调；锁顺序不一致导致死锁；返回内部 slice/map 的别名 |
| context | ctx 是否作为第一个参数、是否尊重取消、是否被存入结构体 | 请求路径不得用 `context.Background()`；清理路径需要 `context.WithoutCancel`；后台任务用 `slot.RuntimeContext()`；不得把 ctx 存进长生命周期结构体 |
| 时间与数值 | 时间、时长、时区、整数溢出、0 值语义 | `0` 表示“不限制”还是“未设置”必须明确；时长单位统一；跨时区逻辑依赖 `app.timezone` 而不是本地时区 |
| 类型断言 | 类型断言是否使用双返回值并处理失败 | `x.(T)` 裸断言；`x.(T)` 在接口可能为 nil 时 panic |
| 重试与幂等 | 重试是否有上限、退避、抖动，是否区分可重试错误 | 无限重试；对不可重试错误重试；重试放大下游压力；幂等键是否稳定 |
| panic 边界 | 库内 goroutine 与回调是否有 recover | 包内 `go` 启动的 goroutine 顶部必须有 recover；recover 后要转 error 或记录，不得静默吞掉 |

### 3.6 维度三：编码质量

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 错误传播 | 错误是否包装并保留原因链 | 用 `errors.Wrap` / `fmt.Errorf("%w")` / `errors.Join`；不得丢原因、不得重复包装同一层 |
| defer 使用 | 解锁、关闭、计时、恢复是否用 defer 保证执行 | `Lock()` 后未 `defer Unlock()`；循环内 defer 是否堆积；defer 参数是否在注册时已求值 |
| 命名规范 | 导出/非导出命名是否符合 Go 约定与库内习惯 | 驼峰而非下划线；缩写词大小写一致（`HTTP`/`ID`/`URL`）；哨兵统一 `Err*`；构造函数统一 `New*`/`Must*` |
| 编译期校验 | 接口实现是否有编译期断言 | `var _ Interface = (*Impl)(nil)`；泛型约束下的断言是否仍然有效 |
| 测试 | 关键路径、边界、失败路径是否有可执行验证 | 不以覆盖率数字论好坏；核心导出 API 至少有正常与失败用例；并发库应有 `-race` 可运行用例 |
| 包文档 | 每个包是否有且只有一处包注释 | 优先 `doc.go`；插件包可写在主实现文件头；包注释与 `package` 之间不空行，非包注释的文件头与 `package` 之间空一行 |
| 导出最小化 | 是否导出了只在本库内部使用的内容 | 内部辅助函数、转换函数、实现类型不应首字母大写；导出即承诺兼容 |
| 依赖管理 | `go.mod` 依赖是否精确、是否有未使用依赖 | `go mod tidy` 后无残留；不引入仅为单个小功能的重型依赖；第三方库版本固定 |
| 死代码 | 是否存在无调用方的函数、分支、配置项 | 全仓搜索确认；不可达的防御分支只记录不单列；配置项无消费方要指出 |
| 日志与输出 | 库内是否直接使用标准库日志或打印 | 禁止 `fmt.Print`/`log.Print`；统一走 `component/core/logger` 或返回 error；日志不得输出敏感字段 |
| 全局状态 | 是否存在可变包级变量、`init()` 副作用 | 包级可变状态影响测试隔离与并发安全；`init()` 只允许做无副作用的注册 |

### 3.7 维度四：注释规范

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 注释语言 | 是否统一中文，是否中英混写 | 除 Go 指令注释（`//go:embed`、`//nolint`）外，注释使用中文 |
| 注释格式 | 是否使用 `//`，与被注元素是否紧贴 | 声明级符号统一 `// 注释`；注释与被注元素之间不空行；不使用 `/* */` 做常规说明 |
| 包注释 | 每个包是否有且只有一处包注释，职责是否准确 | 优先 `doc.go`；插件包可写在主文件头；非包注释的文件头与 `package` 之间空一行，避免被 godoc 合并 |
| 类型注释 | 导出类型、接口、类型别名是否有注释 | 以 `// 类型名 描述` 开头；导出字段在名称不自解释时补行尾注释 |
| 函数注释 | 所有函数（含非导出）是否有 `// 函数名 描述` | 描述契约：参数语义、返回值、副作用、nil/空值约定、是否幂等、是否尊重 ctx |
| 接口注释 | 接口与接口方法是否描述“做什么”而非“怎么做” | 接口注释说明契约与实现约束，不暴露具体实现细节 |
| 常量注释 | 同组常量是否有块前注释 | const 块前统一注释，不逐行重复；无法自解释的常量在行尾补充 |
| 关键步骤 | 方法体内关键分支、边界、非直观逻辑是否有行内注释 | 只注释“为什么”，不复述“做了什么”；自解释代码不注释 |
| 特殊标记 | TODO/FIXME/HACK/nolint 是否带原因或期限 | 禁止裸写；`//nolint` 必须写明忽略原因；TODO 要能定位到后续动作 |
| 注释准确性 | 注释是否与当前实现、默认值、行为一致 | 重点核对配置默认值、TTL、并发语义、错误语义；过时注释按问题处理 |
| 作者信息 | `@author` 是否只出现在文件头 | 函数、类型、接口的声明级注释不得出现作者标识 |
| 冗余注释 | 是否为自解释代码添加注释 | 禁止为 `return nil`、简单赋值、显而易见的循环加注释；禁止用注释掩盖混乱结构 |

### 3.8 维度五：代码风格统一

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 格式化 | 是否通过 gofmt/gofumpt | 检查阶段用 `gofmt -l` 判断；goimports/gofumpt 差异记为待确认；修复阶段再执行 `make fmt`；不得手工对齐 |
| import 分组 | 标准库、第三方、本仓是否分组 | 组间空行，组内按路径排序；不使用相对导入 |
| 命名一致性 | 同类概念是否统一命名 | 同一库内不要混用 `Client`/`Conn`/`Proxy`；同类字段在不同结构体中同名同义 |
| 缩写词 | 缩写词大小写是否统一 | `ID`/`URL`/`HTTP`/`API` 在导出与非导出场景保持同一风格 |
| 错误风格 | 错误包装、哨兵、错误文案是否统一 | 同一库内统一 `errors.Wrap` 或统一自定义错误类型；错误文案统一库名前缀 |
| 函数组织 | 构造函数、导出方法、非导出方法是否有稳定顺序 | 按构造函数 → 导出方法 → 非导出方法排列；同一接收器的方法集中 |
| 配置命名 | YAML key 与 Go 字段是否对称、是否成组 | YAML 用 snake_case；成组配置带统一前缀（如 `outbox_*`/`inbox_*`），不得混用裸前缀；Go 字段同名转驼峰 |
| 可选值表达 | “未设置”和“显式零值”是否可区分 | 需要区分时用 `*bool`/`*int` + `BoolOrDefault`/`OrDefault`；不需要区分时不要过度使用指针 |
| Go 惯用法 | 是否符合 Go 惯例 | 包名简短小写无下划线；getter 不带 `Get` 前缀；接口名合理使用 `-er`；接收器用单字母或短缩写；避免 `this`/`self` |

### 3.9 维度六：优化空间

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 内存分配 | 热点路径是否存在可避免的堆分配 | 循环内 `fmt.Sprintf`、`[]byte`/`string` 反复转换、小对象装箱；只在可测量或明显高频的路径上提 |
| 重复计算 | 循环内不变量、可缓存的解析结果是否重复计算 | 配置解析、正则编译、模板构建是否每次调用都重做 |
| 序列化 | JSON/消息序列化是否有不必要的中间结构 | 大对象多次编解码；可用流式处理或复用 buffer 的场景 |
| 并发利用 | 独立任务是否可并行，是否需要限制并发度 | 串行处理明显可并行的独立任务；并发无上限导致下游被打爆 |
| 反射 | 反射是否可用泛型或代码生成替代 | Go 1.18+ 能用泛型的场景；反射在热点路径反复执行 |
| 锁粒度 | 锁范围是否可缩小，是否该用读写锁 | 锁内做 I/O、序列化、回调；读多写少仍用互斥锁 |
| 字符串拼接 | 大量拼接是否使用高效方式 | 循环内 `+=` 改为 `strings.Builder`；固定分隔拼接用 `strings.Join` |
| 资源复用 | 连接、buffer、对象池是否合理复用 | 每次请求新建连接池/客户端；可复用 buffer 反复分配 |
| 过早优化 | 是否为不存在的问题增加复杂度 | 没有测量依据的“优化”、为省一次分配引入复杂缓存，按 🔵 记录甚至不提 |

> 优化项必须说明“在什么场景下才有收益”。没有可达场景的优化不提；不要为了性能建议引入新的第三方依赖。

### 3.10 维度七：重复与简化

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 重复代码 | 同库内结构相同、仅参数不同的代码 | 相同逻辑出现三处以上，评估提取为通用函数；两处重复不强行抽象 |
| 样板代码 | 是否可用泛型消除的重复实现 | 为不同类型重复实现相同的 `Find`/`Map`/`Filter`/`Set` 操作 |
| 冗余包装 | 是否只有一行转发的包装 | 函数体仅调用另一个同名函数且无参数转换、无额外语义 |
| 可合并分支 | 多个相似分支是否可合并 | 多个 `if`/`switch` 执行相似操作，可用表驱动或策略合并 |
| 过度提取 | 是否提取了只有一个实现且无替换需求的接口 | 接口仅有一个实现、无 mock/替换需求、无消费者侧定义价值时，评估删除 |
| 配置重复 | 是否存在含义相同或互相覆盖的配置项 | 同一语义出现两个 key；旧 key 未删净；默认值在两处各写一份 |
| 重复校验 | 同一规则是否在多层重复校验 | 配置层、构造层、调用层重复校验同一条件；保留最靠近边界的一层，其余说明必要性 |
| 文档重复 | 同一说明是否在多个文件重复维护 | 包注释、README、配置注释三处写同一份默认值，容易漂移；保留一处真源 |

> `BootConfig`（YAML 绑定）与运行时 `Config` 的分离是刻意设计，不算重复；判断标准是“是否有独立职责”，不是“字段是否长得像”。

### 3.11 维度八：封装边界

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 导出面 | 是否暴露了不应对外开放的类型和函数 | 仅内部使用的辅助类型、转换函数、实现结构体被导出 |
| 实现泄漏 | 公开 API 是否泄漏底层实现 | 返回 `*redis.Client`、`*gorm.DB`、第三方类型；返回内部结构体指针；导出字段可直接改写内部状态 |
| 构造函数 | 需要初始化的结构体是否提供构造函数 | 导出结构体未提供 `New*`，或构造函数未完成必要初始化；构造函数是否校验入参 |
| 包依赖 | 是否依赖了不该依赖的库 | 组件库依赖 `plugin`/`boot`；下层依赖上层；循环依赖；为一个小功能引入整个大包 |
| 全局状态 | 包级可变变量是否影响测试与并发 | 全局 client、全局 map、全局配置；测试之间无法隔离；并发访问无保护 |
| 接口内聚 | 接口是否只包含高度相关的功能 | 一个接口同时承担读写、生命周期、序列化等无关职责 |
| 配置泄漏 | 库内是否直接读环境变量或配置文件 | 库内部调用 `os.Getenv`、读 YAML；配置应由调用方通过 `Config` 注入 |
| 返回值所有权 | 返回的 slice/map/指针是否与内部状态共享 | 返回内部切片别名，调用方修改会影响库内状态；应返回副本或明确文档说明 |
| internal 使用 | 跨包共享的私有实现是否放在 `internal/` | 多个子包复用的底层实现放在 `internal/`，避免被外部 import；`internal/` 保持无环，避免反向依赖公开包造成依赖倒挂 |

### 3.12 结构专项检查

#### 3.12.1 组件库（`component/*`）

| 检查项 | 判断口径 |
| ------ | -------- |
| 包注释 | 每个包有且只有一处包注释；优先 `doc.go`，写明职责、不变量、典型用法 |
| 运行时 Config | 不含 `mapstructure` tag；不读 YAML/环境变量；提供 `Validate()` 或构造时校验 |
| 默认值 | 默认值集中在构造/配置层，不在业务分支里散落；`0` 值语义明确 |
| 哨兵错误 | 统一放 `errors.go`；用 `component/core/errors` 的 `NewNoStack` + 调用点 `Sentinel`；错误文案带库名前缀 |
| 日志 | 使用 `component/core/logger`，不直接 `fmt.Print`/`log.Print`；不在库内初始化全局 logger |
| 依赖 | 不 import `plugin`/`boot`/业务代码；`component/core` 不依赖兄弟 `component/*` |
| 测试 | 同包或 `_test` 包；表驱动优先；不依赖真实外网；需要外部服务时用 `dbtest`/`kafkatest`/`miniredis` 等测试辅助 |
| 子包 | 子包职责清晰；`internal/` 只放跨子包复用的私有实现；不在子包里再建 `plugin` 子包 |

#### 3.12.2 插件包（`plugin/builtin/{lib}`）

| 检查项 | 判断口径 |
| ------ | -------- |
| 包名与文件 | 包名统一 `{lib}plugin`；配置放 `config.go`，插件实现放主实现文件（通常 `{lib}_plugin.go`），复杂插件按职责拆文件；包注释写在主实现文件头或 `doc.go` |
| 配置绑定 | 必须有 `SectionKey`、`BootConfig`（带 `mapstructure`）、`ToConfig()`、`Validate()`、`ConfigSection()`；运行时 `Config` 不得带 `mapstructure` |
| 插件身份 | `Name` 常量；嵌入 `plugin.Base`；`var _ plugin.Plugin = (*X)(nil)`；`NewX()` 构造函数 |
| 取用方式 | 需要被其他插件取用时提供 `From(slot)`；未注册时返回 nil；访问器对 nil 接收者安全 |
| Init | 用 `config.MustSection[BootConfig](slot.Config, SectionKey)` 取配置；按 `enabled` 开关的插件未启用时返回 `plugin.ErrDisabled`；失败前清理本次申请的资源 |
| Close | 幂等、尊重 ctx、不 panic；先停后台任务再关资源；返回聚合错误 |
| 后台任务 | 使用 `slot.RuntimeContext()`，不得用 `context.Background()`；任务必须在 Close 时退出或被等待 |
| 阶段 hook | `OnReady` 失败导致启动失败；`OnDraining` 失败只记录日志；hook 顺序依赖要在注释中说明 |
| 插件顺序 | 依赖前序插件时，在 `plugin/builtin/plugins.go` 的顺序注释中写明依赖；不得假设未注册的插件存在 |
| 依赖边界 | 不 import `plugin/builtin` 根包（会成环）；不 import 业务代码；只依赖 `component/*` 与 `plugin` |

#### 3.12.3 清单/框架（`plugin`、`plugin/builtin`、`boot`、`boot/lifecycle`、`boot/server`）

| 检查项 | 判断口径 |
| ------ | -------- |
| 职责单一 | `plugin` 只管插件接口与链式生命周期；`plugin/builtin` 只管清单；`boot` 只管编排；`boot/server` 只管 HTTP 装配；`boot/lifecycle` 只管进程阶段 |
| 顺序与回滚 | 插件按注册顺序 Init、逆序 Close；Init 失败逆序回滚；Close 超时/panic 不阻塞剩余插件 |
| 错误语义 | 启动失败 panic 还是返回 error 必须一致；`ErrDisabled` 表示跳过，不参与 hook 与 Close |
| 并发与超时 | Close 有默认超时；Init/Close 的 ctx 只约束启动/关闭；后台任务用 `RuntimeContext` |
| 清单一致性 | `DefaultPlugins()` 与 `DefaultConfigs()` 覆盖一致；新增插件同步顺序注释与配置段；无孤儿配置段（有配置段但无插件时要么说明用途，要么删除） |
| 反向依赖 | `plugin` 根包不 import `plugin/builtin`；`boot` 可以 import 两者；`component` 不 import 任何 `plugin`/`boot` |
| 文档 | 顺序、依赖、失败行为写在包注释或函数注释里；不靠阅读实现推断 |

### 3.13 可执行验证

检查阶段按需执行以下命令，并在报告“实测记录”中逐条写明命令与结果：

| 目的 | 命令 |
| ---- | ---- |
| 编译 | `go build ./<库>/...` |
| 静态检查 | `go vet ./<库>/...` |
| 单元测试 | `go test -count=1 ./<库>/...` |
| 竞态 | `go test -race -count=1 ./<库>/...`（并发相关库必做，其他按需） |
| lint | `go run github.com/golangci/golangci-lint/v2/cmd/golangci-lint@v2.1.6 run --config .golangci.yml ./<库>/...` |
| 导出面 | `go doc -all ./<库>` |
| 依赖方向 | `go list -deps ./<库>` / `go list -m all` |
| 格式化 | `gofmt -l ./<库>`（只检查不改写；goimports/gofumpt 差异记为待确认；`make fmt` 会改写源码，检查阶段禁止执行） |

规则：

- 没有执行过的命令不得写成“已通过”；不能执行时写明原因（缺少外部服务、平台限制、耗时过长等）。
- 测试依赖外部中间件时，先用 `-run` 收窄到可安全运行的用例；不得为了跑测试去连生产或共享环境。
- `-race` 依赖 CGO 工具链；Windows 无 gcc 等无法执行时写明原因，改用并发探针加人工审查，并在报告中标注“未验证竞态”。
- 禁止在检查阶段修改源码来“让测试通过”。
- 需要写临时探针时放 `.tmp/<库名>-review/`，探针不得 import 被测包以外的私有符号；用完清理并确认工作区干净。
- 报告中的数字（文件数、行数、问题数）必须与命令输出一致。

### 3.14 问题分级与星级

#### 3.14.1 问题分级

| 级别 | 标签 | 判定标准 | 示例 |
| ---- | ---- | -------- | ---- |
| 🔴 严重 | bug / design-flaw | 在项目实际场景下可达，会导致崩溃、数据损坏、死锁、资源泄漏、安全边界失效或对外契约破坏 | 并发写无锁、nil 解引用、Close 不释放连接、鉴权绕过、公开 API 返回内部可变状态 |
| 🟡 警告 | logic-warning / code-smell | 在特定但合理输入下可能出错，或明显损害可维护性、可观测性、可运维性 | 边界未处理、错误被静默吞掉、后台任务无法退出、配置默认值有陷阱、锁内做 I/O |
| 🔵 建议 | optimization / simplification | 不影响正确性，改进后有明确收益 | 可提取公共函数、可缩小锁粒度、注释与实现不一致、可补测试、命名不统一 |

判级规则：

- **按后果判级，不按代码形态判级**。同样是 `if err != nil`，吞掉致命错误是 🔴，只影响日志文案是 🔵。
- 可达性必须结合项目实际配置与调用方式判断；只在理论极端场景触发的问题降级为 🔵 或“待确认”。
- 架构、注释、可观测性、测试覆盖类建议一律 🔵，不丢星。
- 同一根因在多处出现只记一条，位置列全部相关文件；不得按文件数重复计价。
- 无法确认的问题写“待确认”，不计星；确认后再升级。

#### 3.14.2 星级

每个包给 1–5 星，必须写清丢星原因：

| 星级 | 参考标准 |
| ---- | -------- |
| 5 ★ | 无 🔴、无 🟡；🔵 不影响结论 |
| 4 ★ | 无 🔴，仅有少量（≤2）🟡，且不是系统性问题 |
| 3 ★ | 1 个 🔴；或 🟡 较多且集中在同一类问题 |
| 2 ★ | 2 个 🔴；或 1 个 🔴 加系统性 🟡 |
| 1 ★ | 3 个及以上 🔴；或存在导致库整体不可用/无法安全使用的根本缺陷 |

- 星级是综合判断，不机械换算；但“🔵 不丢星、待确认不计星、架构/注释/可观测性不丢星”是硬规则。
- 有子包时按包分别给星；父目录只给汇总说明，不重复计价。
- 报告必须包含“丢星原因”，不能只给数字。

### 3.15 报告输出

报告落盘到 `_ipc-doc/{YYYYMMDD}_{库名}-ipc.md`：

- 目录不存在时先创建；同名报告已存在时直接覆盖初版，不另起序号。
- 库名用目录名或包名，保持可读，例如 `20261104_snowflake-ipc.md`、`20261104_component.common.db-ipc.md`。
- 报告结构固定如下：

```text
# {YYYYMMDD} {库名} 基础库检查

> 修订记录：{日期} {做了什么}（{问题编号} 见 §八）；§一～§七 为初检快照，保留不动。

## 一、检查范围与依据
- 检查对象、包含/排除的包
- 快照：commit、git status
- 规模：包数、文件数、非测试行数、测试文件数
- 依据：本 Skill + 按需加载的知识文档
- 执行方式：通读文件、go doc、验证命令、探针位置

## 二、分包星级
| 包 | 星级 | 说明（丢星原因） |

## 三、八维结论
| 维度 | 结论 |

## 四、问题清单
### {ID} {级别} {一句话标题}
- 位置：文件:行号（多处列全）
- 问题描述：发生了什么
- 影响：在什么场景下会造成什么后果
- 依据：本 Skill 条款 / 按需知识文档条款 / 代码事实
- 修复建议：怎么改，改完行为有什么变化

## 五、实测记录
- 命令 + 结果 + 未能执行的原因

## 六、人工确认项
- 需要用户拍板的语义取舍、配置默认值、兼容性影响

## 七、综合评估
- 整体结论、主要风险、建议的处理顺序

## 八、修复记录（授权修复后追加）
- 逐条状态：已修复 / 部分处理 / 按用户决定不处理 / 误判撤销
- 行为变化与未覆盖项
- 复审后星级与剩余问题
```

问题编号规则：`{库缩写}-NN`，例如 `SNOW-01`、`DBTX-01`；复审新增项续号，删除项不复用编号。

写作要求：

- 问题、影响、修复建议用白话讲清楚；包名、函数名、配置项照原样写，只用于定位，不代替解释。
- 每条问题必须有位置、影响、依据、修法；缺一项不写入正式问题清单。
- 推测必须标注“待确认”，不得写成事实。
- 报告是复审的唯一载体：初检快照不修改，修复与复审结果只追加。

### 3.16 修复与复审

- **默认只检不修**。只有用户明确说“修复”“按推荐修复”“继续修复”后才动代码。
- 修复范围只限报告内已确认的问题；不做顺手重构，不扩大改动面。
- 修复顺序：🔴 → 🟡 → 用户点名的 🔵；同一文件的问题合并修改。
- 修复后至少执行：`gofmt`/`go build ./<库>/...`/`go vet ./<库>/...`/相关测试；并发相关改动加 `-race`。
- 复审回写同一份报告，追加 `## 八、修复记录`（已有则按 九、十…… 顺序追加新的一节，不替换旧节）：
  - 逐条标注状态与行为变化；
  - 写明未覆盖项与剩余风险；
  - 给出复审后星级，保留初检星级不动；
  - 复审要重新读代码验证，不能只信上一轮报告的结论；报告快照早于修复时，用 `git show <commit>^` 对照旧版本。
- 用户只修一部分是正常情况：未修项标“部分处理/按用户决定不处理”，不得写成“已修复”。

### 3.17 对抗性自查（落盘前必做）

逐条自问，任一不通过就修正报告：

1. **证据**：每条问题的行号是否实际存在？描述的行为是否能在当前代码里指出来？
2. **可达**：触发条件在项目实际配置和调用方式下是否真的会出现？是否用假设场景扣了星？
3. **意图**：是否把刻意的设计取舍当成缺陷？先看注释、文档、调用方，再定性。
4. **修法**：建议的修法本身能否编译、是否符合当前语义？有没有引入新的兼容问题？
5. **分级**：🔴/🟡 是否按后果判定？同类问题在不同包是否用了不同标准？是否重复计价？
6. **数字**：报告里的文件数、行数、问题数是否与命令输出一致？正文条目数与汇总数字是否一致？
7. **快照**：报告对应的是修复前还是修复后？是否把已修复的问题又报了一遍？
8. **口径**：🔵 是否被算进丢星？待确认项是否被当成确认问题？架构/注释/可观测性建议是否被扣星？
9. **引用**：引用的规范条款是否真的存在？是否引用了已删除或不适用的文档？
10. **白话**：不读代码的人能否从“问题描述 + 影响”看懂发生了什么、为什么要改？

## 4. 约束与红线

- 禁止一次检查多个兄弟库，禁止把多个库的结论合并成一份报告。
- 禁止跳过任何维度；每个维度必须产出明确结论。
- 禁止只写“有问题”而不给文件、行号、影响和依据。
- 禁止把推测写成事实；不确定的问题必须标“待确认”。
- 禁止用“这段代码一直如此”“上游也这样”放过明显问题。
- 禁止直接复制其他库的检查结论作为当前库的结果。
- 禁止在未授权时修改源码、调整配置默认值或删除能力。
- 禁止用测试覆盖率、代码行数、文件数量作为质量结论；这些只是事实记录。
- 禁止把架构、注释、可观测性、测试覆盖类建议计入丢星。
- 禁止按文件数重复计算同一根因；同一问题只记一条。
- 禁止引用不存在的规范条款；未加载的知识文档不能作为判罚依据。
- 禁止在报告里保留与代码不一致的数字或过时快照。
- 修复必须真迁移：不保留类型别名、re-export、双哨兵等兼容层；对外协议兼容另行评估，不混入内部重构。

## 5. 验收标准（DoD）
