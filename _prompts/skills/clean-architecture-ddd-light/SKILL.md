# 清洁架构 + DDD-light

> **清洁架构定依赖方向；DDD-light 定业务边界；模块化定协作与演进节奏。**

本文是判断标准与操作规程，不是目录模板。语言、框架、目录名、模块系统、持久化方式、部署形态都不在本文范围内：先按工程已经在用的写法找到落点，再用本文的角色、可见性和依赖方向去审。需要某工程的具体骨架，看该工程自己的落地文档。

结论写在回复里。默认只判不改；调用方授权后再动代码。

---

## 1. 解决什么

| 症状 | 本文的回答 |
| ---- | ---------- |
| 规则散落在接口层、存储层 | 规则收敛到领域 |
| 接口层变薄了，Service 成了上帝类 | 把「编排」与「单域规则」拆开 |
| 多个入口复制业务逻辑 | 领域复用，差异只在编排 |
| 跨域随手引用对方实现 | 只依赖对方公开面 |
| 完整 DDD 太重、拖慢交付 | 保留上下文与契约，不强制战术仪式 |

**不必上本文的信号**：单入口、以存取为主、生命周期短、规则能一眼看完。此时简单三层往往更划算。硬套只会多出一堆空编排和转发层。

## 2. 五个角色（不是五个目录）

本文只认角色，不认目录名。一个目录可以承载多个角色（小系统），一个角色也可以拆多个目录（大系统）。

| 角色 | 一句话 | 做 | 不做 |
| ---- | ------ | -- | ---- |
| 适配层 | 把外部协议翻成领域无关的入参 | 解析协议、绑定与格式校验、调用编排、把结果与错误译回协议 | 业务分支、多域组合、直接读写存储 |
| 编排 | 一次业务动作的流程 | 身份上下文、跨域组合、一致性边界、出入参映射 | 复制领域规则 |
| 领域 | 什么合法、状态怎么变 | 不变量、状态机、唯一性、领域错误、持久化模型与领域模型互转 | 解析请求、依赖协议与框架、接管全局事务 |
| 基础设施 | 技术实现 | 仓储实现、外部网关、缓存、消息、文件 | 承载业务规则 |
| 共享编排策略 | 跨域不变量的可复用片段 | 跨域授权、多域一致性检查 | 单域业务规则、存储细节、协议解析 |

**「适配层」不等于路由**：HTTP、RPC、定时任务、消息消费的入口都算这一层。路由只是其中的分发动作；绑定、格式校验、结果与错误的回译也在这里。别用一个 router / controller 目录把角色缩小成分发器。

**为什么单列「共享编排策略」**：有一类规则换入口仍成立，但要同时看两个域才能判断（例如「最后一个超级管理员不能被删除」）。放进任一域，那个域就得反向依赖别的域；放进某个入口的私有区，别的入口会静默绕过。

**用词**：下文「契约」指能力契约，「共享策略」指共享编排策略；「入口」只指交付入口，接线用的那个叫「装配点」。

### 2.1 投影到具体工程

1. **先照工程已有的目录、命名和分层词汇**，不要为了套本文重命名整仓。评审时用工程自己的词指出角色，比要求改目录更有用。
2. **公开面只有三样**：本域公开类型、能力契约（含领域错误）、装配点。其余默认私有。
3. 语言或构建系统能表达可见性边界（模块、包、命名空间、导出规则）就用它把私有实现真正封住；表达不了，就靠目录约定加依赖检查，并在评审里守住。
4. 角色缺位比角色错位更容易出问题：没有编排，流程就会挤进适配层或领域；没有领域，规则就散在两边。

## 3. 依赖硬约束

**调用方向**：

```text
适配层 → 编排 → 领域 → 端口（仓储/网关抽象） ← 基础设施实现
```

**依赖方向必须向内**：内层不知道外层的存在，基础设施在端口后面实现，不反向指挥领域。

| 角色 | 可以依赖 | 禁止依赖 |
| ---- | -------- | -------- |
| 适配层 | 编排、基础设施中的技术工具与装配 | 领域私有实现、任何仓储端口与持久化模型 |
| 编排 | 各域公开面（类型、契约）、共享编排策略、事务 / 时钟 / 网关等基础设施抽象 | 任意域私有实现、任何仓储端口（查询同样走契约） |
| 共享编排策略 | 多个域的公开面、浅层错误与上下文工具 | 任意域私有实现、适配与编排的具体实现 |
| 领域 | 本域内部（含端口与持久化模型）、按需的其他域公开面 | 适配层、编排、共享策略、其他域私有实现 |
| 基础设施 | 领域端口、本域私有持久化模型、技术库 | 反向指挥领域 |

**口诀**：领域依赖了编排或外域私有实现 → 打回；共享策略依赖了领域私有实现 → 打回；编排或适配层摸到了仓储端口 → 打回。

**仓储是特例**：仓储端口与持久化模型都在领域私有区，仓储实现也必须待在能看见它们的位置——不要把仓储拆到领域之外，再为了让实现能编译而把持久化模型公开出去。

**领域直接依赖另一个域的公开面是允许的，但那是边界之外的耦合**：能由编排组合的，优先交给编排；只在类型或契约确实必需时才直连，并且只碰公开面。

## 4. 业务边界

**按业务能力与不变量切，不按页面、接口、技术层或「某某 Service」切。**

判断边界只需要一个动作：把整个交付层换掉（HTTP → RPC → 定时任务 → 消息消费），哪些概念和规则会一起搬走？会一起搬走的是一伙。

| | 内容 |
| - | ---- |
| 公开面 | 跨边界需要的类型、能力契约、领域错误、装配点 |
| 私有面 | 持久化模型、仓储实现、内部服务实现、算法细节 |

**统一语言**：界内一个概念一个名字，用业务词汇而不是技术词汇。同一个词在界内只有一种含义；想换个说法时，先确认它是另一个概念，还是命名还没定。

### 4.1 类型随域走

不要上收成全局业务类型库：

- 跨域需要对方的类型 → 依赖对方的公开类型，不要复制一份「差不多的」。
- 两个域反复争改同一个结构 → 先怀疑边界切错，或加防腐层做转换；**不要**再抽「公共模型」把两个域焊死。
- 「公共基础类型」只放真正没有业务含义的东西（标识、时间、分页这类）。带业务含义的都不算。

### 4.2 双模型（硬要求）

| | 领域模型 | 持久化模型 |
| - | -------- | ---------- |
| 用途 | 表达业务含义、跨边界传递 | 对接存储 |
| 谁经手 | 领域服务对外只给这个 | 仓储端口收发这个 |
| 可见性 | 公开（或域内公开） | 私有，只在领域私有区内流转 |
| 变化理由 | 业务语义变了 | 存储结构变了 |

**职责分工固定**：

```text
存储 ⇄ 仓储（持久化模型）⇄ 领域服务（转换点）→ 领域模型 → 公开面
```

- **仓储只碰持久化模型**：入参、返回值都是持久化模型，不认识领域模型。
- **领域服务负责转换**：读到持久化模型后转成领域模型再对外返回；写入时反向转回持久化模型交给仓储。
- **对外只见领域模型**：能力契约、跨域调用、跨边界返回一律是领域模型。

**必须分开，没有例外**：领域模型与持久化模型是两个模型，不是同一个类的两种叫法。领域不得暴露持久化模型——不返回、不入参、不继承、不作为领域实体的字段。

落地判据：

- 存储细节（表名、列名、索引、软删除列、审计列、序列化标签）不出现在领域模型上。
- 持久化模型不跨出领域私有区：不出现在能力契约里，也不出现在适配层、编排或共享编排策略里。
- 两边改动的理由不同：业务语义变了改领域模型，存储结构变了改持久化模型。如果一个改动两边都要跟着变，说明还没分开。
- 转换点只有一处：领域服务。别把它往上推给编排或适配层，也别让这两层见到持久化模型。

**这是一处有意的取舍**：领域因此知道存储结构长什么样（仓储端口与持久化模型都在领域私有区，见 §3）。换来仓储与映射简单、集中；代价是存储结构变了会波及领域私有区。所以持久化模型必须锁在私有区里只做内部搬运，一旦外溢就变回「共用模型」。

### 4.3 领域错误是契约的一部分

领域错误定义**稳定语义**（不存在、冲突、非法状态、不允许的操作），由适配层负责投影成协议错误。领域错误里不要带状态码、错误编号、字段名这类传输细节。

## 5. 规则归属

按顺序问，命中即停：

```text
这条规则，换一个入口还成立吗？
├─ 是 ──► 领域（若需同时深入两个域 → 拆契约，交给编排或共享策略）
└─ 否 ──► 依赖本次请求的身份 / 幂等 / 事务范围吗？
          ├─ 是 ──► 编排
          │         └─ 必须在所有入口生效 ──► 共享编排策略；
          │            仍会分叉 ──► 下沉领域，把操作者作为显式入参传进去
          └─ 否 ──► 这个入口特有的浅层规则，留在编排或适配，不下沉领域；
                    若它其实是业务不变量，说明第一问答错了
```

| 规则 | 落点 |
| ---- | ---- |
| 聚合完整性、状态机、唯一性、字段格式 | 领域 |
| 换入口仍成立的不变量 | 领域 |
| 跨域步骤编排、事务与幂等边界 | 编排 |
| 依赖本次会话身份的授权判断 | 编排；不变量本身属领域的，把操作者作为显式入参传进去，不让领域读会话 |
| 需组合多个域的可复用不变量 | 共享编排策略；多入口都要就得抽出去 |
| 协议空值、分页默认、字段名转换 | 适配（协议层归一，不替代领域规则） |

**口诀**：换入口仍成立 → 领域；依赖本次请求身份、幂等、事务或多域组合 → 编排。两者都像，先看换入口会不会变。

**常见错放**：

| 错放 | 后果 |
| ---- | ---- |
| 规则写进适配层 | 换入口就复制一遍，两份迟早分叉 |
| 规则写进编排 | 领域退化成数据访问，规则无法脱离会话单测 |
| 跨域判断塞进某个域 | 该域反向依赖别域，边界名存实亡 |

## 6. 读写路径、一致性与错误

```text
适配层 → 编排 →（一致性边界：事务 / 幂等 / 重试）→ 领域 → 端口（持久化模型）→ 存储
```

- **模型转换归领域服务**：仓储端口收发持久化模型，领域服务转成领域模型后再往外给。编排和适配层永远看不到持久化模型。
- **一致性边界归编排**：领域不知道事务存在，也不负责开启它。领域服务被编排包裹，才可组合、可单测。
- **领域不接管全局事务、不自行幂等**。它只保证「在一个已经开启的边界里，这些规则成立」。
- **读路径同样走契约**：列表、报表这类查询也不能直摸存储或返回持久化模型；要专用投影就把它做成公开类型放进契约，别靠暴露存储结构省事。
- **跨进程的写各侧各自提交**，需要一起进退就用补偿或对账；不要把远程写塞进本地事务。
- **领域错误保持语义稳定**，编排不改写业务含义；编排只负责把「编排失败」和「业务失败」分开。
- **浅层错误按层归属**：解析与绑定失败归适配；会话失效与权限不足归编排或共享策略；投影成协议错误统一在适配层完成。

## 7. 跨域与装配

**允许**：

- 编排组合多个契约；
- 装配期注入其他域契约；
- 按需使用事件。

**禁止**：

- 碰外域私有实现；
- 复制外域持久化模型；
- 新建全局业务类型库；
- 编排直接持有任何仓储（别域的、自己域的都不行）。

**两级装配**：每个域内部自己组装，产出可用的模块 → 交付侧只负责把模块接到编排与适配。装配代码负责连线，不负责业务判断。

**装配与启动不是业务角色**：把模块接到编排、适配上的那层代码（bootstrap / wiring）不在这五个角色之内，可以放在交付侧，也可以单独成目录。它只连线，不做判断——一旦出现分支、默认值兜底或顺序性业务逻辑，说明有逻辑放错了地方。

**横切能力**（日志、审计、幂等、事务、鉴权）注入编排，不穿透进领域实现。

**事件的位置**：只有「发出去之后不要求当前调用成功」的语义才用事件。要求同生共死的写，用事务，不要用事件假装一致。

## 8. 与 MVC / 经典 DDD 的关系

### 8.1 主矛盾不同

| | MVC / 三层 | 本文 |
| - | ---------- | ---- |
| 经典目标 | 界面与数据的分离 | 业务策略与交付入口的分离 |
| 典型场景 | 页面驱动、以表单 CRUD 为主 | 多入口、规则复杂、领域需长期复用 |
| 成功标准 | 页面可维护、交互清晰 | 规则可测、可复用、依赖可评审 |

MVC 本身没问题，客户端继续用 MVC / MVVM 完全正常。真正的痛点是：**Controller 变薄之后，Service 变成上帝类**——一个类注入大量仓储，跨表跨模块交叉读写，规则、流程、持久化搅在一起。本文针对的正是这种「入口瘦了、服务胖了」的结构性膨胀。

### 8.2 上帝类为什么会出现

1. **按接口堆方法**：新接口就在「对应 Service」里加一段，Service 随接口数膨胀。
2. **用仓储当集成点**：跨模块协作不经明确边界，直接注入对方仓储。
3. **编排与规则不分**：事务、校验、状态机、查库全写在同一处。
4. **缺少边界**：没有「哪些概念不能进这个 Service」的硬约束。

结果是：入口看起来很干净，复杂度全沉到服务里——更难测、更难拆、更难复用。

### 8.3 结构对照

| 维度 | 典型三层 | 本文 |
| ---- | -------- | ---- |
| 主分离轴 | 接口 / 服务 / 模型 | 编排 / 领域 / 基础设施 |
| 适配层 | 可薄，但薄不等于健康 | 极薄：绑定与委托 |
| **服务层** | **易成上帝类**：流程 + 规则 + 多仓储交叉 | 拆成**编排**与**领域** |
| 仓储使用 | 任何服务都能注入多个仓储，靠自觉 | 仓储留在领域私有区，编排也不直接持有；查询同样走契约 |
| 模型 | 常混数据、持久化、部分规则 | 持久化私有；跨边界用域模型 |
| 边界 | 常按页面、接口或「某某 Service」切 | 按有界上下文切 |
| 多入口 | 易复制，或继续堆进同一个大服务 | 领域复用，入口只换编排 |
| 依赖方向 | 常无强制 | **依赖向内**是硬约束 |

### 8.4 取舍

**三层的优点**：概念少、路径短、上手快；小系统交付快；接口层变薄后短期「看起来很干净」。

**三层的缺点**：服务上帝类；仓储交叉导致边界名存实亡；多入口时规则复制或继续汇入同一个大服务；纯规则难单测，常与事务、多表访问绑死。

**本文的优点**：用「编排 vs 领域」拆开上帝类的两种职责；跨域禁止仓储交叉；规则可单测、可复用；依赖可评审。

**本文的缺点**：前期概念与样板更多；需要统一「规则放哪、编排放哪」，否则会出现空编排或胖领域；偷建全局业务类型库仍会重新耦合。

### 8.5 何时迁移

| 信号 | 更合适 |
| ---- | ------ |
| 单入口、简单存取、生命周期短 | 三层往往够用 |
| 多入口、规则复杂、服务已成上帝类、仓储交叉严重 | 本文 |
| 入口已瘦，但服务难测、难拆 | 优先拆编排与领域，而不是再抽「公共 BaseService」 |

迁移顺序：

1. **按有界上下文切开上帝类**（先定边界，再搬代码）。
2. **跨上下文的仓储注入改为契约调用**；跨上下文流程升到编排。
3. **单上下文规则留在领域**；入口保持薄。

只改目录名、不改「谁持有哪些仓储」，通常无效。

### 8.6 DDD-light 的取舍

**采用**：有界上下文、统一语言、能力契约、域内仓储、按需事件与策略。

**弱化**：显式聚合根、跨层公开仓储、默认全域事件、CQRS/ES、繁琐值对象。

| 经典 DDD | 本文 |
| -------- | ---- |
| 富聚合根 | 公开实体 + 领域服务守不变量（可渐进变富） |
| 仓储作跨层端口 | 仓储私有，对外只有能力契约 |
| 共享内核上收 | 类型留在本域，随域走 |
| 用例只在应用层 | 领域服务与应用编排拆开 |

## 9. 演进：从同仓到独立发布

领域从第一天就该是可以独立发布的最小单元候选：公开面与私有面分开，公开面稳定后整体搬出去，依赖方向不变。

```text
阶段 1  同仓协作开发
阶段 2  域模块独立发版
阶段 3  消费方按标准依赖引用
```

只变「从哪里解析、怎么发版」，不变依赖方向。公开面始终是：类型、契约、装配点；私有实现永不当跨模块 API。

| 宜留同仓 | 宜独立发布 |
| -------- | ---------- |
| 契约与类型剧烈抖动 | 公开面已稳定 |
| 消费方少且同团队 | 多入口或多仓消费 |
| 本地联调是主要矛盾 | 发布节奏互相阻塞 |

**口诀**：先有界、后版本、再拆仓。

不必为了「以后可能拆」现在就拆。但公开面与私有面从第一天就分清，这几乎零成本，拆的时候才不用重写。

## 10. 反模式

1. 适配层或编排直接访问仓储、写存储细节。
2. 领域模型与持久化模型共用一个类；或持久化模型离开领域私有区，出现在公开面、适配层、编排或共享策略里。
3. 领域依赖请求上下文（会话、当前用户、语言、链路标识）。
4. 编排复制领域校验（两层结论迟早分叉）。
5. 跨域引用私有实现。
6. 全局业务类型库，或把编排塞进公开类型区。
7. 领域依赖交付层，或依赖某个入口私有的编排与策略。
8. 领域私自接管全局事务、幂等或重试。
9. 共享编排策略里塞单域业务规则，或反过来依赖域私有实现。
10. **空编排 + 胖领域**：所有流程都塞进领域，编排只做转发——和上帝类 Service 是同一个病，只是换了个名字。
11. 为了让依赖图好看造一批只转发的层，反而让主路径行为说不清。
12. 把「必须跨入口生效」的不变量只放在某一个入口的私有策略里。

## 11. 检查清单

### 评一段现有代码

- [ ] 这条规则换入口还成立吗？现在放的位置会随入口变化吗？
- [ ] 有没有跨域私有引用（直接摸对方的仓储、持久化模型、内部实现）？
- [ ] 领域模型和持久化模型是不是两个类型？仓储只收发持久化模型、领域对外只给领域模型，转换是不是都落在领域服务？
- [ ] 事务、幂等开在编排，还是漏进了领域？
- [ ] 编排里有没有抄领域已经做过的校验？
- [ ] 适配层和编排有没有直接持有仓储？（查询也算）
- [ ] 适配层里有没有业务分支？

### 新领域 / 拆领域

1. 写清上下文、非目标、对外词汇。
2. 定公开面（类型、契约、错误、装配点），其余默认私有。
3. 纳入依赖检查；补领域单测——规则能脱离事务与网络单独跑起来才算合格。
4. 交付侧接线，装配只连线。

### 新接口

1. 这条规则需要补契约，还是编排已有契约就够？
2. 编排在写路径上包住一致性边界；适配保持薄；装配只接线。
3. 授权判断放编排或共享策略；涉及操作者的业务不变量若下沉领域，把操作者作为显式入参传进去，不让领域读会话。

### 多入口

1. 新入口只复用领域公开面；入口自己的编排与策略各自独立，不互相引用。
2. 是否存在必须跨入口生效的授权或一致性不变量？有则下沉领域（操作者显式入参）或抽成共享编排策略，不能只留在单入口——否则新入口会静默绕过。

## 12. 边界判定示例

**领域词汇里出现「接口路径 / 界面路径」，算不算领域承载路由？**
判断标准不是词汇长什么样，而是领域有没有解析请求、有没有依赖 Web 框架。若适配层先把请求解析成「资源」对象再交给领域，领域只是给资源打标签，不算越界。

**配置和运行时实例能不能共用一个模型？**
通常不能：配置是启动期常量，实例是运行期状态，生命周期与变更方式都不同。别揉成「万能模型」。

**两个域都需要的类型放哪？**
放说出它的那个域，另一个域依赖它的公开面。都不太像「它的」，说明这个类型很可能横跨了边界，先看是不是切错了。

## 附录：最小心智模型

```text
编排：怎么接请求、怎么组合多域、怎么保证写一致
领域：什么合法、状态怎么变
类型：属于某个域，随域走
```

方法论管原则与边界；工程约定管目录与技术选型；规格管业务；代码与测试是真源。
