# 代码巡检

检查调用方指定的代码模块。不区分业务模块还是基础库，用同一套方法：先取证，再对照，再分级。先看这个模块实际怎么组织、怎么写、怎么开事务，再对照《事务设计规范》；代码里出现 Redis Key 时再对照《Redis设计规范》。依据是模块自己的对外契约、范围内能指出的既有写法，以及本次加载的知识文档。

本 Skill 独立使用，不依赖需求显化、审核或落地工作流，也不规定目录名、类型名、注册函数、表前缀或组件选型。这些以目标工程里已经在用的写法为准。知识库里没有的条款，不得当作依据。

---

## 1. 目标

- **做什么**：对指定模块通读源码，用命令核实可疑行为，按同一套观察—验证—对照—分级的方法写出带位置和依据的问题清单；调用方授权后才改代码，并把结果回写同一份报告。
- **为什么**：没有固定方法时，容易凭阅读印象打分，或把「长得不像某一份示例」报成缺陷，真正的契约、正确性和事务问题反而被放过。
- **不做什么**：
  - 不检查前端
  - 不做压测、渗透测试、容量规划
  - 不把测试覆盖率、文件数、行数当作质量结论
  - 不替代编译、vet、测试等自动工具，而是在其之上做人工审查
  - 未经调用方明确授权，不改源码

---

## 2. 输入

**必需**：要检查的模块，目录、包或文件均可。一份报告对应一次指定的范围；一次点了多个互不包含的模块，就分别出报告，不要混检。

未给范围时，先列出仓库里能看到的可部署单元和入口，在报告里写明本次实际打开了哪些包。未打开的包不写结论。不要假设目录名叫 `services`、`internal/biz`、`component` 或其他固定名字。

范围内未明确排除的文件不得跳过。历史报告、生成代码、第三方 vendored 代码不作为判罚对象；要指出第三方行为时，只当作影响说明的证据。

另外两项以调用方为准：

- 检查重点。未说明时按本文全部维度走；范围内看不到的维度标「不适用」。
- 是否允许修复。未说明时只检不修。

知识文档：

| 文档 | 何时加载 |
| ---- | -------- |
| `_prompts/knowledge/事务设计规范.md` | 范围内有写路径时，通读后作为事务维度的依据 |
| `_prompts/knowledge/Redis设计规范.md` | 范围内出现 Redis Key 时，通读后只核对 Key 命名 |

未加载的文档不能作为依据。仓库里若还有别的约定，只有调用方点名，或代码写明「遵循某约定」时才引用，并在发现里写明条款。约定里没有的内容，不得判违规。

---

## 3. 工作立场

先记下代码里能指出来的事实，再判断。观察不到的形态不补想象。可疑行为优先用命令或临时探针确认，不能只凭阅读印象。

专门找这几类洞：

- 事务边界错了：该一起消失的写不在同一次提交里，或远程调用、缓存、消息、对外响应被放进事务
- 本模块已经公开的行为被做窄、做宽或做反
- 和本工程已经稳定在用的写法不一致，而且这处不一致会让行为分叉
- 注释描述的契约和当前行为相反
- 在本工程真实调用方式下会崩溃、泄漏、死锁，或把数据写成违反契约的状态
- 导出面泄漏了内部实现，或返回值与内部状态共享，调用方一改就破坏不变量
- 资源、后台任务、锁和取消在真实退出路径上收不干净

下面这些不进入发现列表：

| 情形 | 怎么处理 |
| ---- | -------- |
| 目录名、文件名、类型名、注册方式、框架函数和某份示例不同 | 只用来定位，不单独构成问题 |
| 工程里没有某一种服务形态、中间件或表 | 对应维度写「不适用」，并写明范围内没看到什么 |
| 只有一处样本的写法 | 单一样本不是约定，不据此判其他代码违规 |
| 《Redis设计规范》声明不管的内容 | 不检查 TTL、数据结构、缓存一致性、锁 |
| 《事务设计规范》没有点名的框架、包和函数 | 审事务是否满足那份规范里的三条，不要求换成某个组件 |
| 自解释的代码没有注释 | 不记缺失 |
| 测试覆盖率高低、文件数、行数 | 只作规模记录，不记为问题 |
| 没有测量依据、也没有可达热点的「优化」 | 不提 |
| 只在极端输入下出现，且本工程到不了这条路径 | 不记；拿不准时标「待确认」，不计为已确认问题 |

检查阶段禁止顺手改代码。修复阶段与检查阶段分开。

---

## 4. 检查顺序

```text
开始
  ↓
1. 确认检查单元、包含/排除范围、是否允许修复
  ↓
2. 记录快照与规模
  ↓
3. 通读包注释、导出 API、配置、测试与写路径，建立事实底稿
  ↓
4. 做可执行验证，记录命令与结果
  ↓
5. 按维度逐项对照，边查边记文件行号
  ↓
6. 分级、整理待确认项，做落盘前自检
  ↓
7. 落盘报告
  ↓
8.（可选，需授权）修复 → 重新验证 → 复审回写同一份报告
  ↓
结束
```

通读范围内的入口、写路径和被调用的包之后再记发现。每一维都要有结论：通过、存在问题，或不适用。不适用要写一句话原因。「未发现问题」也是结论，不得跳过该维。

### 4.1 确认单元与快照

1. **检查单元**：调用方指定的那一个范围，含其直属子包。开始前写清包含与排除。
2. **快照**：`git rev-parse --short HEAD` 与 `git status --short`。报告对应这份快照。复审时先确认报告对应的是哪个快照。
3. **规模**：包数、Go 文件数、测试文件数、非测试行数。写进报告，避免数字与代码对不上。能用仓库已有命令统计就用；没有则按范围内文件清点，并写明统计方式。

### 4.2 先观察

记入报告，不在这里下结论。至少看清：

1. **包与职责**：这些包各自做什么。以包注释、入口和调用关系为准，不靠目录名猜。
2. **对外契约**：导出了什么、注释和测试固定了什么、范围内谁在调用。没有测试或调用方就写明。能列出导出符号时列出，标出疑似内部实现泄漏。
3. **配置**：有没有运行时配置、文件绑定、默认值、开关。`0` / 空值表示「不限制」还是「未设置」必须看清。没有配置就写明。
4. **依赖**：这个模块依赖谁、谁依赖它。方向以范围内已经稳定的分层为准。
5. **写路径**：写从哪里开始，事务在哪里开启和结束，失败时哪些写会一起消失。没有写就写明。
6. **数据访问**：用什么访问数据，同类查询现在怎么写，模型和表怎么对应。以范围内已经存在的写法和能看到的表或迁移为准。
7. **跨进程的写**：有没有调用其他服务或资源，现在怎么收场。
8. **生命周期**：有没有构造、启动、关闭、后台任务。没有就写明。
9. **Redis**：有没有 Key，现有 Key 的模式是什么。没有就写明。
10. **测试**：测试固定了哪些正常、边界和失败路径；是否依赖外部服务。不以覆盖率论好坏。

看不到的项写「未观察到」。

需要实测时，探针放在仓库根 `.tmp/{模块名}-review/`，不得放进源码树；用完清理，并确认 `git status --short` 没有残留。

### 4.3 可执行验证

检查阶段按需执行，并在报告「实测记录」里逐条写明命令与结果。优先用该工程已经在用的编译和检查命令；看不到既定命令时，对范围内的包至少做编译和静态检查，有测试则跑测试。

| 目的 | 做什么 |
| ---- | ------ |
| 编译 | 范围内能编译 |
| 静态检查 | vet 或工程等价命令 |
| 测试 | 相关测试；依赖外部服务时收窄到可安全运行的用例，不连生产或共享环境 |
| 竞态 | 范围内有共享状态或自行起 goroutine 时加竞态检查；工具链做不到时写明原因，改用探针加人工审查 |
| 导出面 | 列出导出符号，核对是否泄漏内部实现 |
| 依赖方向 | 列出依赖，核对有没有反向依赖 |
| 格式 | 只检查不改写 |

规则：

- 没有执行过的命令不得写成「已通过」。不能执行时写明原因。
- 禁止在检查阶段修改源码来「让测试通过」。
- 探针不得使用被测包以外的私有符号。
- 报告中的规模数字必须与统计结果一致。

### 4.4 对外契约与设计

口径是本模块已经暴露出去的行为：导出签名、注释里的约定、测试所固定的结果、范围内能看到的调用方。没有测试、没有调用方：不把「缺测试」记成问题；只审代码自身是否自相矛盾。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 导出行为 | 同名导出在各入口下行为一致 | 行为分叉：警告；主路径结果已经不同：严重 |
| 失败与空值 | 调用方能从签名、注释或返回值看出失败和空值 | 主路径无法判断：警告 |
| 已公开的范围 | 已经公开的行为没有被静默缩小或做反 | 主路径：严重；旁路：警告 |
| 导出面 | 只导出调用方需要的类型和函数 | 仅内部使用的辅助类型被导出：警告；因此破坏不变量：严重 |
| 实现泄漏 | 公开 API 不把内部存储、连接或可变状态交出去 | 调用方能改内部状态：严重 |
| 返回值所有权 | 返回的切片、map、指针不与内部状态共享，或文档写明所有权 | 调用方一改就破坏内部状态：严重 |
| 零值与构造 | 零值可用，或必须经构造函数；构造会完成必要初始化 | 零值使用会 panic 或静默写坏：严重 |
| 错误契约 | 非法入参返回错误；panic 只出现在文档写明的 Fail Fast 边界 | 库路径上 panic 或把错误吞成成功：严重 |
| 抽象 | 每层都有独立职责 | 只转发、无替换价值的包装：建议；因此让主路径行为说不清：警告 |

### 4.5 正确性

结合本工程实际的调用方式和配置看会不会发生，不按代码形态扣分。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 失败 | 失败被返回或按契约处理，没有被当成成功 | 主路径把错误吞成成功：严重 |
| 空值 | 指针、接口、map、channel、切片在 nil 下安全 | 会 panic 或写坏：严重 |
| 边界 | 空输入、单元素、最大长度、负数、溢出、递归终止是安全的 | 主路径：严重；特定合理输入：警告 |
| 资源 | 文件、连接、goroutine、定时器、订阅在退出路径上能释放；关闭幂等、尊重取消 | 泄漏或关不掉：严重 |
| 并发 | 共享状态有保护；锁不包外部回调；不返回内部可变别名 | 竞态、死锁：严重 |
| 取消 | 请求路径尊重调用方截止时间；不把取消上下文存进长生命周期对象 | 取消后仍占用资源或继续写：严重 |
| 崩溃 | 包内自行启动的 goroutine 失败能被看见，不会静默消失 | 严重 |
| 契约 | 重复提交、不允许的状态、半成功的结果和本模块已经公开的行为一致 | 主路径：严重 |

到不了的路径不记。拿不准是否到得了：待确认。

模块承担启动、关闭或后台任务时，额外看：关闭是否幂等、是否先停任务再放资源、失败时是否清理本次已申请的资源。没有这类生命周期：本项不适用。

### 4.6 事务

范围内没有写路径：不适用。

有写路径时，按《事务设计规范》对每一处写回答三个问题：

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 要不要开 | 能一句话说清这个事务保护哪条不变量；只读、以及单次已被存储保证原子的写，没有被多余地包进事务 | 说不清保护什么却开了事务，或「先读再判断再写」既没进事务也没下推到存储：严重 |
| 边界 | 失败时必须一起消失的写在同一次提交里；参与写决策的读与写同事务，或判断已下推到存储 | 主路径会留下半成功：严重 |
| 事务里放了什么 | 只有本事务资源上的读写和必要的轻量计算 | 远程调用、缓存、消息、文件、对外响应、等待或事务内重试放在事务里：严重 |
| 传递 | 调用链已在同一事务中则加入并复用，提交点归最外层 | 静默又开一个会独立提交的事务：严重；确需独立提交但没有写明外层回滚不会撤销它：警告 |
| 同生共死的辅助记录 | 必须和业务写一起消失的记录（如幂等凭证）在同一事务里 | 业务写回滚后凭证仍在，或相反：严重 |

工程用什么机制开启事务，就审那个机制。不要求出现某个包名或函数名。

### 4.7 分层、依赖与封装

不检查「是否存在某个目录」。检查行为是否和本工程已经稳定的职责划分一致。

「本工程的做法」要能指出至少两处一致的现有代码。只有一处样本时，不据此判其他代码违规。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 职责 | 协议适配和业务规则分开；谁拥有这个原子动作，事务就在那一侧开启 | 规则和协议搅在一起，导致主路径行为说不清：严重；只是放错了文件、行为仍然正确：警告 |
| 跨进程的写 | 各侧各自完成本侧事务；需要一起进退时有补偿或等价的收场，而不是把另一侧的写塞进本侧事务 | 严重 |
| 依赖方向 | 和已观察到的方向一致 | 下层反过来依赖上层：严重 |
| 平行实现 | 工程已经依赖的能力，业务路径没有再做一份行为不同的实现 | 两份行为会分叉：警告；分叉已经导致主路径结果不同：严重 |
| 配置从哪来 | 模块通过参数或配置对象接收设置，不在内部私自读环境或配置文件 | 内部偷读配置导致调用方无法注入：警告；因此主路径用错配置：严重 |
| 全局状态 | 没有可变包级状态，或有明确的并发与测试隔离办法 | 测试无法隔离或并发无保护：严重 |

工程没有分层，或范围内只有一个包：不记「缺少某一层」。工程没有依赖某份库：不要求接上它。

### 4.8 数据访问

范围内没有数据访问：不适用。

口径是范围内已经在用的访问方式和能看到的表或迁移。不另定基类、tag 或表前缀。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 同类查询 | 同一种条件的写法一致；外部输入没有被拼进 SQL 文本 | 外部输入被拼进 SQL：严重；同类查询各写各的，读起来会用错条件：警告 |
| 模型与表 | 代码读写的列和能看到的表一致，包括空值与删除语义 | 主路径列对不上：严重；看不到表或迁移：标待确认，不编造应有哪些列 |
| 事务 | 参与当前事务的访问使用调用上下文里的那次事务，不另开一条会独立提交的连接 | 严重 |

### 4.9 Redis Key

范围内没有 Redis Key：不适用。

有 Key 时只核对《Redis设计规范》：冒号分层、小写、字符集、标识稳定、同类数据共用同一模式。

同一类数据用了两套前缀或两套分隔：警告；两套模式已经让读写找不到同一条数据：严重。

### 4.10 表结构

只在本次范围改了表结构，或调用方明确要求看表时检查。只读写已有表、结构不动：不适用。

新表和改列与目标库里已经在用的口径对齐：命名、主键如何生成、审计列、删除如何表达、索引如何命名。看不到存量表时，这些项标待确认，不套一套前缀和字段清单。

和存量表口径冲突：警告；因此主路径读写会错：严重。

### 4.11 编码与可维护性

对照本模块已经稳定的写法，不另套一份语言习惯清单。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 错误传播 | 错误保留原因链，和本模块已有包装方式一致 | 丢掉原因导致调用方无法判断：警告；因此主路径把失败当成成功：严重 |
| 释放 | 解锁、关闭、恢复用能保证执行的方式 | 锁或资源在失败路径上泄漏：严重 |
| 死代码 | 没有无调用方的导出、配置项或主路径分支 | 无调用方的导出仍被当成契约：警告 |
| 日志与输出 | 不直接打印；不输出秘密 | 打出秘密：严重；直接打印且本工程另有日志入口：建议 |
| 同类命名 | 同一概念在本模块内同名同义 | 读起来会用错：警告 |
| 重复 | 三处以上相同逻辑才考虑抽取；只有一处实现、无替换需求的接口不强行抽象 | 重复已经导致行为分叉：警告 |
| 校验重复 | 同一规则不在多层各判一次还互相打架 | 边界上的校验和内部校验结论相反：严重 |

### 4.12 注释

只记会让人按错误契约使用代码的注释。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 注释与行为 | 注释里的副作用、空值、是否幂等、默认值与当前代码一致 | 按注释调用会走错：警告；主路径会写错数据：严重 |
| 关键导出 API | 签名读不出的契约，在注释或调用处能看懂 | 主路径调用方无法判断失败和空值：警告 |

自解释的代码没有注释，不记缺失。不为「缺包注释」「缺函数注释」单独记问题，除非因此让人按错误契约调用。

### 4.13 优化

没有可达场景的优化不提。必须说明在什么调用下才有收益。不要为了性能建议引入新的第三方依赖。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 热点浪费 | 可指出的热点路径上没有明显可避免的重复分配、重复解析或锁内 I/O | 建议；已导致主路径超时或打满：警告 |
| 过早优化 | 没有为不存在的问题增加复杂度 | 建议 |

## 5. 分级

| 级别 | 何时使用 |
| ---- | -------- |
| 严重 | 按现在的代码走，主路径会写错、提交错、崩溃、泄漏，或和本模块已经公开的契约相反 |
| 警告 | 主路径暂时还能跑，但后续会返工，或特定合理输入下会错 |
| 建议 | 不影响正确性，只影响阅读、局部一致或可测量的局部浪费 |

按后果判级，不按代码形态判级。只有前后语义互斥、事务边界断裂，或调用方能观察到的结果是错的，才把「写得不够整齐」升成严重。架构、注释、可观测性、测试覆盖类意见默认是建议。

编号为「发现 1」「发现 2」……整份报告连续。顺序为严重、警告、建议。同一根因在多处出现只记一条，位置列全。

### 6.3 修复与复审

  - 逐条状态：已修复、部分处理、按调用方决定不处理、误判撤销
  - 行为变化，以及还没盖住的部分
  - 复审要重新读代码，不沿用上一轮的结论
- 调用方只修一部分是正常情况：未修项标「部分处理」或「按调用方决定不处理」，不得写成「已修复」。

## 7. 约束

- 先写观察和实测，再写发现。未打开的包不写结论。
- 目录名、类型名、组件名不构成问题。问题必须是行为、事务边界或调用方能观察到的契约。
- 每一维都有结论。不适用写原因。
- 每条发现都有位置、现状、影响、依据、建议。依据来自已加载的知识文档、本模块的对外契约，或本工程里能指出的既有写法。
- 推测标成待确认。待确认不写成已确认问题。
- 同一根因只记一条。
- 未授权不改源码。
- 不引用知识库里已经不存在的文档，也不把《事务设计规范》《Redis设计规范》没有写的条款补进去。
- 不把其他模块的检查结论复制到当前模块。
- 不用「这段代码一直如此」放过已经能指出来的主路径错误。
