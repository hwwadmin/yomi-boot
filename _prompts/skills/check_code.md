# 代码巡检

巡检业务 Go 代码。先看这次范围内代码实际怎么分层、怎么写、怎么开事务，再对照《事务设计规范》；代码里出现 Redis Key 时再对照《Redis设计规范》。有关联显化稿时，以稿里已经写明的事务切入点、接口和表为准。

本 Skill 不规定目录名、类型名、注册函数、表前缀或组件选型。这些以目标工程里已经在用的写法为准。知识库里没有的条款，不得当作依据。yomi-boot 基础库用《基础库检查》，不走本 Skill。

---

## 1. 目标

- **做什么**：对调用方指定的业务 Go 代码做巡检，写出带位置和依据的问题清单；调用方授权后才改代码，并把结果回写同一份报告。
- **为什么**：固定目录清单会和工程真实结构脱节，把「长得不像示例」报成缺陷，真正的事务和契约问题反而被放过。
- **不做什么**：
  - 不检查 yomi-boot 基础库
  - 不检查前端
  - 不做压测、渗透测试、容量规划
  - 不改显化稿和审核稿
  - 未经调用方明确授权，不改源码
  - 不把测试覆盖率数字当作质量结论

---

## 2. 输入

**必需**：要巡检的目录或文件。

未给范围时，按下面顺序收束，收束结果写进报告：

1. 调用方给了显化稿，或本次对话里刚落地过一份稿：只打开稿里点名的领域、接口、表所在的包。
2. 仍然定不出包：先列出仓库里能看到的可部署单元和入口，在报告里写明本次实际打开了哪些包。未打开的包不写结论。

不要假设目录名叫 `services`、`internal/biz` 或其他固定名字。

另外两项以调用方为准：

- 关联显化稿的路径。给了就对照；没给就写「无显化稿，不对照设计」，不把缺稿当成问题。
- 是否允许修复。未说明时只检不修。

知识文档：

| 文档 | 何时加载 |
| ---- | -------- |
| `_prompts/knowledge/事务设计规范.md` | 范围内有写路径时，通读后作为事务维度的依据 |
| `_prompts/knowledge/Redis设计规范.md` | 范围内出现 Redis Key 时，通读后只核对 Key 命名 |

未加载的文档不能作为依据。仓库里若还有别的约定，只有调用方点名，或代码、显化稿写明「遵循某约定」时才引用，并在发现里写明条款。约定里没有的内容，不得判违规。

## 3. 工作立场

先记下代码里能指出来的事实，再判断。观察不到的形态不补想象。

专门找这几类洞：

- 和关联显化稿冲突：写的范围被做窄、做宽或做反
- 事务边界错了：该一起消失的写不在同一次提交里，或远程调用、缓存、消息、对外响应被放进事务
- 和本工程已经稳定在用的写法不一致，而且这处不一致会让行为分叉
- 注释描述的契约和当前行为相反
- 在本工程真实调用方式下会崩溃、泄漏、死锁，或把数据写成违反契约的状态

下面这些不进入发现列表：

| 情形 | 怎么处理 |
| ---- | -------- |
| 目录名、文件名、类型名、注册方式、框架函数和母版示例不同 | 只用来定位，不单独构成问题 |
| 工程里没有某一种服务形态、中间件或表 | 对应维度写「不适用」，并写明范围内没看到什么 |
| 只有一处样本的写法 | 单一样本不是约定，不据此判其他代码违规 |
| 《Redis设计规范》声明不管的内容 | 不检查 TTL、数据结构、缓存一致性、锁 |
| 《事务设计规范》没有点名的框架、包和函数 | 审事务是否满足那份规范里的三条，不要求换成某个组件 |
| 自解释的代码没有注释 | 不记缺失 |
| 测试覆盖率高低 | 不记 |
| 只在极端输入下出现，且本工程到不了这条路径 | 不记；拿不准时标「待确认」，不计为已确认问题 |

## 4. 巡检顺序

通读范围内的入口、写路径和被调用的包之后再记发现。每一维都要有结论：通过、存在问题，或不适用。不适用要写一句话原因。

### 4.1 先观察

记入报告，不在这里下结论。至少看清：

1. **包与职责**：这些包各自做什么。以包注释、入口和调用关系为准，不靠目录名猜。
2. **写路径**：写从哪里开始，事务在哪里开启和结束，失败时哪些写会一起消失。没有写就写明。
3. **数据访问**：用什么访问数据，同类查询现在怎么写，模型和表怎么对应。以范围内已经存在的写法和能看到的表或迁移为准。
4. **跨进程的写**：有没有调用其他服务或资源，现在怎么收场。
5. **Redis**：有没有 Key，现有 Key 的模式是什么。没有就写明。
6. **显化稿**：有稿时记下稿里的事务切入点、接口和表；没稿时写明不对照。
7. **快照**：`git rev-parse --short HEAD` 与 `git status --short`。报告对应这份快照。

看不到的项写「未观察到」。

### 4.2 和显化稿是否一致

没有关联显化稿：结论写「无显化稿，不对照设计」。

有稿时核对：

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 稿里的写 | 代码里同一次提交的范围和稿的事务切入点一致 | 主路径写丢、写多，或事务起止对不上：严重 |
| 稿里的接口与失败 | 调用方能观察到的结果没有被做窄、做宽或做反 | 主路径：严重；旁路：警告 |
| 稿里的表 | 代码读写的列和稿里的列一致 | 主路径列对不上：严重 |
| 稿声明不适用的部分 | 代码没有自行长出那一块 | 自行扩大了范围：警告；因此会做错主路径：严重 |

稿里标了待确认并采用了假设的，代码按那条假设实现即通过。代码用了另一条假设：严重。

### 4.3 事务

范围内没有写路径：不适用。

有写路径时，按《事务设计规范》对每一处写回答三个问题：

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 要不要开 | 能一句话说清这个事务保护哪条不变量；只读、以及单次已被存储保证原子的写，没有被多余地包进事务 | 说不清保护什么却开了事务，或「先读再判断再写」既没进事务也没下推到存储：严重 |
| 边界 | 失败时必须一起消失的写在同一次提交里；参与写决策的读与写同事务，或判断已下推到存储 | 主路径会留下半成功：严重 |
| 事务里放了什么 | 只有本事务资源上的读写和必要的轻量计算 | 远程调用、缓存、消息、文件、对外响应、等待或事务内重试放在事务里：严重 |
| 传递 | 调用链已在同一事务中则加入并复用，提交点归最外层 | 静默又开一个会独立提交的事务：严重；确需独立提交但没有写明外层回滚不会撤销它：警告 |
| 同生共死的辅助记录 | 必须和业务写一起消失的记录（如幂等凭证）在同一事务里 | 业务写回滚后凭证仍在，或相反：严重 |

工程用什么机制开启事务，就审那个机制。不要求出现某个包名或函数名。

### 4.4 分层与依赖

不检查「是否存在某个目录」。检查行为是否和本工程已经稳定的职责划分一致。

「本工程的做法」要能指出至少两处一致的现有代码，或显化稿里写明的结构。只有一处样本时，不据此判其他代码违规。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 职责 | 协议适配和业务规则分开；谁拥有这个原子动作，事务就在那一侧开启 | 规则和协议搅在一起，导致主路径行为说不清：严重；只是放错了文件、行为仍然正确：警告 |
| 跨进程的写 | 各侧各自完成本侧事务；需要一起进退时有补偿或等价的收场，而不是把另一侧的写塞进本侧事务 | 严重 |
| 依赖方向 | 和已观察到的方向一致 | 下层反过来依赖上层，或基础库依赖了业务代码：严重 |
| 平行实现 | 工程已经依赖的能力，业务路径没有再做一份行为不同的实现 | 两份行为会分叉：警告；分叉已经导致主路径结果不同：严重 |

工程没有分层，或范围内只有一个包：不记「缺少某一层」。工程没有依赖某份基础库：不要求接上它。

### 4.5 数据访问

范围内没有数据访问：不适用。

口径是范围内已经在用的访问方式和能看到的表或迁移。不另定基类、tag 或表前缀。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 同类查询 | 同一种条件的写法一致；外部输入没有被拼进 SQL 文本 | 外部输入被拼进 SQL：严重；同类查询各写各的，读起来会用错条件：警告 |
| 模型与表 | 代码读写的列和能看到的表一致，包括空值与删除语义 | 主路径列对不上：严重；看不到表或迁移：标待确认，不编造应有哪些列 |
| 事务 | 参与当前事务的访问使用调用上下文里的那次事务，不另开一条会独立提交的连接 | 严重 |

### 4.6 Redis Key

范围内没有 Redis Key：不适用。

有 Key 时只核对《Redis设计规范》：冒号分层、小写、字符集、标识稳定、同类数据共用同一模式。

同一类数据用了两套前缀或两套分隔：警告；两套模式已经让读写找不到同一条数据：严重。

### 4.7 表结构

只在本次范围改了表结构，或调用方明确要求看表时检查。只读写已有表、结构不动：不适用。

新表和改列与目标库里已经在用的口径对齐：命名、主键如何生成、审计列、删除如何表达、索引如何命名。看不到存量表时，这些项标待确认，不套一套前缀和字段清单。

和存量表口径冲突，且显化稿没有说明为什么不同：警告；因此主路径读写会错：严重。

### 4.8 注释

只记会让人按错误契约使用代码的注释。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 注释与行为 | 注释里的副作用、空值、是否幂等、默认值与当前代码一致 | 按注释调用会走错：警告；主路径会写错数据：严重 |
| 关键导出 API | 签名读不出的契约，在注释或调用处能看懂 | 主路径调用方无法判断失败和空值：警告 |

自解释的代码没有注释，不记缺失。

### 4.9 正确性

结合本工程实际的调用方式和配置看会不会发生，不按代码形态扣分。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 失败 | 失败被返回或按契约处理，没有被当成成功 | 主路径把错误吞成成功：严重 |
| 崩溃与泄漏 | 空值、并发、退出路径在真实调用下是安全的 | 会 panic、泄漏 goroutine 或打不开的资源：严重 |
| 契约 | 重复提交、不允许的状态、半成功的结果和显化稿或现有接口契约一致 | 主路径：严重 |

到不了的路径不记。拿不准是否到得了：待确认。

## 5. 分级

| 级别 | 何时使用 |
| ---- | -------- |
| 严重 | 按现在的代码走，主路径会写错、提交错、崩溃，或和显化稿的关键决策相反 |
| 警告 | 主路径暂时还能跑，但后续会返工，或特定合理输入下会错 |
| 建议 | 不影响正确性，只影响阅读或局部一致 |

上面各节已经给出常用级别。只有前后语义互斥、事务边界断裂，或调用方能观察到的结果是错的，才把「写得不够整齐」升成严重。

编号为「发现 1」「发现 2」……整份报告连续。顺序为严重、警告、建议。同一根因在多处出现只记一条，位置列全。

## 6. 报告

### 6.1 落盘

报告落在 `_ipc-doc/`。目录不存在时先创建。

| 场景 | 路径 |
| ---- | ---- |
| 关联了显化稿或需求名称 | `_ipc-doc/{YYYYMMDD}_{需求名称}-ipc.md` |
| 未关联 | `_ipc-doc/{YYYYMMDD}_全项目-ipc.md` |

同名报告已存在时，初检直接覆盖。调用方声明本轮是修复后的复审时，不覆盖：沿用原编号，在文末追加一节修复记录。

没有发现时仍写完全文。2.1、2.2、2.3 写「无」。

每条发现都要有位置、现状、影响、依据、建议。缺一项不写入发现列表，改放到待确认。依据写不出规范条款或另一处既有代码时，不得记为发现。

问题、影响、建议用白话写。包名、函数名、配置项照原样出现，只用于定位。

### 6.3 修复与复审

默认只检不修。调用方明确说修复之后才改代码。

- 只改报告里已确认的发现。不做顺手重构，不扩大改动面。
- 顺序：严重、警告，然后是调用方点名的建议。
- 改完后用该工程已经在用的编译和检查命令验证改动包。看不到既定命令时，至少执行 `go build` 和 `go vet`，并在修复记录里写明命令和结果。没有执行过的命令不得写成已通过。
- 复审回写同一份报告，文末追加「修复记录」，已有修复记录则再追加一节，不替换旧节：
  - 逐条状态：已修复、部分处理、按调用方决定不处理、误判撤销
  - 行为变化，以及还没盖住的部分
  - 复审要重新读代码，不沿用上一轮的结论

---

## 7. 约束

- 先写观察，再写发现。未打开的包不写结论。
- 目录名、类型名、组件名不构成问题。问题必须是行为、事务边界或调用方能观察到的契约。
- 每一维都有结论。不适用写原因。
- 每条发现都有位置、现状、影响、依据、建议。依据来自已加载的知识文档、关联显化稿，或本工程里能指出的既有写法。
- 推测标成待确认。待确认不写成已确认问题。
- 同一根因只记一条。
- 未授权不改源码。
- 不引用知识库里已经不存在的文档，也不把《事务设计规范》《Redis设计规范》没有写的条款补进去。

## 8. 完成前自检

落盘前逐项核对。

- [ ] 报告里的范围是实际打开的包，没有用假设的目录名填空
- [ ] 八个维度都有结论；不适用的写了原因
- [ ] 没有把「和示例目录、类型、函数不同」记成发现
- [ ] 事务发现能对应《事务设计规范》里的某一条；没有写路径的维度是不适用
- [ ] Redis 只核了 Key 命名；没有 Key 的维度是不适用
- [ ] 表结构只在有结构变更或调用方要求时才审；看不到存量表的口径标了待确认
- [ ] 每条发现的行号在当前快照里存在；影响在本工程调用方式下到得了
- [ ] 单一样本没有被当成约定
- [ ] 没有显化稿时没有编造对照结论
- [ ] 待确认没有被写成已确认问题
- [ ] 检查阶段没有改源码；若已授权修复，修复记录写了命令和结果
