# 代码巡检

---

## 0. 基础信息

- **Skill 名称**: 代码巡检
- **描述**: 对 **yomi-boot 基础库**或**业务 Go 工程**执行多维代码巡检（分层架构、BFF 编排、数据访问、事务、令牌、注释、Redis、表设计），输出问题清单与 `_ipc-doc` 报告；本母版不含前端规程
- **作者**: zwei
- **创建日期**: 2026-04-16（2026-10-16 合并重写）

## 1. 目标

- **做什么**：对指定 Go 代码范围执行多维度巡检——分层架构（handler / usecase / contract / service / repository）、BFF 编排、数据访问、事务控制、令牌鉴权、事件机制、注释规范、Redis 设计、数据库表设计，输出问题清单或在用户授权下直接修复。
- **为什么**：统一巡检口径，确保分层边界清晰、数据访问规范、事务可控、鉴权安全、缓存和数据库设计合理，减少 Code Review 返工和线上风险。
- **不做什么**：不涉及前端；不做压测与渗透测试；不把 OpenSpec/SDD 文档混入输入。

## 3. 技术方案

### 3.1 巡检流程

```text
开始巡检
  ↓
1. 确认范围与是否允许修复
  ↓
2. 按 §3.2 维度检查（读 §2.2 知识文档）
  ↓
3. 问题分级（§3.9）
  ↓
4. 落盘 _ipc-doc/...-ipc.md（§3.10）
  ↓
5. 若修复：go build / golangci-lint 验证
  ↓
结束巡检
```

### 3.3 分层架构巡检

| 检查项 | 检查内容 | 依据 |
| ------ | -------- | ---- |
| 依赖引用 | 业务单元是否标准 `require gitee.com/hq_project/yomi-boot`（或本地 `go.work` / `replace`）；`gitee.com/hq_project/yomi-boot` 不依赖业务代码 | Go架构规范 §3.5 |
| bootstrap | 各服务 `internal/bootstrap/` 以 `server.go` 为入口；Kafka 消费者用 `*_consumer_plugin.go` + `AddCustomPlugin`；无 `wire/` 子目录 | Go架构规范 §3.4 |
| BFF 目录 | 是否含 `internal/handler/`、`bff/`、`saga/`、`bizerr/`；无领域库访问/领域业务表；本服务库仅基础设施用途 | GoBFF规范 §3.1 |
| 领域目录 | `biz/handler`、`usecase` 平铺；含 `api_types.go` 别名 client DTO；无 token 中间件 | Go业务分层规范 §3.4 |
| 领域零互调 | 领域服务是否无 HTTP 调其他领域 | Go架构规范 §3.1.3 |
| 微服务契约 | 符合 [微服务调用规范](../knowledge/微服务调用规范.md) §3 | 微服务调用规范 |
| 业务幂等 | 写 usecase 使用 `gitee.com/hq_project/yomi-boot/component/common/idempotency.Execute` | 微服务调用规范 §3.4 |
| BFF 喂饱 | 各接口 DTO 按需传参；领域不读 token | GoBFF规范 §3.2.3 |
| handler | 协议适配是否经 `gitee.com/hq_project/yomi-boot/component/common/handler`；领域写用 `dtm.BindAndHandleAction/Compensate` | Go代码规范 §3.3.1 |
| usecase | 平铺命名；Saga 写含 `Compensate`；无跨域 HTTP | Go业务分层规范 §3.4.2 |
| Saga Handler | Action/Compensate 是否独立入口，路由 `/compensate` 成对 | Go事务规范 §3.4.2 |
| gitee.com/hq_project/yomi-boot | 是否无业务依赖；基础设施经 `plugin/` 契约 + `plugin/builtin/{lib}` 生命周期与 YAML 绑定管理；组件库不得反向依赖 boot/plugin；`component/common/event` 为可选组件 | Go架构规范 §3.3、§3.4.4 |
| 令牌 | BFF 经 `infra.TokenService`（gitee.com/hq_project/yomi-boot/component/common/token）注入；config 使用 `token` 段 | GoBFF规范 §3.3 |
| depguard | 分层依赖方向是否符合规范 | Go业务分层规范 §3.8 |

**yomi-boot 根目录额外检查**（巡检本仓各能力库时）：

| 检查项 | 检查内容 |
| ------ | -------- |
| 基础库检查规范 | 逐库对照 [Go基础库检查规范](../knowledge/Go基础库检查规范.md) 的静态检查标准 |

| 同名能力 | 新增能力是否已对照《Go架构规范》§3.3 避免重复包、重复抽象 |

### 3.4 数据访问巡检

| 检查项 | 检查内容 | 依据 |
| ------ | -------- | ---- |
| GORM 查询 | 常规 CRUD 用链式 API；复杂查询用 `Raw` + repository 内 SQL 常量；禁止字符串拼接 SQL | Go数据库规范 §3.2 |
| Model 映射 | 是否使用 `gorm:"column:xxx"` tag 映射列名 + 包级表名常量 + `TableName()` 返回该常量 | Go数据库规范 §3.3 |
| 审计字段 | Model 是否包含 `ID`/`CreateTime`/`CreateBy`/`UpdateTime`/`UpdateBy`/`DeleteTime`/`DeleteBy` | Go数据库规范 §3.3.2 |
| 事务感知 | repository 是否通过 `db.Exec(ctx, r.DB)`（内部 `db.GetTx`）感知事务环境 | Go数据库规范 §3.4 |

### 3.5 事务控制巡检

| 检查项 | 检查内容 | 依据 |
| ------ | -------- | ---- |
| 事务入口 | 事务是否在 usecase 层通过 `db.TxExecutor.Execute`（生产实现基于 `gorm.DB.Transaction`）开启 | Go事务规范 §3.2 |
| 事务边界 | 一个事务是否只包含真正需要原子性的操作 | Go事务规范 §3.3 |
| 事务传递 | repository 是否通过 Context 的 `db.GetTx` 自动感知事务 | Go事务规范 §3.5 |
| 分布式事务 | 跨域写是否由 BFF `saga/` 提交 DTM；领域是否 Execute/Compensate 同文件 | Go事务规范 §3.1、§3.4 |

### 3.6 注释规范巡检

| 检查项 | 检查内容 | 依据 |
| ------ | -------- | ---- |
| 文件头注释 | 每个包是否至少一个文件包含 `// Package xxx ...` 注释 | Go注释规范 §3.2 |
| 类型注释 | 所有导出类型定义是否有注释 | Go注释规范 §3.3 |
| 函数注释 | 所有函数（含非导出）是否有注释，格式是否符合 `// 函数名 描述` | Go注释规范 §3.4 |
| 常量注释 | 同组常量是否有块前注释，不必要的不逐行注释 | Go注释规范 §3.5 |
| 关键步骤 | 方法体内关键业务步骤是否有注释 | Go注释规范 §3.6 |

### 3.7 Redis 设计巡检

| 检查项 | 检查内容 | 依据 |
| ------ | -------- | ---- |
| Key 命名 | 是否遵循 `{项目名}:{模块名}:{业务名}:{标识}` 冒号分层格式 | Redis设计规范 §3.2 |
| TTL 设置 | 是否根据业务特性判断是否需要 TTL，设置的值是否合理 | Redis设计规范 §3.4 |
| 数据结构 | String/Hash/List/Set/ZSet 选择是否匹配业务场景 | Redis设计规范 §3.3 |
| 缓存策略 | 回源、失效、刷新策略是否清晰且一致 | Redis设计规范 §3.4 |
| 分布式锁 | 是否仅在需要跨实例互斥时使用，锁是否设置超时 | Redis设计规范 §3.5 |
| 敏感数据 | 是否避免明文缓存密码、验证码等高敏感信息 | Redis设计规范 §3.7 |

### 3.8 数据库表设计巡检

| 检查项 | 检查内容 | 依据 |
| ------ | -------- | ---- |
| 表命名 | 表名是否使用小写字母和下划线，是否遵循 `t_` 前缀规范 | 数据库表设计规范 §3.1 |
| 主键设计 | 主键是否使用 `bigint`，是否避免自增 | 数据库表设计规范 §3.2.1 |
| 审计字段 | 是否包含 `create_time`/`create_by`/`update_time`/`update_by`/`delete_time`/`delete_by` | 数据库表设计规范 §3.2.2 |
| 字段类型 | 业务枚举、金额、时间字段选型是否合理 | 数据库表设计规范 §3.2.3 |
| 字段注释 | 注释是否完整且与业务语义一致 | 数据库表设计规范 §3.2.4 |
| 索引设计 | 索引命名、数量、组合方式是否合理，是否存在冗余索引 | 数据库表设计规范 §3.3 |

### 3.9 问题分级

| 级别 | 说明 | 示例 |
| ---- | ---- | ---- |
| 🔴 严重 | 可能导致错误行为或架构失控 | Handler 直接操作 DB、事务边界缺失、Token 回检查询库 |
| 🟡 警告 | 影响可维护性和一致性 | 模型混用、SQL 内嵌代码、注释缺失 |
| 🔵 建议 | 可优化项；架构建议（不计入丢星，见 command） | 公共逻辑可提取、注释可补充 |

### 3.10 报告落盘

报告统一落盘到项目根目录 `_ipc-doc/`，命名与应开发文档对齐（类比 audit 的 `_feat-doc/{YYYYMMDD}_{需求名称}/audit.md`）：

| 场景 | 输出路径 |
| ---- | -------- |
| 关联应开发文档 | `_ipc-doc/{YYYYMMDD}_{需求名称}-ipc.md` |
| 未关联应开发文档（如全项目巡检） | `_ipc-doc/{YYYYMMDD}_全项目-ipc.md` |

- 目录不存在时先创建 `_ipc-doc/`；同名报告已存在时直接覆盖，不另起序号
- 报告须含：范围、分包星级（1～5 星，丢星给原因）、问题清单（级别 / 位置 / 依据 / 建议）、综合评估
- 每条问题必须包含文件路径、行号、问题级别、问题描述、依据规范、影响说明和修复建议
- 描述尽量只有白话：问题、影响、修复建议都用大白话讲清楚，不堆缩写、术语和代码片段；包名、函数名、配置项这类标识符照原样写，只用于定位与取证

## 4. 约束与规范

- [ ] 巡检必须以项目 Go 知识文档为唯一规范依据，禁止给出无来源的主观建议
- [ ] 必须遵守 `_prompts/knowledge/Go架构规范.md` §3.11「基础库优先使用（强制）」，将可复用 gitee.com/hq_project/yomi-boot 能力却平行实现或重复依赖的代码列为问题
- [ ] 未经用户允许，不扩大到无关目录或无关模块；默认只检不修
- [ ] 有可执行校验时，修复后必须重新执行编译或 lint 检查
- [ ] 不得把推测写成确认事实，不确定的问题标注为"待确认"；无文件位置、行号或依据的问题不得写入正式报告
- [ ] 涉及分层、事务、令牌等架构级问题时，必须先回看对应规范再定性
- [ ] 报告描述尽量只有白话：先用人话讲清出了什么事、会有什么后果、怎么改；标识符与代码片段只用于定位，不得代替解释
- [ ] 架构建议不计入丢星（与 `check_code` command 一致）

## 5. 验收标准（DoD）

### 5.1 仅检查场景

- [ ] 已明确巡检维度、范围和规范依据
- [ ] 已输出分包星级与问题清单，包含级别、描述、依据和修复建议
- [ ] 问题描述以白话为主，不先读代码也能看懂问题是什么、会造成什么后果
- [ ] 已说明是否存在需要人工判断的边界问题
- [ ] 已落盘 `_ipc-doc/`（文件名遵循 `{YYYYMMDD}_{需求名称}-ipc.md` 或全项目规则）

### 5.2 直接修复场景

- [ ] 已修复项均有对应规范依据
- [ ] `golangci-lint run ./...` 或 `go build ./...` 已重新执行并通过
- [ ] 未引入新的编译错误、分层混乱或无关改动
