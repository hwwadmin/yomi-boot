# 显化审核

---

## 0. 基础信息

- **Skill 名称**: 显化审核
- **描述**: 审需求显化产出的显化稿，抓住业务语义失真和业务偏离。产出一份审核稿，作为进入实现前的门禁。

审核前阅读《需求显化》。显化稿要回答哪些问题、按什么顺序回答、骨架长什么样，以那份 Skill 为准。本 Skill 不另定一套章节，也不把某一门语言、某一个仓库的目录、组件或规范写成对所有稿都成立的检查项。两边措辞不一致时，以《需求显化》为准。

---

## 1. 目标

- **目的**：在实现开始前，抓住显化稿里的业务语义失真和业务偏离。
- **做什么**：对照需求原文和《需求显化》规定的问题，审显化稿有没有写歪、写漏、写矛盾，并给出是否可进入实现的结论。
- **不做什么**：
  - 不改显化稿
  - 不替显化稿补设计。缺了就记发现
  - 不写实现代码，不拆任务，不写验收清单，不记录执行状态、证据或自动验收结果
  - 不制定压测、部署和运维方案
  - 不采集稿中没有的规模、并发和耗时，也不把它们写成已确认事实

---

## 2. 输入

**必需**：一份按《需求显化》写出的显化稿。常见文件名为 `spec.md`。稿里声明的需求原文要能读到：写在稿内，或由调用方附上。原文是产品口径的唯一来源。

另外两项以调用方为准：

- 审核稿的保存路径与文件名。调用方或所执行的 command 已指定时，按指定写入。都未指定时，写到显化稿同目录，文件名为 `audit.md`，并在回复里给出完整路径。
- 是否对照目标系统里的某份约定。调用方明确要求，或显化稿写明「遵循某约定」时，才把该约定当作依据，并在发现里写明条款。约定里没有的内容，不得判违规。未要求对照时，只审稿自身是否把《需求显化》要求的问题答完、答对、前后一致。

缺原文时向调用方索取。拿到之前，「语义忠实」记为「无法对照原文」，其余维度照审，不因缺原文而停笔。

信息不足时：记入发现或剩余风险。不替稿补设计，不把未观察到的规模、并发、耗时写成事实。

---

## 3. 工作立场

对抗着读。默认稿里每一句都可能把产品原意写窄、写宽或写反。发现用白话写，让没看过实现的人能判断要不要改稿。

先在全文里找答案，再看答案落在哪一章。某章声明不适用且理由成立，该章通过。章节在、内容是占位或空模板，按该问题未回答处理。

专门找这几类洞：

- 和原文冲突，或原文有的能力在稿里消失，原文没有的能力被加进范围
- 漏掉的状态、重复提交、半成功
- 流程图上的写，和事务切入点对不上
- 接口列表和流程图对不上
- 把推测写成事实

`⚠️ 待确认` 本身不是问题。《需求显化》要求信息不足时采用一条假设继续写完。已写出备选、采用假设，并且后文用的是这条假设，就视为闭环。只有标记、没有采用假设，或后文用了另一条，才记发现。

---

## 4. 审核顺序

通读原文和全文后再记发现。先审语义，再按《需求显化》的问题顺序往下审，最后看前后是否对得上。

### 4.1 语义是否失真

对照原文，逐条看功能点和限制有没有被写歪。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 原文里的每个功能点 | 在范围内，或写进非目标，或标了待确认并采用了假设 | 范围内的能力消失：严重 |
| 稿里多出来的能力 | 能指出原文哪一句支持 | 指不出：严重 |
| 原文里的限制 | 状态、不能做的事、失败时怎样，没有被放宽 | 放宽且未标出：严重 |
| 数字、并发、耗时 | 只写原文或目标系统里已经出现的；其余是待确认加采用假设 | 未观察到的写成已确认事实，且会改变主路径：严重；只是多写了一句量级：警告 |

缺原文时本维写「无法对照原文」，不编造对照结论。

### 4.2 骨架与元信息

显化稿骨架是第 0 章到第 13 章，章节不跳号。不适用的章节保留标题，并用一句话说明原因。

头部要有：生成时间、原始需求来源、优先级、目标版本、影响范围、关联表、关联接口。未知的项写待确认。文档编号仅在调用方要求时才需要。

答案已在全文出现，只是章节号或章节名与骨架不一致：记建议，并指出应归入哪一章。问题在全文任何位置都找不到：按该问题在下面各节给出的级别记缺失。

### 4.3 待确认是否闭环

待确认章集中在显化稿第 3 章。原文无歧义时，该章写「无」。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 每条待确认 | 有备选，有本次采用的假设 | 警告 |
| 后文 | 使用的是采用的那条假设 | 用了另一条：严重 |
| 边界、状态、失败、相关数据是否立刻一致 | 还不能据此做设计的点已进入待确认，或原文已经无歧义 | 主路径仍靠猜：严重 |

### 4.4 背景、目标、范围、非目标

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 背景 | 写了为何现在要做、现状哪里不够 | 警告 |
| 目标 | 是业务上可以确认的结果 | 只写了实现动作、看不出业务结果：警告 |
| 范围 | 本次要交付的能力具体 | 严重 |
| 非目标 | 相关但本次明确不做的事具体 | 缺失，或只有「不做无关改动」：警告 |
| 头部影响范围 | 与范围、关联表、关联接口一致 | 不一致：警告；因此会做错范围：严重 |

### 4.5 规则、场景、异常

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 规则 | 不依赖界面文案也能复述 | 警告 |
| 场景 | 有触发条件、处理过程、期望结果，并能对上后文的接口和流程图 | 主场景对不上：严重；次要场景对不上：警告 |
| 状态 | 会改变状态的动作写了哪些状态下允许做 | 原文有状态而被漏掉：严重；原文未写：警告 |
| 预期失败 | 每条有触发条件，以及一个稳定的失败身份。人读的句子可以变，身份不变 | 主路径失败无法据此分支：严重；其余：警告 |
| 技术故障 | 收成一个统一的失败身份，内部细节没有写成对外契约 | 警告 |

### 4.6 表设计

先看这次有没有表变动。新建表、改列、改约束、改索引，都算变动。只读写已有表、结构不动，不算。

**稿声明无变动时**：正文只有「本需求不涉及表变动」这一类说明。出现候选表、DDL 或查询–索引对照：警告。这些内容把范围外的表写进了交付：严重。

**稿声明有变动时**：

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 收入的表 | 只含结构有变化的表，并标明新建或改已有表 | 把结构不动的表写进来：警告 |
| 新建表 | 有 `CREATE TABLE`（或目标系统存量表已在用的方言） | 严重 |
| 改已有表 | 有 `ALTER` 或等价变更语句，并有变更清单 | 严重 |
| 表意图 | 每张变动的表写了存什么、服务哪个场景、和哪些表关联、唯一性和删除各表达什么 | 严重 |
| 列 | 含义、是否可空、默认值、唯一性清楚；表间关联落在哪一列，删除或更新时如何处理 | 主路径列说不清：严重；其余：警告 |
| 冗余 | 能由其他列算出的事实不重复存；冗余写明由谁在何时维护 | 警告 |
| 查询–索引对照 | 变动的表本次会被查询时有对照；没有查询则不写这张表 | 有查询却没有对照：警告 |
| 索引 | 索引用来服务对照里的过滤、排序、分页；唯一性用唯一索引表达 | 对不上：警告 |
| 存量表口径 | 主键、审计列、删除语义、表名和索引名与稿中声称观察到的存量表一致；看不到的已标待确认 | 写成了未观察到的口径且未标待确认：警告 |
| 并发约定 | 只有明显需要的查询或写入才写「可并发 / 须串行 / 流程级互斥 / 待确认」之一 | 把未观察到的数据量或并发写成事实：按 4.1 |

条件不清却没有待确认和采用假设：警告。

### 4.7 领域

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 归属 | 写明归入哪个已有领域，或为何新建 | 归属缺失，规则不知道由谁负责：严重 |
| 归入已有领域 | 写了为什么是它、要不要扩大职责、容易混淆的领域为什么不是 | 警告 |
| 新建领域 | 有名称、职责、包含、不包含、依赖 | 缺「不包含」：警告；职责和范围对不上：严重 |
| 依赖 | 单向，不成环 | 成环：严重 |
| 拿不准 | 标了待确认，并写下本次采用的归属 | 未采用就往下设计：严重 |

### 4.8 Model、领域出入参、接口出入参

三样分开写。某一跳两边字段一致时，写明「与上一层相同」，仍然分节列出。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 表无变动 | 写明不新增 Model | 无变动却新造一套 Model：警告 |
| 表有变动 | 每个变动表的 Model 只含该表的列，字段对应 表设计 里的列 | 对不上：严重 |
| 领域出入参 | 本次每个领域动作都有入参和出参；业务校验失败用第 5 章的失败身份 | 主路径动作缺失：严重 |
| 查询条件 | 若表设计写了查询–索引对照，领域入参里的查询条件与之同一组字段 | 警告 |
| 接口出入参 | 接口列表中的每个接口一组；接口名与列表一致；写明对应哪一项领域出入参 | 主路径对不上：严重；其余：警告 |
| 校验落点 | 格式和必填在接口入参；状态、唯一性等业务校验在领域入参 | 两层搅在一起导致规则说不清：警告 |
| 缓存 | 只有需求关心「读到的是不是最新」时才写，并写明以表里的行为准，还是以缓存为准 | 写成事实但需求未涉及：警告 |

Model 含接口协议字段，或只在某次调用里出现的过滤条件：警告。

### 4.9 接口列表

覆盖本次新增、修改，以及沿用并被这次流程调用到的接口。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 每条接口 | 有名称、作用、uri、变更（新增 / 修改 / 沿用）、是否幂等 | 主路径缺名称或变更：严重；缺 uri 或是否幂等：警告 |
| uri | 用目标系统已有的名字；还没有则待确认 | 编造了未观察到的 uri 且未标待确认：警告 |
| 是否幂等 | 重复调用和调用一次的业务结果相同则填「是」 | 会改变已有状态，但「是否幂等」和场景里都读不出重复做的结果：严重 |
| 失败与字段 | 预期失败指向关键异常；入参出参指向 4.8，不把字段表塞进接口列表充数 | 建议 |

只改已有行为、不新增接口时，列出被波及的已有接口。一个都不列：警告。

### 4.10 业务流程

每个主场景有一张大致流程图，用 mermaid `flowchart`。节点是业务动作，并标上接口列表里的接口名。一条主路径加上关键分支：成功、规则里已经出现的失败、重复做会怎样。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 主场景 | 每张图注明对应哪个场景 | 主场景没有图：严重 |
| 接口 | 图中的接口都能在接口列表里找到；列表里被这次流程调用的接口能在某张图里找到 | 主路径对不上：严重；旁路对不上：警告 |
| 写表 | 写表的那一段标出事务从哪一个节点开始、到哪一个节点结束 | 严重 |
| 事务外 | 远程调用、缓存、通知、把结果返回调用方，画在写表那段之外 | 画进了写表段，且和事务切入点矛盾：严重 |

不要求图展开到每一层内部的对象转换，也不要求另附逐步调用表。没有这些，不记缺失。

### 4.11 事务切入点

没有写表时，本章写「本需求无事务切入点」。图上仍有写表：严重。

有写表时，每张含写表动作的流程图有一行：

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 切入点 | 写明哪个接口的哪一步 | 严重 |
| 同一次提交 | 写明哪些表、写入什么 | 严重 |
| 多处写表 | 写清是从同一个切入点开启一次提交，还是每处各自提交 | 读不出来：严重 |
| 事务外 | 远程调用、缓存、通知、返回放在事务外 | 和流程图矛盾：严重 |
| 半成功 | 写明调用方看到什么；没有半成功则写「同一次提交」 | 存在事务外动作或多次提交，却没写调用方看到什么：严重 |

本步只审切入点和提交范围。稿里没有闭包内部的逐步调用、补偿地址或幂等组件的名字，不记缺失。《需求显化》要求这些不写进显化稿。

### 4.12 风险、依赖与摘要

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 第 12 章 | 写了可能让实现走偏的风险、依赖的外部条件、仍未关闭的问题 | 主路径风险在前文出现、这里完全没提：警告 |
| 第 13 章 | 四行可以独立阅读：变更目标、主要影响面、必须守住的约束、适合继续拆开的方向。拆开的方向选一种并说明为何这样切 | 缺行或与正文矛盾：警告 |
| 稿内禁区 | 没有任务、验收、证据、执行状态、自动验收命令 | 出现这些：警告，要求从显化稿删去 |

### 4.13 前后是否对得上

分章都过了，仍可能彼此矛盾。逐对核对：

| 左边 | 右边 | 对不上时 |
| ---- | ---- | -------- |
| 规则 | 场景 | 主路径：严重；其余：警告 |
| 场景里的失败 | 关键异常的失败身份 | 同上 |
| 表的列 | Model 字段 | 严重 |
| 查询–索引对照 | 领域入参的查询条件 | 警告 |
| 领域出入参 | 接口出入参 | 主路径：严重 |
| 接口列表 | 流程图 | 主路径：严重 |
| 流程图上的事务起止 | 事务切入点 | 严重 |
| 待确认的采用假设 | 后文设计 | 严重 |
| 第 13 章四行 | 正文 | 警告 |

同一字段、同一状态、同一失败在两处含义不同：严重。

### 4.14 分级与编号

| 级别 | 何时使用 |
| ---- | -------- |
| 严重 | 按这份稿做，业务语义会做错，或关键决策缺失，实现者只能各自补假设 |
| 警告 | 主路径还能读懂，但后续会返工或理解分叉 |
| 建议 | 不影响语义，只影响表达或章节归位 |

上面各节已经给出常用级别。只有前后语义互斥、关键流程断裂，或输入输出约束不完整时，才把「写得不够细」升成严重。只是可以再补一句的，保持建议。

编号为「发现 1」「发现 2」……整份审核稿连续、不跨级别复用。顺序为严重、警告、建议。同一级别内按发现顺序编号。

### 4.15 什么不算问题

定级前先排除下面这些。它们不进入发现列表。

| 情形 | 怎么处理 |
| ---- | -------- |
| 类型名、注册方式、定时表达式、框架写法 | 不影响业务语义、职责边界或关键输入输出时，不记 |
| 某个现存实现刚好是另一种写法 | 单一样本不是约定。调用方未要求对照约定时，不据此判违规 |
| 稿没写某个实现口径 | 不等于矛盾。写成「口径待明确」只在它挡住主路径时升为发现 |
| 已闭环的待确认 | 不因为带着 `⚠️ 待确认` 就升格 |
| 调用方未要求对照现有代码 | 不把「代码和稿不一致」当作主结论 |
| 稿没有压测数字、补偿组件名、闭包内部步骤 | 不记缺失 |
| 未做执行计划 | 显化阶段不审真实执行计划 |

## 5. 审核稿

### 5.1 唯一产物

只写一份审核稿。不改显化稿，不另写任务清单或验收清单。

调用方声明本轮是复审时：沿用上一份审核稿的编号；已改掉的发现保留编号，标明已修复和修复位置；仍在的和新增的按原级别排在未关闭的发现里。

### 5.2 文档骨架

```markdown
# 显化审核：{需求名称}

| 字段 | 值 |
| ---- | -- |
| 审核对象 | {显化稿路径} |
| 审核时间 | {日期时间} |
| 原始需求来源 | {稿中所引；没有则写无法对照原文} |
| 审核方式 | {首轮 / 复审} |

## 0. 审核总评

{1–2 段：稿有没有守住原文语义，主要风险，能否进入实现}

| 维度 | 结论 | 说明 |
| ---- | ---- | ---- |
| 语义忠实 | {通过 / 存在问题 / 无法对照原文} | |
| 骨架与待确认 | {通过 / 存在问题} | |
```
