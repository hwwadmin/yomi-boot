# spec落地执行

审核允许进入实现之后，按显化稿拆成任务，在目标系统里把设计落地，并留下可追踪的任务记录。

执行前阅读《需求显化》（`.cursor/skills/create-spec/SKILL.md`）和《显化审核》（`.cursor/skills/audit-spec/SKILL.md`）。调用方点名、或显化稿写明遵循的其他约定，在任务里写明条款后采用。

基于第一性原理和对抗性审查，用白话写。信息不足标待确认，不臆造、不直接假定。

---

## 1. 产出

- 一份任务清单
- 目标系统里与清单对应的实现和验证

调用方指定了路径就用该路径。未指定时：

- 显化稿：`_feat-doc/{YYYYMMDD}_{需求名称}/spec.md`
- 审核稿：与显化稿同目录 `audit.md`
- 任务清单：`_task-doc/{需求名称}/tasks.md`

目录不存在则先创建，并在回复里给出路径。改动范围以调用方指定的仓库、模块或目录为准；未指定时，改显化稿「影响范围」对应的代码。

---

## 2. 输入

**必需**：

- 按《需求显化》写出的显化稿（常见 `spec.md`）
- 对应审核稿（常见 `audit.md`）。开工条件：没有未关闭的严重问题，且结论写明可以进入实现

没有审核稿，或结论仍是不可进入实现：指出缺什么或未关闭的严重问题在哪，停在这里。

目标系统里看不到同类写法、事务入口、失败出口或验证方式时，标 `⚠️ 待确认`，不臆造、不直接假定。列出候选后，标明本次采用的一条（取最贴近现有写法的）再继续。需要尚不存在的基础设施时，先说明缺口和候选，得到确认再写。

---

## 3. 守住什么

先看显化稿要守住什么，再看目标系统已经怎么做。分层、命名、事务入口、失败出口、测试位置，沿用已经在用的形式。某一个现存实现换了种写法，不足以成为新规范。

- 范围以稿为准，非目标里的事放在「本次不动」
- 流程图上的写与事务切入点是同一段
- 接口的名称、uri、出入参、失败身份、是否幂等与稿一致
- 只动稿里写了变动的表
- 一个任务做完并写下证据，再做下一个

实现和稿冲突时停手，把矛盾写进该任务的证据。

---

## 4. 工作流程

### 4.1 确认可以开工

读审核稿结论。允许进入实现后，通读显化稿，至少抓住：范围与非目标、规则与异常、表变动、领域、出入参、接口、流程图、事务切入点、第 13 章摘要。待确认项沿用稿里已经采用的假设。

### 4.2 观察目标系统

拆任务和写代码之前，看这次会改到的地方已经存在的：

- 代码按什么职责分开，新代码应落在哪一种已有位置
- 事务从哪里开启，同一次提交怎样传下去
- 失败身份怎样变成调用方看到的结果
- 验证放在哪，用什么方式能跑这一处
- 已有能力能不能直接用

观察不到的项进入对应任务的待确认。

### 4.3 拆任务

任务从显化稿的范围里拆。一个任务是一次可以独立验证的改动。

- 写清依赖、输入，以及完成时能看到什么
- 分组沿用显化稿第 13 章「适合继续拆开的方向」；该章没写清时，按领域、接口或场景选一种，在清单开头说明
- 表结构、领域规则、接口、事务边界都能指回稿里的章节

清单骨架见第 5 节。任务状态和证据只写在这份清单里。

### 4.4 按任务实现

一次只做一个任务，按依赖顺序做：

1. 先写会失败的验证，覆盖这个任务对应的规则、失败身份或事务边界。位置和写法沿用目标系统已经在用的。
2. 再写让验证通过的实现，只服务这个任务。
3. 用目标系统已经在用的构建和验证方式跑这一处；观察不到统一入口时，跑与该任务直接相关的验证，在证据里写明用了什么、结果是什么。
4. 通过后把状态改为已完成。证据写清：改了哪些位置、跑了什么、结果。

验证要先失败，再因实现而通过。这一处确实没有验证入口、且调用方同意不做验证时，状态写「已完成（无验证）」，证据写明原因。没跑过的，证据里如实写未跑。

**事务**。写路径以显化稿第 11 章的切入点为准：说得清保护哪条不变量；同一次提交里的表写入与稿一致；稿写在事务外的远程调用、缓存、通知、返回放在事务外；已处于同一次提交中则加入并复用。稿写「本需求无事务切入点」时沿用这一结论。实现时才发现「先读再判断再写」、而稿没有对应切入点：停在该任务。

**幂等**。接口列表里「是否幂等」为「是」的，重复调用和调用一次的业务结果相同。做法沿用目标系统已有的幂等写法。必须和业务写同生共死的凭证，放进同一次提交。没有现成写法时，在该任务里写明本次如何保证，并先向调用方确认。

**失败**。预期失败使用显化稿里的失败身份，出口形式沿用目标系统已经在用的写法。稿和现有系统都没有出口时，标待确认。

**表**。落实稿里写了变动的表。方言、主键、审计列、命名沿用稿中已经对齐的口径。

**接口**。名称、uri、出入参、是否幂等与稿一致。格式和必填在入口校验；状态、唯一性等业务校验留在领域动作里。

**已有能力**。目标系统或它已经依赖的公共能力里，有能满足本任务的，先读实现，满足则使用。需要新的公共能力时，写出缺口、候选和影响，等调用方确认。公共库里放可复用能力；业务规则留在拥有该领域的系统里。

**Redis Key**。本次要新增或修改 Key 时，写法为 `{命名空间}:{用途}:{对象}:{标识}`：冒号分层、小写、标识稳定、同类同一模式。

### 4.5 收束

全部任务已完成，或明确标出未做及原因。范围、规则、表、接口或事务切入点在实现中发现稿写错了：停手，在任务证据里说明矛盾。先改显化稿，再走审核，然后继续实现。

---

## 5. 任务清单

调用方声明在已有清单上继续时：沿用原有任务编号；已完成的保留证据；新增任务接在后面。

```markdown
# 落地任务：{需求名称}

| 字段 | 值 |
| ---- | -- |
| 显化稿 | {路径} |
| 审核稿 | {路径} |
| 生成时间 | {日期} |
| 目标系统 | {本次改动所在的系统；调用方未指定则写观察到的位置} |
| 拆分方式 | {按领域 / 按接口 / 按场景，及原因} |

## 0. 本次不动

{非目标，以及周边存在但这次不改的部分}

## 1. 任务

### {分组名}

#### 任务 {n}：{标题}

- **对应**：{显化稿章节，或接口 / 表 / 场景}
- **依赖**：{无，或任务编号}
- **做什么**：{一句话}
- **输入**：{依赖的稿、表、接口或已有代码}
- **完成时**：{怎样算做完}
- **状态**：未开始
- **证据**：—
```

状态：未开始、进行中、已完成、阻塞。已完成但调用方同意不做验证的，写「已完成（无验证）」。阻塞在证据里写明停在什么矛盾上。

---

## 6. 落盘前自检

- [ ] 审核稿没有未关闭的严重问题，且结论是可以进入实现
- [ ] 任务清单与显化稿的范围一致，非目标写在「本次不动」
- [ ] 分组方式与第 13 章的拆分方向一致，或已说明另选一种的原因
- [ ] 每个已完成任务都有证据：改动位置、验证方式、结果
- [ ] 没跑过的验证在证据里如实写未跑
- [ ] 写路径的事务切入点、同一次提交的表、事务外动作与显化稿一致
- [ ] 接口的失败身份、出入参、是否幂等与显化稿一致
- [ ] 表结构只动了稿里写明变动的表
- [ ] 新代码落在目标系统已有的职责划分里
- [ ] 已有能力被复用；新的公共能力经过调用方确认
