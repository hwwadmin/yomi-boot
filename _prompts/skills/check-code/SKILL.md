# 代码巡检

检查指定代码模块：先取证，再对照，再分级。先看这个模块实际怎么组织、怎么写、怎么开事务，再按本文各维对照。依据是模块自己的对外契约、范围内能指出的既有写法，以及本文的检查项。

基于第一性原理和对抗性审查，用白话写问题、影响与改法。信息不足标待确认，不臆造、不直接假定。

---

## 1. 产出

一份巡检报告。路径 `_ipc-doc/{YYYYMMDD}_{模块名}-ipc.md`。模块名取指定路径的最后一段；一次指定多个顶层包时用共同父目录名；都没有时用仓库目录名。目录不存在时先创建。

默认只检不修。调用方授权后再改代码，复审回写同一份报告。

---

## 2. 输入

**必需**：要检查的模块（目录、包或文件）。一份报告对应一次指定的范围；多个互不包含的模块分别出报告。

未给范围时，列出仓库里能看到的可部署单元和入口，写明本次实际打开了哪些包。未打开的包不下结论。范围内未排除的文件都读到。

另外两项以调用方为准：

- 检查重点。未说明时按本文全部维度走；范围内看不到的维度标「不适用」
- 是否允许修复。未说明时只检不修

调用方点名、或代码写明遵循的其他约定，在发现里写明条款后引用。历史报告、生成代码、第三方 vendored 代码只作影响说明的证据。

---

## 3. 怎么判断

先记下能指出来的事实，再判断。可疑行为用命令或临时探针确认。信息不足标待确认，不臆造、不直接假定。

发现必须同时满足：当前快照里有位置；在本工程真实调用下到得了；依据来自本文对应检查项、本模块对外契约，或至少两处既有写法。

形态、命名、示例目录不同，只用于定位。语言和框架的具体写法沿用本工程已经在用的；本文只审行为。覆盖率、文件数只记规模。自解释代码没有注释，单独不构成发现。拿不准是否到得了的路径标待确认。

检查阶段与修复阶段分开。

---

## 4. 检查顺序

```text
确认范围 → 记录快照与规模 → 观察事实 → 可执行验证 → 按维度对照 → 分级与自检 → 落盘
（授权后）修复 → 重新验证 → 复审回写
```

每一维都有结论：通过、存在问题，或不适用（写一句话原因）。「未发现问题」也是结论。

### 4.1 确认单元与快照

1. **检查单元**：指定范围及其直属子包，写清包含与排除。
2. **快照**：`git rev-parse --short HEAD` 与 `git status --short`。
3. **规模**：包数、源文件数、测试文件数、非测试行数。能用仓库已有命令统计就用，并写明统计方式。

### 4.2 先观察

记入报告，此处不下结论：

1. **模块与职责**：以模块说明、入口和调用关系为准。
2. **对外契约**：公开了什么、注释和测试固定了什么、范围内谁在调用。能列出公开入口时列出，标出疑似内部实现泄漏。
3. **配置**：运行时配置、文件绑定、默认值、开关；`0` / 空值表示「不限制」还是「未设置」。
4. **依赖**：这个模块依赖谁、谁依赖它。
5. **写路径**：写从哪里开始，事务在哪里开启和结束，失败时哪些写会一起消失。
6. **数据访问**：用什么访问数据，同类查询怎么写，模型和表怎么对应。
7. **跨进程的写**：有没有调用其他服务或资源，现在怎么收场。
8. **生命周期**：初始化、启动、关闭、后台任务。
9. **Redis**：有没有 Key，现有 Key 的模式是什么。
10. **测试**：固定了哪些正常、边界和失败路径；是否依赖外部服务。

看不到的项写「未观察到」。探针放在 `.tmp/{模块名}-review/`，用完清理。

### 4.3 可执行验证

优先用该工程已经在用的编译和检查命令；否则对范围内的包做编译和静态检查，有测试则跑测试。命令与结果写入「实测记录」。

| 目的 | 做什么 |
| ---- | ------ |
| 编译 | 范围内能编译 |
| 静态检查 | 该工程已经在用的静态检查 |
| 测试 | 相关测试；依赖外部服务时收窄到可安全运行的用例 |
| 竞态 | 有共享状态或自行启动的后台任务时加竞态检查；工具链做不到时写明原因，改用探针加人工审查 |
| 公开面 | 列出公开入口 |
| 依赖方向 | 列出依赖 |
| 格式 | 只检查 |

执行过的命令才写结果。探针只用被测范围内的公开入口。规模数字与统计一致。

### 4.4 对外契约与设计

口径：公开签名、注释约定、测试所固定的结果、范围内能看到的调用方。没有测试或调用方时，审代码自身是否自相矛盾。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 公开行为 | 同名公开入口在各调用下行为一致 | 行为分叉：警告；主路径结果已经不同：严重 |
| 失败与空值 | 调用方能从签名、注释或返回值看出失败和空值 | 主路径无法判断：警告 |
| 已公开的范围 | 已经公开的行为保持完整 | 主路径被做窄或做反：严重；旁路：警告 |
| 公开面 | 只公开调用方需要的类型和函数 | 仅内部使用的辅助类型被公开：警告；因此破坏不变量：严重 |
| 实现泄漏 | 公开入口把内部存储、连接或可变状态留在模块内 | 调用方能改内部状态：严重 |
| 返回值所有权 | 返回的可变数据与内部状态分离，或文档写明所有权 | 调用方一改就破坏内部状态：严重 |
| 初始化 | 未经初始化就能安全使用，或必须经指定入口完成必要初始化 | 未初始化就使用会崩溃或静默写坏：严重 |
| 错误契约 | 非法入参以失败返回；崩溃只出现在文档写明的快速失败边界 | 对外路径上崩溃，或把错误吞成成功：严重 |
| 抽象 | 每层都有独立职责 | 只转发、无替换价值的包装：建议；因此让主路径行为说不清：警告 |

### 4.5 正确性

结合本工程实际的调用方式和配置看会不会发生。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 失败 | 失败被返回或按契约处理 | 主路径把错误吞成成功：严重 |
| 空值 | 空值（nil / null）、空集合、未初始化的容器在缺省状态下安全 | 会崩溃或写坏：严重 |
| 边界 | 空输入、单元素、最大长度、负数、溢出、递归终止是安全的 | 主路径：严重；特定合理输入：警告 |
| 资源 | 文件、连接、后台任务、定时器、订阅在退出路径上能释放；关闭幂等、尊重取消 | 泄漏或关不掉：严重 |
| 并发 | 共享状态有保护；锁的范围内是本地临界区 | 竞态、死锁：严重 |
| 取消 | 请求路径尊重调用方截止时间；取消信号留在这次请求里 | 取消后仍占用资源或继续写：严重 |
| 崩溃 | 模块自行启动的后台任务失败能被看见 | 严重 |
| 契约 | 重复提交、不允许的状态、半成功的结果和本模块已经公开的行为一致 | 主路径：严重 |

模块承担启动、关闭或后台任务时，额外看：关闭是否幂等、是否先停任务再放资源、失败时是否清理本次已申请的资源。没有这类生命周期：本项不适用。

### 4.6 事务

范围内没有写路径：不适用。有写路径时，对每一处写回答三个问题：要不要开、边界画在哪、事务内放什么。工程用什么机制开启事务，就审那个机制。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 要不要开 | 能一句话说清这个事务保护哪条不变量；只读、以及单次已被存储保证原子的写保持原样 | 说不清保护什么却开了事务，或「先读再判断再写」既没进事务也没下推到存储：严重 |
| 边界 | 失败时必须一起消失的写在同一次提交里；参与写决策的读与写同事务，或判断已下推到存储 | 主路径会留下半成功：严重 |
| 事务里放了什么 | 只有本事务资源上的读写和必要的轻量计算 | 远程调用、缓存、消息、文件、对外响应、等待或事务内重试放在事务里：严重 |
| 传递 | 调用链已在同一事务中则加入并复用，提交点归最外层 | 静默又开一个会独立提交的事务：严重；确需独立提交但没有写明外层回滚不会撤销它：警告 |
| 同生共死的辅助记录 | 必须和业务写一起消失的记录（如幂等凭证）在同一事务里 | 业务写回滚后凭证仍在，或相反：严重 |

### 4.7 分层、依赖与封装

检查行为是否和本工程已经稳定的职责划分一致。「本工程的做法」要能指出至少两处一致的现有代码。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 职责 | 协议适配和业务规则分开；谁拥有这个原子动作，事务就在那一侧开启 | 规则和协议搅在一起，导致主路径行为说不清：严重；只是放错了文件、行为仍然正确：警告 |
| 跨进程的写 | 各侧各自完成本侧事务；需要一起进退时有补偿或等价的收场 | 把另一侧的写塞进本侧事务：严重 |
| 依赖方向 | 和已观察到的方向一致 | 下层反过来依赖上层：严重 |
| 平行实现 | 工程已经依赖的能力被复用 | 两份行为会分叉：警告；分叉已经导致主路径结果不同：严重 |
| 配置从哪来 | 模块通过参数或配置对象接收设置 | 内部偷读配置导致调用方无法注入：警告；因此主路径用错配置：严重 |
| 全局状态 | 可变的模块级状态有明确的并发与测试隔离办法 | 测试无法隔离或并发无保护：严重 |

范围内只有一个包：职责维写清这个包做什么即可。

### 4.8 数据访问

范围内没有数据访问：不适用。口径是范围内已经在用的访问方式和能看到的表或迁移。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 同类查询 | 同一种条件的写法一致；外部输入作为参数传递 | 外部输入被拼进 SQL：严重；同类查询各写各的，读起来会用错条件：警告 |
| 模型与表 | 代码读写的列和能看到的表一致，包括空值与删除语义 | 主路径列对不上：严重；看不到表或迁移：标待确认 |
| 事务 | 参与当前事务的访问使用调用上下文里的那次事务 | 另开一条会独立提交的连接：严重 |

### 4.9 Redis Key

范围内没有 Redis Key：不适用。有 Key 时核对：`{命名空间}:{用途}:{对象}:{标识}`，冒号分层、小写、字符集为字母数字下划线冒号、标识稳定、同类数据共用同一模式。

同一类数据用了两套前缀或两套分隔：警告；两套模式已经让读写找不到同一条数据：严重。

### 4.10 表结构

本次范围改了表结构，或调用方明确要求看表时检查。只读写已有表、结构不动：不适用。

新表和改列与目标库里已经在用的口径对齐：命名、主键如何生成、审计列、删除如何表达、索引如何命名。看不到存量表时这些项标待确认。

和存量表口径冲突：警告；因此主路径读写会错：严重。

### 4.11 编码与可维护性

对照本模块已经稳定的写法。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 错误传播 | 错误保留成因，外层能取到内层原因，和本模块已有包装方式一致 | 丢掉原因导致调用方无法判断：警告；因此主路径把失败当成成功：严重 |
| 释放 | 解锁、关闭和失败后的收尾用能保证执行的方式 | 锁或资源在失败路径上泄漏：严重 |
| 死代码 | 公开入口、配置项和主路径分支都有调用方 | 无调用方的公开入口仍被当成契约：警告 |
| 日志与输出 | 走本工程已有的日志入口；秘密留在模块内 | 打出秘密：严重；本工程另有日志入口却直接打印：建议 |
| 同类命名 | 同一概念在本模块内同名同义 | 读起来会用错：警告 |
| 重复 | 三处以上相同逻辑才考虑抽取 | 重复已经导致行为分叉：警告 |
| 校验重复 | 同一规则在边界和内部的结论一致 | 两层结论相反：严重 |

### 4.12 注释

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 注释与行为 | 注释里的副作用、空值、是否幂等、默认值与当前代码一致 | 按注释调用会走错：警告；主路径会写错数据：严重 |
| 关键公开入口 | 签名读不出的契约，在注释或调用处能看懂 | 主路径调用方无法判断失败和空值：警告 |

### 4.13 优化

说明在什么调用下才有收益。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 热点浪费 | 可指出的热点路径上没有明显可避免的重复分配、重复解析或锁内 I/O | 建议；已导致主路径超时或打满：警告 |
| 复杂度 | 现有结构与当前负载相称 | 为未出现的负载增加结构：建议 |

## 5. 分级

| 级别 | 何时使用 |
| ---- | -------- |
| 严重 | 按现在的代码走，主路径会写错、提交错、崩溃、泄漏，或和本模块已经公开的契约相反 |
| 警告 | 主路径暂时还能跑，但后续会返工，或特定合理输入下会错 |
| 建议 | 不影响正确性，只影响阅读、局部一致或可测量的局部浪费 |

按后果判级。编号为「发现 1」「发现 2」……整份连续。顺序为严重、警告、建议。同一根因只记一条，位置列全。

### 6.1 修复与复审

只改报告里已确认的发现。顺序：严重、警告，然后是调用方点名的建议。同一文件的问题合并修改。

改完后用该工程已经在用的编译和检查命令验证。否则至少做编译和静态检查，有测试则跑相关测试；改了并发路径则加竞态检查。

复审追加「修复记录」：逐条状态（已修复 / 部分处理 / 按调用方决定不处理 / 误判撤销）、行为变化、还没盖住的部分。重新读代码后再下结论。

## 7. 落盘前自检

- [ ] 范围是实际打开的包，包含/排除写清
- [ ] 十个维度都有结论；不适用的写了原因
