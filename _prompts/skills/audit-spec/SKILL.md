# 显化审核

对照需求原文和《需求显化》要回答的问题，审显化稿有没有写歪、写漏、写矛盾，给出能否进入实现的结论。

审核前阅读《需求显化》（`.cursor/skills/create-spec/SKILL.md`）。问题、顺序和骨架以那份为准。

基于第一性原理和对抗性审查，用白话写。信息不足标待确认，不臆造、不直接假定。

---

## 1. 产出

一份审核稿。调用方指定了路径就用该路径；给出了显化稿路径则写到该稿同目录 `audit.md`；都未指定时写入 `_feat-doc/{YYYYMMDD}_{需求名称}/audit.md`。目录不存在则先创建，并在回复里给出路径。发现记在审核稿里。

---

## 2. 输入

**必需**：按《需求显化》写出的显化稿（常见 `spec.md`）。稿里声明的需求原文要能读到。原文是产品口径的唯一来源。

缺原文时向调用方索取。「语义忠实」记为「无法对照原文」，其余维度照审。信息不足标待确认，不臆造、不直接假定；未观察到的规模、并发、耗时不得写成已确认事实。

调用方要求对照某份约定、或稿写明遵循某约定时，把该约定当作依据，并在发现里写明条款。

---

## 3. 审什么

对抗着读：每一句都可能把产品原意写窄、写宽或写反。发现用白话写。

先在全文找答案。某章声明不适用且理由成立，该章通过。章节在、内容是占位，按该问题未回答处理。

重点核对：

- 和原文冲突，或原文有的能力消失、原文没有的能力被加进范围
- 漏掉的状态、重复提交、半成功
- 流程图上的写与事务切入点是否同一段
- 接口列表与流程图能否对上
- 待确认是否带采用假设，后文是否用的这条假设

`⚠️ 待确认` 已写出备选、采用假设、后文用的是这条，视为闭环。

进入发现列表的，是会让语义失真、关键决策缺失或前后互斥的内容。类型名、框架写法、单一样本、稿未写的实现细节、已闭环的待确认，单独不构成发现。

---

## 4. 审核顺序

通读原文和全文后再记发现。先审语义，再按《需求显化》的问题顺序往下审，最后看前后是否对得上。

### 4.1 语义是否失真

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 原文里的每个功能点 | 在范围内，或写进非目标，或标了待确认并采用了假设 | 范围内的能力消失：严重 |
| 稿里多出来的能力 | 能指出原文哪一句支持 | 指不出：严重 |
| 原文里的限制 | 状态、不能做的事、失败时怎样，没有被放宽 | 放宽且未标出：严重 |
| 数字、并发、耗时 | 只写原文或目标系统里已经出现的；其余是待确认加采用假设 | 写成已确认事实且会改变主路径：严重；只是多写了一句量级：警告 |

缺原文时本维写「无法对照原文」。

### 4.2 骨架与元信息

显化稿第 0 章到第 13 章，章节连续。不适用的章节保留标题并说明原因。

头部要有：生成时间、原始需求来源、优先级、目标版本、影响范围、关联表、关联接口。未知写待确认。文档编号仅在调用方要求时才需要。

答案已在全文出现、只是章节归位不同：建议，并指出应归入哪一章。问题在全文找不到：按下面各节的级别记缺失。

### 4.3 待确认是否闭环

待确认章集中在第 3 章。原文无歧义时该章写「无」。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 每条待确认 | 有备选，有本次采用的假设 | 警告 |
| 后文 | 使用的是采用的那条假设 | 用了另一条：严重 |
| 边界、状态、失败、相关数据是否立刻一致 | 还不能据此做设计的点已进入待确认，或原文已经无歧义 | 主路径仍靠猜：严重 |

### 4.4 背景、目标、范围、非目标

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 背景 | 写了为何现在要做、现状哪里不够 | 警告 |
| 目标 | 是业务上可以确认的结果 | 只写了实现动作：警告 |
| 范围 | 本次要交付的能力具体 | 严重 |
| 非目标 | 相关但本次明确不做的事具体 | 缺失或空泛：警告 |
| 头部影响范围 | 与范围、关联表、关联接口一致 | 不一致：警告；因此会做错范围：严重 |

### 4.5 规则、场景、异常

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 规则 | 不依赖界面文案也能复述 | 警告 |
| 场景 | 有触发、过程、结果，并能对上后文的接口和流程图 | 主场景对不上：严重；次要：警告 |
| 状态 | 会改变状态的动作写了哪些状态下允许做 | 原文有状态而被漏掉：严重；原文未写：警告 |
| 预期失败 | 每条有触发条件和稳定失败身份 | 主路径失败无法据此分支：严重；其余：警告 |
| 技术故障 | 收成一个统一失败身份 | 警告 |

### 4.6 表设计

先看这次有没有表变动。

**稿声明无变动**：正文是「本需求不涉及表变动」这一类说明。出现候选表、DDL 或查询–索引对照：警告。这些内容把范围外的表写进了交付：严重。

**稿声明有变动**：

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 收入的表 | 只含结构有变化的表，并标明新建或改已有表 | 把结构不动的表写进来：警告 |
| 新建表 | 有 `CREATE TABLE`（或存量表已在用的方言） | 严重 |
| 改已有表 | 有 `ALTER` 或等价语句，并有变更清单 | 严重 |
| 表意图 | 存什么、服务哪个场景、和哪些表关联、唯一性和删除各表达什么 | 严重 |
| 列 | 含义、可空、默认值、唯一性清楚；关联列在删除或更新时如何处理 | 主路径列说不清：严重；其余：警告 |
| 冗余 | 能算出的事实不重复存；冗余写明由谁在何时维护 | 警告 |
| 查询–索引对照 | 变动的表本次会被查询时有对照 | 有查询却没有对照：警告 |
| 索引 | 服务对照里的过滤、排序、分页；唯一性用唯一索引 | 对不上：警告 |
| 存量表口径 | 主键、审计列、删除、命名与稿中声称观察到的存量表一致；看不到的已标待确认 | 写成未观察到的口径：警告 |
| 并发约定 | 只有明显需要的查询或写入才写「可并发 / 须串行 / 流程级互斥 / 待确认」 | 把未观察到的量级写成事实：按 4.1 |

条件不清却没有待确认和采用假设：警告。

### 4.7 领域

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 归属 | 写明归入哪个已有领域，或为何新建 | 规则不知道由谁负责：严重 |
| 归入已有领域 | 写了为什么是它、要不要扩大职责、容易混淆的为什么不是 | 警告 |
| 新建领域 | 有名称、职责、包含、不包含、依赖 | 缺「不包含」：警告；职责和范围对不上：严重 |
| 依赖 | 单向 | 成环：严重 |
| 拿不准 | 标了待确认，并写下本次采用的归属 | 未采用就往下设计：严重 |

### 4.8 Model、领域出入参、接口出入参

三样分开写。某一跳两边字段一致时写明「与上一层相同」，仍然分节列出。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 表无变动 | 写明不新增 Model | 无变动却新造一套 Model：警告 |
| 表有变动 | 每个变动表的 Model 只含该表的列，字段对应表设计里的列 | 对不上：严重 |
| 领域出入参 | 本次每个领域动作都有入参和出参；业务校验失败用第 5 章的失败身份 | 主路径动作缺失：严重 |
| 查询条件 | 若表设计写了查询–索引对照，领域入参与之同一组字段 | 警告 |
| 接口出入参 | 接口列表中的每个接口一组；接口名一致；写明对应哪一项领域出入参 | 主路径对不上：严重；其余：警告 |
| 校验落点 | 格式和必填在接口入参；状态、唯一性在领域入参 | 两层搅在一起导致规则说不清：警告 |
| 缓存 | 需求关心「读到的是不是最新」时才写，并写明以表为准还是以缓存为准 | 需求未涉及却写成事实：警告 |

Model 含接口协议字段，或只在某次调用里出现的过滤条件：警告。

### 4.9 接口列表

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 每条接口 | 有名称、作用、uri、变更、是否幂等 | 主路径缺名称或变更：严重；缺 uri 或是否幂等：警告 |
| uri | 用目标系统已有的名字；还没有则待确认 | 编造了未观察到的 uri：警告 |
| 是否幂等 | 重复调用和调用一次的业务结果相同则填「是」 | 会改变已有状态，却读不出重复做的结果：严重 |
| 失败与字段 | 预期失败指向关键异常；入参出参指向 4.8 | 建议 |

只改已有行为时，列出被波及的已有接口。一个都不列：警告。

### 4.10 业务流程

每个主场景一张 mermaid `flowchart`。节点是业务动作，并标上接口列表里的接口名。

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 主场景 | 每张图注明对应哪个场景 | 主场景没有图：严重 |
| 接口 | 图中的接口都能在列表里找到；列表里被这次流程调用的接口能在某张图里找到 | 主路径对不上：严重；旁路：警告 |
| 写表 | 写表的那一段标出事务起止 | 严重 |
| 事务外 | 远程调用、缓存、通知、返回画在写表那段之外 | 画进了写表段且和事务切入点矛盾：严重 |

### 4.11 事务切入点

没有写表时，本章写「本需求无事务切入点」。图上仍有写表：严重。

有写表时，每张含写表的流程图有一行：

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 切入点 | 写明哪个接口的哪一步 | 严重 |
| 同一次提交 | 写明哪些表、写入什么 | 严重 |
| 多处写表 | 写清是同一次提交还是各自提交 | 读不出来：严重 |
| 事务外 | 远程调用、缓存、通知、返回放在事务外 | 和流程图矛盾：严重 |
| 半成功 | 写明调用方看到什么；没有半成功则写「同一次提交」 | 存在事务外动作或多次提交，却没写调用方看到什么：严重 |

本步审切入点和提交范围。

### 4.12 风险、依赖与摘要

| 检查 | 通过 | 未通过时 |
| ---- | ---- | -------- |
| 第 12 章 | 写了可能让实现走偏的风险、依赖的外部条件、仍未关闭的问题 | 主路径风险在前文出现、这里完全没提：警告 |
| 第 13 章 | 四行可以独立阅读：变更目标、主要影响面、必须守住的约束、适合继续拆开的方向 | 缺行或与正文矛盾：警告 |

### 4.13 前后是否对得上

| 左边 | 右边 | 对不上时 |
| ---- | ---- | -------- |
| 规则 | 场景 | 主路径：严重；其余：警告 |
| 场景里的失败 | 关键异常的失败身份 | 同上 |
| 表的列 | Model 字段 | 严重 |
| 查询–索引对照 | 领域入参的查询条件 | 警告 |
| 领域出入参 | 接口出入参 | 主路径：严重 |
| 接口列表 | 流程图 | 主路径：严重 |
| 流程图上的事务起止 | 事务切入点 | 严重 |
| 待确认的采用假设 | 后文设计 | 严重 |
| 第 13 章四行 | 正文 | 警告 |

同一字段、同一状态、同一失败在两处含义不同：严重。

### 4.14 分级

| 级别 | 何时使用 |
| ---- | -------- |
| 严重 | 按这份稿做，业务语义会做错，或关键决策缺失，实现者只能各自补假设 |
| 警告 | 主路径还能读懂，但后续会返工或理解分叉 |
| 建议 | 不影响语义，只影响表达或章节归位 |

编号为「发现 1」「发现 2」……整份连续。顺序为严重、警告、建议。
