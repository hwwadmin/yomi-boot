# 显化审核

---

## 0. 基础信息

- **Skill 名称**: 显化审核
- **描述**: 对需求显化产出的 `spec.md` 做结构化审核并输出 `audit.md`，作为进入实现前的质量门禁
- **要点**:
  - 阶段 0 按需采集规模/并发假设（禁止猜测、禁止无脑全问）
  - 写路径事务两步法为严重门禁
  - 按需审 Repository/SQL 可服务性
  - 并发两轴打星（1/5～5/5）：**接口并发**（仅 HTTP）+ **非接口并发**（明显需要的方法或整段流程）
- **作者**: zwei
- **创建日期**: 2026-06-04

## 资源与路径约定

- **提示词工程位置**：`_prompts/` 位于**工程根目录**（业务工程整体拷入本套提示词工程，无外部查找）；`_prompts/skills/`、`_prompts/knowledge/` 均相对工程根，知识依赖路径均相对 `_prompts/` 根。
- **业务产物落点**：`_doc/`、`_feat-doc/`、`_task-doc/`、`_ipc-doc/` 均写入工程根。
- **规范真源**：工作流以 `_prompts/skills/`、`_prompts/knowledge/` 为准。
- 业务包结构以 spec「本项目结构约定」为准；boot 根目录仅基础库与演示。

## 本 Skill 用法（与 audit_spec command 一致）

- **门禁**：§3、§5、§6；思维与口径、PRD 边界以 `commands/audit_spec.md` 第 1 步为准。
- **落盘前**：按本文 §6（DoD）自检并勾选。
- **分阶段 Read**：阶段 0 按需 → §3.1.1；写 audit → **本文 §4.1 章纲**。

## 1. 目标

- **做什么**：加载需求显化 Skill 产出的 `spec.md`（位于 `_feat-doc/{YYYYMMDD}_{需求名称}/` 目录下），先按能力画像完成阶段 0 按需采集，再按本 Skill 定义的审核维度、问题级别和输出格式执行结构化审核，生成同目录下的 `audit.md` 审核稿
- **为什么**：需求显化文档是后续实现、评审和验收的上游输入，必须在进入实现前确保其完整性、一致性和可实现性；本 Skill 通过统一的审核骨架和问题分级标准，消除不同审核者之间的口径偏差，输出可直接用于修正决策的结构化审核报告；并对 Repo/SQL 可服务性，以及接口/非接口两轴并发适配给出有假设依据的结论
- **不做什么**：
  - 不负责修改 `spec.md` 正文（阶段 0 假设只写入 `audit.md`）
  - 不负责执行代码实现、编译验证或真实 `EXPLAIN`/压测
  - 不负责维护任务状态、验收状态或执行证据
  - 本 Skill 为可独立加载的执行规则集，由 `audit_spec` command 触发执行
  - 不把实现层细节（struct tag 拼写、类型装配、cron 精确值等）直接写成需求阻塞问题
  - 不对全量 HTTP 路由或全量方法/流程无脑采集；不在无适用画像时强制采集表量等无关项
  - 禁止猜测读写峰值、方法强度、表数据量等规模事实；置信不足必须询问用户
  - 禁止把 Kafka/cron 等非 HTTP 触发源并入「接口并发」轴；禁止设第三轴

### 3.1.1 阶段 0：能力画像与按需采集门禁

**目标**：在进入任何实质审核前，按 spec 能力画像**按需**采集规模与并发假设；**禁止无脑全量问卷**，**禁止猜测**未确认的峰值/强度/表量等事实。

**并发两轴（对象不同，分清单、分采集、分打星）**：

| 轴 | 名称 | 对象（唯一） |
| -- | ---- | ------------ |
| 一 | **接口并发** | **仅 HTTP 接口**（路由/Handler 契约） |
| 二 | **非接口并发** | **明显需要并发考量**的**方法**，或**整段流程/能力设计**（非 HTTP） |

Kafka Consumer / cron / 库导出方法等 **不进第一轴**；属第二轴（方法或流程）。禁止第三轴。第二轴 **宁缺毋滥**，不是凡方法、凡流程都问。

**硬门禁**：适用采集项未获用户确认前，禁止进入阶段 1，禁止输出 audit 终稿，禁止打吞吐星级。若画像后**无任何适用采集项**（例如无表、无 HTTP、无第二轴候选），须在 audit §0 记录画像与「全部跳过」原因后，**可直接进入阶段 1**。

#### 步骤 A：能力画像（只扫 spec，不臆造）

| 画像信号 | 判定依据（示例） |
| -------- | ---------------- |
| 有表/持久化 | 含 DDL、表变更、Repo 持久化读写、明确落库 |
| 有 HTTP 读/写 | Handler/路由清单中存在读或写 HTTP 接口 |
| 有非接口并发候选 | 见步骤 C2「明显需要」信号（库导出热路径、消费/定时处理函数或整段并发流程等） |
| 可能涉及允许策略 | **仅当** spec **已写明**深分页 / 缓存 / 异步削峰 / 限流（含明确选用或排除）。禁止因「审核或许会建议」而预采 |

#### 步骤 B：按需触发采集（未触发则跳过并记账）

| 触发条件 | 采集项 | 未触发时 |
| -------- | ------ | -------- |
| 有表/持久化 | **表数据量**（强制询问，不估算、不默认） | 整段跳过 |
| 有 HTTP 读 | 核心 HTTP 读清单 → 各接口**读峰值** | 跳过接口读峰值 |
| 有 HTTP 写 | 核心 HTTP 写清单 → 各接口**写峰值** + 是否热点 | 跳过接口写峰值 |
| 存在「明显需要」的非接口项 | 核心非接口项清单（方法\|流程）→ 按类型采形态/强度或流程假设 | 第二轴整段跳过（记「无明显非接口并发诉求」） |
| 任一轴有核心项，或涉及锁/缓存/限流/多实例互斥 | **部署形态**（默认预选「集群多实例」，须确认） | 可不采 |
| 用户已确认的核心 HTTP 清单**非空** | **P99**（强制问） | 无核心 HTTP 则跳过 P99；第二轴默认不问 P99 |
| spec **已写明**某策略 | 仅对该策略问是否允许 | 未写明则不问 |

**跳过 ≠ 默认填档**：audit 须写明「已采集 / 已跳过（原因）」。

**采集顺序**：先确认第一轴 HTTP 清单与第二轴非接口清单（均可空）→ 再分轴采档 → 部署/表量/允许策略。

#### 步骤 C1：第一轴 · 核心 HTTP 接口

- 对象**仅** HTTP 接口；不对全量路由逐个问。
- Agent 给候选 + 入选理由 → 用户确认/增删 → 再采峰值。
- 上限：核心读 **≤3**，核心写 **≤3**。
- **优先入选**：C 端/开放、首页/高频列表、关键写（事务/Saga/幂等）、热点行冲突风险。
- **通常不入选**：低频后台 CRUD、按 ID 详情、配置类、常规 Compensate/运维、一次性迁移。
- 筛空：记「无核心 HTTP，跳过接口峰值与接口星级」。

#### 步骤 C2：第二轴 · 核心非接口项（方法或流程）

- 对象：**(a) 方法** 或 **(b) 整段流程/能力设计**；合计上限 **≤5**；**宁缺毋滥**。
- Agent 必须写清「为何明显需要」；说不清则不入选；用户确认后再采。
- Kafka/cron 的**处理函数**或**整段消费/定时管道**属本轴，**禁止**并入第一轴。

**明显需要（入选信号，须有 spec 证据，满足其一即可候选）**：

- 共享可变状态 / 包级缓存 / 热点 key 或行
- 锁、幂等、限流、多实例抢执行
- 可能重叠的高吞吐消费/定时，或与积压/吞吐相关的管道
- 方法或流程内可能无界扇出 goroutine/worker
- 本库能力方案中作为并发安全契约的导出面或能力流程

**默认不入选**：

- 纯转换、`MustInit*`、一次性装配/Close
- 仅被单个 HTTP 串行调用、无共享状态的内部 Service/Repo 步骤（并发算在第一轴）
- 低频单次任务、无重叠/性能诉求的管理流程
- 常规 Compensate（除非 spec 写明高并发重试）

筛空：记「无明显非接口并发项，跳过第二轴」。

#### 步骤 D：字段规则与选项

**第一轴（HTTP）**：

| 字段 | 规则 | 选项 |
| ---- | ---- | ---- |
| 读/写峰值 | 可估则估+依据并供确认；置信不足禁止预填；确认前不得写入 audit §0 为已确认 | `<10` / `10–100` / `100–1k` / `>1k` QPS |
| 写热点 | 随写峰值 | `有热点` / `无热点` / `不确定` |
| P99 | 有核心 HTTP 时强制问 | `无明确要求（按后台可接受）` / `<50ms` / `<100ms` / `<200ms` / `其他（须手填）` |

**第二轴（方法 | 流程）**：

| 字段 | 适用 | 选项 |
| ---- | ---- | ---- |
| 项类型 | 每项必填 | `方法` / `流程` |
| 调用形态 | 方法 | 单 goroutine / 同进程多 goroutine / 多实例同时调（可多选） |
| 强度 | 方法 | 低 / 中 / 高（或调用方量级档）；不够信只问不填 |
| 热点 | 方法 | 同一 key/资源：有 / 无 / 不确定 |
| 并发契约 | 方法 | 可并发 / 须外部串行 / 须每实例互斥 |
| 流程假设 | 流程 | 多实例是否重叠；分片/抢占；步骤幂等与顺序；背压；流程级互斥位置（选择或短填，禁止猜测冒充确认） |
| P99 | 第二轴 | **默认不问** |

**共用**：

| 字段 | 规则 | 选项 |
| ---- | ---- | ---- |
| 部署 | 默认预选多实例；预选 ≠ 已确认 | `单实例` / `集群多实例（默认）` |
| 表数据量 | 有表才问 | `<1万` / `1万–100万` / `>100万` |
| 允许策略 | 仅 spec 已写明项 | 每项：`允许` / `不允许` / `待定` |

**HTTP 峰值高置信估算门槛**（须能引用 spec/PRD/仓内容量说明，否则只问不估）：文档已写明量级；或明确低频人工后台且无开放/大批量风险。

#### 步骤 E：采集 UI（强制 AskQuestion）

有适用采集项时，阶段 0 **必须**调用 Cursor **原生工具** `AskQuestion` 弹出选择框，等待用户提交后再进入阶段 1。

**工具定位（禁止误判为「没有」）**：

- `AskQuestion` 与 `Read`/`Grep` 同级，是会话内置工具，**不在** MCP / `GetDynamicTools` 目录中。
- **禁止**因动态工具目录搜不到该名，就改用纯文本问卷。
- 未调用 `AskQuestion`（有适用项时）视为阶段 0 **未完成**，不得交付 audit 终稿、不得打星。

**调用要求**：

- 用 `AskQuestion` 一次抛出本轮适用题（可多题）；选项与步骤 D 档位一致。
- 建议拆题：① 确认/增删核心清单；② 第一轴各 HTTP 峰值/热点（若有）；③ 第二轴各方法/流程的形态·强度·契约或流程假设（若有）；④ 部署；⑤ 表量（有表时）；⑥ P99（有核心 HTTP 时）；⑦ 允许策略（仅 spec 已写明）。
- 推荐项放选项第一位，并在 label 末标「（推荐）」；用户仍可改选。
- 清单确认题的选项须含：按建议确认 / 增删后确认（Other）/ 本轴全部跳过。

**回退（唯一例外）**：仅当 **已经调用** `AskQuestion` 且运行时报错或被拒绝后，才允许改用对话模板；须在 audit §0 写明失败原因。不得未调用就回退。回退模板：

```text
【显化审核 · 阶段 0 并发与规模采集】（AskQuestion 失败回退）
- AskQuestion 失败原因：…
- 能力画像：{有表/有 HTTP/有非接口候选/…}
【第一轴 · 接口并发】
- 核心 HTTP 读：… → 各峰值
- 核心 HTTP 写：… → 各峰值/热点
- P99：（有核心 HTTP 时）…
【第二轴 · 非接口并发】
- 核心项（方法|流程，≤5）：…

【共用】
```

### 3.4 阶段 3：业务逻辑审核

**目标**：检查 spec 中的业务描述是否存在逻辑冲突、边界缺失、异常路径遗漏或跨域交互不清晰。

**检查维度**：

| 维度 | 检查内容 |
| ---- | -------- |
| 需求覆盖度 | spec 是否完整覆盖了原始需求中的所有功能点；需求显化中标记的 `⚠️ 待确认` 项是否已在 spec 中收敛 |
| 边界条件 | 关键业务动作是否明确了前置条件、后置结果和边界限制（如"已删除的记录不可操作"） |
| 状态流转 | 若涉及状态机，状态转换路径是否完整、是否存在不可达状态或死循环 |
| 异常路径 | 关键写操作是否覆盖了参数校验失败、业务规则冲突、依赖服务不可用等异常场景 |
| 跨域交互 | 跨领域调用方向是否符合架构分层约束；数据传递方式（同步调用/事件）是否明确 |
| 幂等性 | 写操作是否声明 `bizId`/`bizSubId` + `gitee.com/hq_project/yomi-boot/component/common/idempotency`；是否与 DTM barrier 分工清晰（不得互相替代）；是否另有唯一索引/状态前置等业务层保护 |
| 数据一致性 | ① 是否先完成全部写数据动作的事务决策（开否 + 传播关系）再画边界；② 同服务多表写是否同一 `TxRunner` 闭包；③ 跨服务写是否 BFF Saga；④ 缓存与 DB 失效是否在事务外；⑤ 非 DB 副作用是否未混入领域 DB 闭包 |
| 并发与吞吐 | 见下方「并发与吞吐审核」；分**接口轴 / 非接口轴**；星级必须引用阶段 0 已确认假设 |

**并发与吞吐审核**（两轴分审、分表打星，禁止混行）：

1. **正确性**（可不依赖峰值/强度）：
   - 接口轴：丢更新、重复写、幂等与唯一约束、多实例互斥（对照 Redis 锁条款与阶段 0 部署）。
   - 非接口轴·方法：竞态、锁误用、多实例双执行、导出方法内无界扇出、并发契约是否写清。
   - 非接口轴·流程：多实例双跑/抢分片、步骤幂等与顺序、背压、流程级互斥位置是否盖住并发面。
   - 不得把「用了锁」等同于设计合理。
2. **效率星级**（须阶段 0 已确认）：
   - 第一轴：仅对已确认**核心 HTTP**打 1/5～5/5，挂路由。
   - 第二轴：仅对已确认**核心非接口项**打 1/5～5/5，挂 `包.方法` 或流程/场景名；相对形态/强度或流程假设。
   - HTTP 链路上的内部 Service/Repo **默认不打第二轴**（除非其为独立并发契约）。
3. **允许策略联动**：阶段 0 不允许的手段不得作为建议。
4. **两轴皆无核心项**：写明跳过原因，不编造星级；有写冲突正确性风险时仍可审正确性并保留第 10 章要点。

| 星级 | 含义（相对该轴已确认档/假设） |
| ---- | ------------------------------ |
| 1/5 | 正确性或吞吐明显不匹配，高概率事故或打满 |
| 2/5 | 勉强可用，热点/锁/路径有明显短板 |
| 3/5 | 基本匹配，有可接受局部风险 |
| 4/5 | 匹配良好，仅有非关键优化点 |
| 5/5 | 相对该档充分且不过度设计 |

**执行规则**：

- 仅审核 spec 中已写明的业务逻辑，不替 spec 补充遗漏
- 若 spec 未覆盖某异常路径，记录为"缺失"，不自行推断"应如何处理"
- 若前后描述存在语义冲突（如同一字段在两处含义不同），记录为"矛盾"
- 优化建议必须可操作，且不违反阶段 0 允许策略；星级条目必须引用阶段 0 假设

### 3.5 阶段 4：问题分级与编号

**目标**：将阶段 1–3 的审核发现统一分级、连续编号，为输出 audit.md 做准备。阶段 0 以「假设确认/跳过记账」为主，**默认不产出编号发现**；仅当阶段 0 出现违规行为（如猜测冒充已确认、无脑全量采集）且需写入 audit 主问题时，一并纳入本阶段编号。

**问题分级标准**：

| 级别 | 图标 | 判定标准 | 典型表现 |
| ---- | ---- | -------- | -------- |
| 严重问题 | 🔴 | 会直接阻断实现、验收或导致关键边界错误 | 关键章节缺失、前后逻辑冲突、核心输入输出约束缺失、架构分层违反项目强制约定；**写数据动作缺事务决策（是否开事务/传播关系）、颠倒两步法、缺完整边界/Saga/Compensate、可直调写、错误传播假设、闭包混 IO**；SQL 逻辑导致错数/误删/拼接注入；**已确认大表**上核心读路径明确无法用索引且无接受说明 |
| 警告问题 | 🟡 | 不一定阻断实现，但会导致理解偏差、方案分叉或后续返工 | 字段含义不清、规则不完整、默认值与现有口径不一致；**Step 1 已决策但 Step 2 的 `executeCtx`/幂等 key/闭包外 Output 写不清**；查询画像缺失、索引与谓词不匹配、N+1/深分页/重 Count、接口或非接口并发正确性缺口 |
| 建议项 | 🔵 | 不改变主流程，但影响表达精度、一致性或后续维护成本 | 描述不够精确、映射方式未说明、示例格式不统一、文件命名建议；**不写数据动作误包事务**；覆盖索引微调、小表场景过度设计提示 |

**编号规则**：

- 审核稿内所有问题连续编号，格式为「发现 1」「发现 2」「发现 3」……
- 同一编号不得跨级别复用
- 编号顺序强制按严重 → 警告 → 建议排列，同一级别内按发现顺序编号

**常见误报过滤**：

在定级前，必须按以下规则过滤误报，避免把实现细节或项目统一约定误判为需求问题。以下规则同时约束 `audit.md` 的输出内容：

| 误报来源 | 典型误判方式 | 正确处理 |
| -------- | ------------ | -------- |

### 4.2 不得包含的内容

- 不得只输出统计摘要（如"共发现 5 个问题"）而不给完整问题列表
- 不得只保留汇总表而省略逐项问题详情
- 不得包含 §3.5 误报过滤表中列出的任何典型误判行为
- 不得保留与本次审核无关的模板痕迹、占位语和空表格

## 5. 约束与规范

### 5.1 行为约束

- 审核对象必须是需求显化 Skill 产出的 `spec.md`，不得自行扩大审核范围
- **必须先完成 §3.1.1 阶段 0**：按能力画像按需采集；适用项未经用户确认不得进入阶段 1、不得交付终稿、不得打吞吐星级
- 阶段 0 假设只写入 `audit.md` §0，**禁止回写** `spec.md`
- 审核依据优先使用项目知识库规范；规范未覆盖的领域，以 spec 自身语义一致性为准
- 涉及 Go 基础设施选型时，必须遵守 `_prompts/knowledge/Go架构规范.md` §3.11：对照 §3.3 能力包清单，将「已有基础库可满足却平行造轮子 / 重复引入同类第三方库」列为问题
- 所有问题必须有 spec 中的具体位置引用，不得使用"整体感觉""可能有问题"等模糊表述
- 问题分级必须对照 §3.5 的分级标准，不得随意升格或降格
- 修正建议必须可操作，不得只写"请修改"或"建议优化"；且不得违反阶段 0「允许策略」

### 5.2 格式约束

- 输出路径固定为 `_feat-doc/{YYYYMMDD}_{需求名称}/audit.md`
- 章节结构必须包含必选章节：已确认假设（§0）、审核总评、逐项审核发现、审核发现汇总与修正建议、审核结论
- 问题编号在整份审核稿内连续且唯一
- 汇总表编号与逐项发现编号一一对应
- 标题层级清晰、编号连续，无未删除的模板分支

### 5.3 禁止项

- 禁止在 spec 目录之外生成 audit.md
- 禁止修改 spec.md 原文
- 禁止以"建议参考某现有模块"替代具体修正建议
- 禁止在审核结论中给出"可以直接进入实现"的结论但正文中存在未解决的严重问题（含严重事务问题）
- 禁止把「UseCase 表写了需要事务」或「直接画了闭包」视为事务设计已通过；必须先核对 Step 1（全部写数据动作的开否 + 传播关系），再核对 Step 2 边界
- 禁止把 spec 中标注的 `⚠️ 待确认` 项直接当作审核问题：应先判断 spec 是否已就该待确认项做出合理假设并完成设计闭环；若 spec 已给出假设与设计，不得仅因标记过 `⚠️ 待确认` 就升格为问题；若 spec 仅保留标记而未给出任何设计闭环，应记录为"需求收敛不完整"（建议级别）
- 禁止无脑全量采集（无表问表量、全量 API 问 QPS、全量方法/流程采并发、未触发策略仍全问）
- 禁止在有适用采集项时不调用原生 `AskQuestion`，或因 MCP/`GetDynamicTools` 搜不到该工具就改用纯文本问卷
- 禁止猜测读写峰值/方法强度/表量并当作已确认；禁止无阶段 0 确认打吞吐星级
- 禁止把 Kafka/cron/库方法并入接口并发轴，或对 HTTP 链路每个内部 Service 打第二轴星
- 禁止在无表量确认时用「大表」话术将性能问题升为严重
- 禁止把「未做 EXPLAIN」本身写成严重问题

## 6. 验收标准（DoD）

生成 `audit.md` 后，必须通过以下自检：

- [ ] 头部元信息完整，`审核对象` 指向正确的 `spec.md` 路径
- [ ] 已完成阶段 0：有适用项则已通过原生 `AskQuestion` 采集并获用户确认（未因动态工具目录无该名而跳过弹框）；仅 AskQuestion 调用失败才允许文本回退并在 §0 记录原因；无适用项则已记录「全部跳过」；跳过项有原因；audit §0 假设表已写入
- [ ] 未对全量 HTTP 无脑采峰值；核心 HTTP 读/写各不超过 3 个（除非用户明确扩大）
- [ ] 第二轴仅含「明显需要」的方法或流程，合计不超过 5 个；说不清入选理由的未强行入选
- [ ] 有表时已采表量；无表时已跳过表相关采集；峰值/强度无「猜测冒充确认」
- [ ] 已包含必选章节：§0 假设、审核总评、逐项审核发现、审核发现汇总与修正建议、审核结论
- [ ] 所有问题已按统一编号、问题级别和固定字段写清
- [ ] 汇总表与前文问题列表的编号、问题级别和建议保持一致
- [ ] 仅在有实质证据时补充专项章节，未使用的章节未残留空标题或空表格
- [ ] 若 spec 含写数据动作：已先审 Step 1 事务决策（全覆盖、含传播关系），再审 Step 2 边界；未颠倒；建议保留「事务与一致性审核」专章
- [ ] 未把「仅声明需要事务」或「只有闭包没有决策」误判为通过
- [ ] 有持久化时：已完成查询–索引对照或明确记录「查询画像缺失」；建议保留 Repository/SQL 专章
- [ ] 有核心 HTTP 或核心非接口项时：星级分轴挂载且引用 §0；建议不违反允许策略；建议保留并发与吞吐专章；未把消费/cron 打成接口星级
- [ ] 若本轮审核结合了现有代码，遵循 §3.5 误报过滤表中"未经授权做代码对照"规则，正文已明确对照范围和依据
- [ ] 已区分需求/设计层问题与实现层问题，未把类型名、装配方式、struct tag 细节等实现补全项直接写成主问题
- [ ] 若引用现有代码模式，已先核对项目规范或确认其为跨模块稳定样本
- [ ] 若某条发现只体现为"建议补充说明"，未误升格为"设计矛盾"或"必须修复"
- [ ] API/错误码相关发现已按 **Encoder 适配**口径核对（`MustRegister`、经 handler 写出、哨兵落点），未把预制 Encoder JSON 当成强制标准，未沿用已删除的 `code.go`/`FromBizCode`
- [ ] 审核结论明确：是否存在阻塞问题、修正后是否可进入实现阶段；存在未关闭严重事务问题（含缺 Step 1 决策）时结论为不可进入实现
- [ ] 定稿前已删除与本轮审核无关的模板痕迹、占位语和无效示例
- [ ] 文件路径符合 `_feat-doc/{YYYYMMDD}_{需求名称}/audit.md` 格式
