# AI 开发工作流说明

一句话：**先把需求说清楚、把方案审干净，再让 AI 写代码。审核不通过，一行代码都不写。**

## 主流程：六步

```
① prd-spec      写 PRD
       ↓
② create-spec   写技术方案
       ↓
③ 人工审阅      拍板定稿
       ↓
④ audit-spec    找问题
       ↓
⑤ 修到闭合      复审
       ↓
⑥ do-spec       写代码
```

| 步骤 | 做什么 | 产物 |
|---|---|---|
| 1. `prd-spec` | 需求聊透后，把结论写成 PRD。只写产品业务，不碰技术 | `_doc/{YYYYMMDD}_{需求名}-prd.md` |
| 2. `create-spec` | 按 PRD 写技术方案：范围、规则、表、领域、出入参、接口、流程、事务切入点 | `_feat-doc/{YYYYMMDD}_{需求名}/spec.md` |
| 3. 人工审阅 | 你来看方案有没有跑偏：拍板 `⚠️ 待确认`、纠正业务规则、指出架构偏差，让 AI 回写 | 修订后的 spec |
| 4. `audit-spec` | 对照需求原文审方案：有没有写歪、写漏、写矛盾，按严重 / 警告 / 建议分级 | 同目录 `audit.md` |
| 5. 修到闭合 | 逐条处理发现并复审。严重问题清零、结论写明「可进入实现」才算过 | 关闭的 `audit.md` |
| 6. `do-spec` | 拆成原子任务，逐个推进：先写会失败的测试 → 再写实现 → 跑通后回写进度 | `_task-doc/{需求名}/tasks.md` + 代码 |

## 三条硬规矩

- **门禁在审核**：`do-spec` 开工前必须看到审核稿没有未关闭的严重问题、结论是可进入实现；否则它停下来，告诉你差在哪。
- **人拍板，AI 执行**：`⚠️ 待确认` 的业务规则由你定。AI 只能列备选、标明本次采用的假设，不能把没观察到的事写成事实。
- **全程说白话**：问题、影响、改法都用大白话写；信息不足就标待确认，不臆造。

## 怎么用

- 技能在 `_prompts/skills/{技能名}/SKILL.md`，对话里直接点名即可，例如 `create-spec：订单退款`。就这一层，没有 commands 之类的中间层。
- 别的工程要用时，把 `_prompts/skills/` 整个拷过去。PRD、spec、任务等产物会落在那个工程的根目录下。

## 可选技能（不在主闭环里）

| 技能 | 什么时候用 | 产物 |
|---|---|---|
| `check-code` | 代码落地后巡检：先取证、再对照、后分级，默认只检不修 | `_ipc-doc/{YYYYMMDD}_{模块名}-ipc.md` |
| `deep-think` | 卡住或要拍板时，用第一性原理 + 对抗性审查把问题想透 | 对话里给结论，不落盘 |
| `clean-architecture-ddd-light` | 评审分层、依赖方向、业务边界，判断一段逻辑该放哪一层 | 对话结论 |

这三个技能互不前置，也不会被 `do-spec` 自动触发。
