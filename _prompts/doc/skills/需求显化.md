# 需求显化

---

## 0. 基础信息
- **Skill 名称**: 需求显化
- **描述**: 将模糊的产品需求显化为单份原始需求显化文档，聚焦 SQL 表结构设计、业务领域归属、UseCase 编排层设计、**事务与一致性设计**、Model / Input / Output 建模、Repository 接口与实现边界、域内/跨域数据交互、Handler 入口与 API 设计、关键异常路径与错误码约束及前端需求转换，作为后续 spec 工作流工具的上游输入
- **作者**: zwei
- **创建日期**: 2026-04-13

---

## 1. 目标

- **做什么**：将产品给出的一段需求描述，整理为结构化、单文档的原始需求显化文档
- **为什么**：产品需求通常以用户故事或非技术语言描述，开发人员需要二次解读，容易产生理解偏差；本 Skill 通过标准化流程消除歧义，先沉淀一份足够完整的技术需求原文，再交给后续 spec 工作流工具继续拆解和推进
- **不做什么**：
  - 不负责编写具体代码实现
  - 不负责输出 `tasks.md`、`checklist.md` 等执行态文档
  - 不负责维护任务状态、验收状态、执行证据与自动验收结果
  - 不负责输出 UI 设计稿、原型图或视觉规范（文字描述的 UI 说明属于需求文档范围）
  - 不负责性能压测方案
  - 不负责部署与运维方案

### 架构分层原则（贯穿全文）

> 分层与目录以 [Go业务分层规范](../knowledge/go/Go业务分层规范.md) 为准，职责边界详见 §3.3。`internal/bootstrap` 手写装配、插件化启动与路由见 [Go架构规范](../knowledge/go/Go架构规范.md) §3.4。本 Skill 额外约束：

- **领域 UseCase**：单域编排 + 入参基础校验（`Validate()`）+ 写操作经 `idempotency.Execute` + `dtm.TxRunner` 包裹 + Entity→Output 映射（Output 映射在事务闭包外）
- **BFF `bff/`**：只读跨域聚合（经**领域 client** 调领域读接口）
- **BFF `saga/`**：跨域写编排（提交 DTM Saga，组装 bizId/bizSubId 信封与补偿快照）；**唯一跨域写入口**
- **Domain Service**：同域编排 + 领域规则 + 不变量校验；通过 `{Module}Service` 暴露语义完整的领域命令；**不感知事务**
- **Repository**：持久化与查询，无业务规则；通过 `db.Exec(ctx, r.DB)` 感知 Context 事务，禁止自行 Begin/Commit
- 跨域协作收口在 BFF `bff/` / `saga/`；域内协作收口在 Domain Service；领域 UseCase 之间禁止互相依赖
- 不得在 UseCase 中拼装同域多步 repo 语义；单域写操作 UseCase 可较薄（调一次 Service 命令即可）
- 常规 CRUD 用 GORM 链式 API；复杂场景才回退原生 SQL
- **事务硬约束**（详见 §3.4.2 与 `Go事务规范.md`）：**凡设计中写数据的动作，须先标明是否开启事务（或与外部接口的事务传播关系），再确定事务边界**；Saga 写必须成对 Action/Compensate；事务闭包仅含本地 DB 步骤；禁止领域直调写路由与 Facade/Direct 回退

### 3.0 需求澄清（前置步骤）

**目标**：在进入任何设计章节之前，识别需求描述中的模糊点，避免基于不确定前提做出错误设计。

**执行规则**：

- 通读产品需求，识别以下类型的模糊点：
  - **缺少边界条件**：如"刷新缓存"——是刷新全部配置缓存，还是仅刷新当前配置项？
  - **缺少状态定义**：如"公告可下线"——哪些状态下允许下线，是否允许重复下线？
  - **缺少异常路径**：如"删除角色前需解绑资源组"——若角色仍绑定用户或资源组，接口如何处理？
  - **缺少关键规则**：如"系统参数支持缓存"——更新配置后是立即清理缓存，还是由后台手动刷新缓存？
- 对每个模糊点，用 `⚠️ 待确认` 标记并列出备选假设，然后**选取最合理的假设继续执行，不阻塞后续设计**
- 所有待确认项汇总在需求显化文档的最前面，供产品/开发确认

**若需求清晰无歧义**：跳过本步骤，直接进入 §3.1。

### 3.1 SQL 表结构设计

**目标**：为本次需求涉及的持久化数据给出完整的 DDL，并说明每张表的设计意图。

**执行步骤**：

1. **识别实体**：从需求描述中提取所有需要持久化的概念（名词），列出候选表清单

2. **加载数据库设计规范**：在正式设计之前，必须加载 §2.2 知识文档依赖中声明的《数据库表设计规范》，**完整阅读**后再进行设计，以确保与项目已有规范保持一致。若需求涉及缓存方案，同时加载《Redis设计规范》

3. **参考已有 DDL**：优先查看 `script/sql/` 目录下的存量表结构，掌握表名前缀、审计字段、枚举字段、索引命名习惯，标记哪些候选表与存量表重合（复用）、哪些需要新建

4. **设计字段与索引**：结合第 2、3 步获取的规范与风格，完成每张表的字段设计和索引设计

5. **输出 DDL 与设计意图**：以标准 `CREATE TABLE` SQL 块输出，每张表后附一段**表意图说明**（2-5 句话），解释该表存储什么数据、服务哪个业务场景、与哪些表存在关联

6. **若无新增表**：若需求不涉及新建表（仅修改已有表字段，或无需任何持久化变更），在本章输出：
   - `本需求不涉及新增表结构`，并简述原因
   - 若涉及**已有表字段变更**，列出变更清单：`表名 | 字段名 | 变更类型（新增/修改/删除）| 变更说明`

**输出格式示例**：

```sql
-- 系统配置表：存储后台可维护的 KV 配置项
CREATE TABLE `t_config` (
  `id` bigint NOT NULL COMMENT '主键ID',
  `config_key` varchar(100) NOT NULL COMMENT '配置键',
  `config_value` varchar(500) NOT NULL COMMENT '配置值',
  `description` varchar(255) DEFAULT NULL COMMENT '配置描述',
  `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
  `create_by` bigint DEFAULT NULL COMMENT '创建人ID',
  `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
  `update_by` bigint DEFAULT NULL COMMENT '更新人ID',
  `delete_time` datetime DEFAULT NULL COMMENT '删除时间',
  `delete_by` bigint DEFAULT NULL COMMENT '删除人ID',
  PRIMARY KEY (`id`),
  UNIQUE KEY `uk_config_key` (`config_key`),
  KEY `idx_create_time` (`create_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='系统配置表';
```

> **表意图说明**：`t_config` 表用于承载后台管理可维护的系统参数，配置键全局唯一，供业务模块按键读取。审计字段遵循项目统一审计字段口径，删除状态通过 `delete_time` 判定。若需求涉及配置缓存，本表仍只存储持久化数据，缓存策略应在 Repository 实现或组件层单独说明。

### 3.2 业务领域判断与定义

**领域判断标准（内置规范）**：

> 领域是一组具有统一业务语义和清晰边界的业务能力集合。判断依据：**同一领域内的概念彼此强内聚，跨领域的概念彼此弱耦合**。

**判断步骤**：

1. **提取核心概念**：从需求中提取 3-5 个核心业务名词（如：系统配置、配置缓存、公告发布、角色资源组）
2. **识别已有领域**：优先结合 `_prompts/doc/knowledge/go/Go业务分层规范.md` 与业务工程可部署单元目录（惯例示例 `services/{unit}/internal/biz/domain/`）模块结构识别现有**各领域服务**，通常应先判断是否归入仓库中已存在的业务域（**示例域**：以项目现有域为准，勿把示例名写成强制适用范围）
3. **匹配度判断**：逐一对比核心概念与已有领域职责，若 **超过 60% 的核心概念** 落在某已有领域的职责范围内，则归属该领域；否则判断为新领域
   - **特殊情形**：若核心概念均匀分散至多个已有领域（如概念 A 属于领域 X、概念 B 属于领域 Y，无任何一个领域超过 60%），则以**主要业务能力**所在领域为归属判断依据（业务能力数量最多的领域），若确实无法判断，直接定义为新领域并在文档中标注 `⚠️ 待确认`
4. **若是新领域**，执行 §3.2.1
5. **若属已有领域**，执行 §3.2.2

#### 3.2.1 新业务领域定义

当需求引入全新的业务概念、无法归入已有任何领域时，必须完整定义新领域：

| 输出项 | 说明 |
| ------ | ---- |
| **领域名称** | 中文业务名 + 英文标识符（如：订单领域 `order`） |
| **领域职责** | 该领域负责管理哪些核心业务概念（2-4 句话描述） |
| **领域边界—包含** | 列出该领域内的所有业务能力（功能列表） |
| **领域边界—排除** | 明确列出哪些相关但不属于本领域的概念 |
| **对外契约** | 本领域向外部暴露的 Service 能力（方法签名或事件） |
| **依赖领域** | 本领域依赖哪些其他领域（允许单向依赖，禁止循环依赖） |

**输出格式示例**：

```
### 新领域定义：{领域中文名}（{domainKey}）

**职责**：
- 管理 {核心业务对象} 的完整生命周期
- 对外暴露 {关键业务能力}，供 UseCase 或其他领域按契约调用

**边界—包含**：
- {能力点 1}
- {能力点 2}
- {能力点 3}

**边界—排除**：
- 不负责 {应由其他已有领域承担的职责 1}
- 不负责 {应由其他已有领域承担的职责 2}

**对外契约**：
- `{DomainKey}Service.{methodA}(...)`
- `{DomainKey}Service.{methodB}(...)`

**依赖领域**：{如有依赖则列出；若无则写“无”}
```

#### 3.2.2 归属已有领域说明

当需求属于已有领域时，必须明确说明：

| 输出项 | 说明 |
| ------ | ---- |
| **归属领域** | 领域名称 + 英文标识符 |
| **归属理由** | 从业务职责角度说明为什么属于该领域（3-5 句话） |
| **对已有边界的影响** | 是否需要扩展该领域的边界？如需扩展，列出新增的业务能力 |
| **不归属其他领域的理由** | 如有可能混淆的领域，逐一说明为何不属于那些领域 |

### 3.3 领域模型定义

> 路径与分层、Entity 贫血/充血建模见 [Go业务分层规范](../knowledge/go/Go业务分层规范.md) §3.1.2；Entity/Model/Mapper 规则见 [Go数据库规范](../knowledge/go/Go数据库规范.md)；文件命名见 [Go文件命名规范](../knowledge/go/Go文件命名规范.md)。

**Entity 建模口径**（详见 [Go业务分层规范](../knowledge/go/Go业务分层规范.md) §3.1.2）：

- **默认贫血**：Entity 以字段与简单状态为主，领域规则与同域编排收口在 domain/service
- **按需充血**：仅当单一 Entity 含复杂状态机、多分支不变量或高度内聚行为组合时，才在 spec 中为 Entity 设计内聚方法；须说明采用充血的理由
- **充血约束**：Entity 方法不访问 repository、不跨 Entity 编排；对外入口仍为 `{Module}Service`

**本 Skill 需区分的两类 I/O**：

- **领域 DTO**（`domain/contract/{module}/{module}_dto.go`）：供 Service 使用，不感知 HTTP
- **UseCase I/O**（`{action}_{scope}_usecase.go`）：供 Handler 使用，带 JSON tag

**执行步骤**：

1. 为领域内每个核心业务概念定义 **Entity**（`domain/contract/{module}/{module}_entity.go`），列出核心字段及含义；默认贫血，仅在确有必要时列出 Entity 行为方法并说明充血理由
2. 定义对应的 GORM **Model**（`repo/db/{module}/{module}_model.go`）和 **Mapper**
3. 为本次需求涉及的业务动作定义 Service 方法，说明入参、出参、业务含义
4. 定义 Repository 接口（repo/contract）与方法（repo/db），说明 SQL 依赖与缓存策略

**输出格式示例**：

**领域 Entity**（`domain/contract/{module}/{module}_entity.go`）

```go
package config

// Config 表示系统配置领域实体
type Config struct {
    ID          int64  // ID 是主键
    ConfigKey   string // ConfigKey 是配置键
    ConfigValue string // ConfigValue 是配置值
    Description string // Description 是配置描述
    CreateTime  int64  // CreateTime 是创建时间，Unix 时间戳（毫秒）
    UpdateTime  int64  // UpdateTime 是更新时间，Unix 时间戳（毫秒）
}
```

**GORM Model**（`repo/db/{module}/{module}_model.go`，包内私有）

```go
package repo

const tableName = "t_config"

type configModel struct {
    ConfigKey   string  `gorm:"column:config_key"`
    ConfigValue string  `gorm:"column:config_value"`
    Description *string `gorm:"column:description"`
    db.BaseModel
}

func (configModel) TableName() string {
    return tableName
}
```

**SQL 映射**（仅当存在 GORM 链式 API 无法表达的复杂原生 SQL 时才创建）

> 本需求所有数据访问均使用 GORM 链式 API 完成，无需原生 SQL。不创建 `{module}_sql_mapping.go` 文件。

**领域 Service 接口契约**（`domain/contract/{module}/{module}_contract.go`）

```go
package {module}

import "context"

// {Module}Service 表示{领域中文名}领域服务接口
type {Module}Service interface {
    // Create 创建{实体名}
    Create(ctx context.Context, input *CreateInput) (*{Entity}, error)
    // GetByID 按 ID 查询{实体名}
    GetByID(ctx context.Context, id int64) (*{Entity}, error)
}
```

**领域 Service 实现**（`domain/service/{module}/{module}_service.go`）

> 实现 domain/contract 中的 `{Module}Service` 接口，依赖 repo/contract 中的 `{Module}Repository` 接口。承担**同域编排**、**领域规则**与**不变量校验**；多步读写（如级联删除、分配前校验）内聚在 Service 的领域命令中，不拆成 repo 步骤暴露给 UseCase。

**Repository 接口契约**（`repo/contract/{module}/{module}_repo_contract.go`）

```go
package repo

    "context"
```

### 3.4.1 UseCase 编排层设计

**目标**：在进入交互流程设计之前，先把当前项目最关键的编排层显式写清，确保需求显化结果能直接映射到业务工程可部署单元目录（惯例示例 `services/{unit}/internal/biz/usecase/{module}/`；BFF 跨域读/写分别映射到 `bff/`、`saga/`）。

**执行规则**（完整 UseCase 约束见 `Go业务分层规范.md` §3.3 和 `Go代码规范.md` §3.1，以下仅列出 Skill 特有的设计输出规则）：

- 一个 HTTP 动作通常对应一个 UseCase 文件；文件命名遵循 `{action}_{scope}_usecase.go`
- UseCase I/O 结构体定义在 UseCase 文件中（带 JSON tag），Input 需实现 `Validate()` 方法（**入参基础校验**：判空、格式、Trim 等）
- UseCase 负责**单域**编排，可调用本域 Service，但不得直接依赖 Repository，不得在 UseCase 中拼装同域多步流程
- **跨域写编排**在 BFF `saga/` 完成，不在领域 UseCase 中 HTTP 调其他服务
- 单域写操作 UseCase 应优先调用 Domain Service 的**一次性领域命令**（如 `RoleService.Create`、`RoleService.Delete`），而非组合多次 repo 语义
- Handler 通过构造函数直接注入所需的独立 UseCase，字段名与用例语义一致
- **凡写数据的 UseCase / Saga / 领域命令，事务列必须先完成「是否开事务 / 传播关系」决策，再写边界细节**（顺序与字段见 §3.4.2）；禁止跳过决策直接写闭包；禁止只写「需要事务」三字；纯查询写「不写数据 / 无需事务」

**事务列填写顺序**（与 §3.4.2 两步法一致；细节表见该节）：

1. **先决策**：是否写数据 → 是否开启本地事务 → 与外部接口的事务传播关系（见传播选项）
2. **再边界**：仅当决策为「开事务」或「Saga 分支本地子事务」时，再补包裹方式、幂等 key、Compensate、闭包范围、依赖注入

**输出格式示例**：

| UseCase 文件 | 输入类型 | 调用的 Service | 输出类型 | 编排职责 | 事务（先决策 → 再边界） |
| ------------ | -------- | -------------- | -------- | -------- | ---- |

### 3.4.2 事务与一致性设计

**目标**：对本次需求中**所有写数据动作**按固定顺序完成设计——**先决策是否开事务（及与外部接口的传播关系），再确定事务边界**——避免未做决策就画闭包，或只勾「需要事务」却无法落地。完整约束以 `Go事务规范.md` §3.2–§3.8 为准。

**何时必须输出本章**：只要需求包含任一写数据动作（领域 DB 写、跨域写、多表写、写后改缓存/发通知等副作用涉及持久化或跨服务状态变更），就必须输出；若全需求均为纯读，写「本需求无写数据动作，无需事务与一致性设计」并简述原因。

**强制顺序（两步法）——不得颠倒**：

```text
Step 1  写动作事务决策（每个写数据动作一行）
        ↓ 是否写数据？是否开本地事务？与外部接口的传播关系？
Step 2  事务边界设计（仅对「开事务 / Saga 分支本地子事务」的动作展开）
        ↓ 闭包内外、Saga 分支与补偿、Handler 入口、幂等、禁止项
```

#### Step 1：写动作事务决策（先做）

**覆盖范围**：设计中出现的每一个写数据动作，包括但不限于：UseCase、领域 Service 命令、BFF `saga/` 编排、Repository 多表写语义、以及会改变外部系统状态的调用（HTTP 写、Redis 写、消息投递等）。**漏列任一写动作视为未完成显化。**

每个写动作必须先回答：

| 决策项 | 可选值与含义 |
| ------ | ------------ |
| 是否写数据 | 是 / 否（否则本行写「无需事务」并停止，不进入 Step 2） |
| 是否开启本地 DB 事务 | **开**：本服务 usecase 经 `idempotency.Execute`+`TxRunner` 开启；**不开**：须写明可接受的非原子理由（默认写路径应开，不开须强理由） |
| 与外部接口的事务传播关系 | 见下方「传播关系选项」；**禁止**假设 HTTP 调用能加入本服务 GORM 事务 |

**传播关系选项**（与本项目架构对齐，四选一或组合说明）：

| 选项 | 适用场景 | 含义 |
| ---- | -------- | ---- |
| `不适用` | 无外部写接口 | 仅本服务本地写 |
| `无传播（外部调用在事务外）` | 本地开事务且调用外部 HTTP/Redis 等 | 外部调用**不得**放入 DB 事务闭包；失败靠业务补偿或 Saga，不靠跨进程事务传播 |
| `Saga 分支本地子事务` | 领域作为 DTM 分支 | 本服务开本地子事务 + barrier；与 BFF/其他域**无**共享 DB 事务，由 DTM Saga 协调 |
| `Saga 提交（编排方）` | BFF `saga/` | 编排方不操作领域 DB；只提交 Saga，各分支自行开本地事务 |

**Step 1 输出表示例**：

| 写动作 | 所在层 | 写的资源 | 是否开本地事务 | 与外部接口的传播关系 | 决策理由 |
| ------ | ------ | -------- | -------------- | -------------------- | -------- |
| 创建配置 | 领域 UseCase | `sys_config` | 开 | 不适用 | 单域单表写，需原子提交 |
| 删除角色 | 领域 UseCase（Saga 分支） | 角色表+绑定表 | 开 | Saga 分支本地子事务 | 同域多表原子；跨域由 BFF Saga 协调 |
| 分配角色（编排） | BFF `saga/` | 多域 + token | 不开（BFF 无领域 DB） | Saga 提交（编排方） | 跨服务不能共享 DB 事务 |
| 撤销 token | BFF 副作用 | Redis token | 不开 DB 事务 | 无传播（独立于领域 DB 事务） | Redis 不进领域 DB 闭包；Saga 成功后或独立分支 |

> Step 1 **未完成前，禁止进入**闭包步骤表、Saga 补偿表等边界设计。

#### Step 2：事务边界设计（后做）

仅对 Step 1 中「开本地事务」或「Saga 分支本地子事务」的动作展开；编排方（Saga 提交）写清分支顺序与各分支对应的领域动作即可。

1. **原子性与闭包边界**：同服务多表是否同一 `TxRunner` 闭包；闭包内**仅**本地 DB（`executeCtx` → Service → `db.Exec`）；Redis/HTTP/缓存失效在闭包外或独立 Saga 分支
2. **Saga 设计**（有跨域写时强制）：分支顺序、Action/Compensate 成对 URL、payload（含补偿快照）、失败补偿语义；BFF **不**实现领域状态恢复
3. **Handler 入口约束**：领域写仅 DTM Action/Compensate 成对入口；**禁止**直调写、Facade/Direct、同 URL 分流
4. **幂等分工**：`bizId`/`bizSubId` + `gitee.com/hq_project/yomi-boot/idempotency` 与 DTM barrier 分开，不得互相替代
5. **禁止项自检**：无直调写、无闭包内组 HTTP Output、无 Compensate 再查外服务、无 repo/service 自行开事务、无「外部 HTTP 加入本地事务」的假设

### 3.5 域内数据交互流程

> 说明：当前项目中的**域内交互**，是指同一业务动作在 **Handler → UseCase → Service → Repository → SQL** 之间的数据流转过程。
> 该章节描述的是同一领域内部的完整执行链路，必须显式区分 Handler、UseCase、Service、Repository 的职责边界：**UseCase 做入参基础校验与 Output 映射；同域多步编排与不变量校验在 Service；Repository 只做持久化**。

**执行规则**：

- 每个独立的 UseCase 为一个交互组
- 触发入口优先写 UseCase 的 `Execute(ctx, input)`，而不是 HTTP 路由字符串；Saga 写用例另列 `Compensate(ctx, input)` 交互要点或同组内成对说明
- 每组内按步骤编号逐条说明数据如何在 Handler、UseCase、Service、Repository 之间流动
- 需标明每一步的数据形态（Input、基础类型、Model、Output）
- 需标明每一步的校验点（UseCase 入参基础校验、Service 领域不变量校验等）
- **写操作交互组强制步骤**（缺任一项视为未完成显化）：
  0. 组首标明 Step 1 决策结论：是否写数据、是否开本地事务、与外部接口的传播关系（与 §3.4.2 Step 1 表一致）
  1. 若决策为开事务：标明 `idempotency.Execute(guard, txRunner, ctx, key, fn)` **进入点**与幂等 key
  2. 事务闭包内步骤须使用 `executeCtx`（不得写「继续用外层 ctx 写库」）
  3. Repository 步骤写明经 `db.Exec(executeCtx, r.DB)`（或等价表述）感知事务
  4. 标明闭包变量捕获方式；**Entity→Output / HTTP 响应组装必须在事务闭包外**；外部 HTTP/Redis 不得出现在闭包内步骤
  5. 若同文件含 `Compensate`，说明补偿步骤与快照字段来源（BFF payload）
  6. 若决策为不开事务但仍写数据：组内须复述强理由，并说明失败时的一致性后果

### 3.6 跨领域数据交互流程

> 说明：当前项目中的**跨领域交互**仅在 BFF 层发生：只读聚合收口到 `bff/`（经**领域 client** 调领域读接口），写编排收口到 `saga/`（提交 DTM Saga）。领域 Service **禁止** HTTP 互调；同域多步流程内聚在各自 Domain Service 的领域命令中。

**执行规则**：

- 每组跨领域交互必须明确标注**参与的领域名称**与所在**入口编排服务（BFF）可部署单元**（多入口时按端拆分，写明端别与 `router_prefix`）
- 跨领域只允许通过 DTO、基础类型或必要的事件 DTO 传递数据，禁止直接传递 SQL 相关对象
- 若为只读聚合，说明 BFF `bff/` 或 handler 经领域 client 的调用顺序及各接口返回数据
- 若为跨域写（DTM Saga），必须说明：
  - BFF `saga/` 分支顺序与 Submit 时机
  - 各领域 **Action / Compensate 成对 URL**（独立 Handler 方法，禁止同一 URL 分流）
  - payload 字段（`bizId`、`bizSubId`、**补偿快照**）；领域 Compensate **不得**再 HTTP 查询其他服务补数据
  - 非 DB 副作用（如 token 撤销）归属：独立 Saga 分支或 Saga 成功后调用，**不得**写入领域 DB 事务闭包
  - 明确**无** BFF 直调领域写、**无** Facade/Direct 回退路径
- 若需求不涉及跨域写，则无需补充 Saga 组；若仅有单域写，跨域章节可写「本需求无跨域写，领域写事务见 §3.4.2 / 域内交互组」

### 3.7 Handler 入口与 API 设计

> 说明：BFF Handler 负责对外路由与编排；领域 Handler 负责协议适配。BFF 从 token 解析 Claims 后通过 client 显式传 `operatorId` 等；领域 usecase 从 Input 读取，不读 token Context。JSON 绑定等重复逻辑经 `gitee.com/hq_project/yomi-boot/handler` 收口。
> Handler 不直接承载业务逻辑，也不直接操作 Service、Repository 或 SQL。
>
> **HTTP 出口编码适配**以 [API编码适配规范](../knowledge/api/API编码适配规范.md) 为准：
> - 服务启动必须 `response.MustRegister(...)` 显式注册 Encoder；禁止静默默认。
> - Handler 只调用 `WriteSuccess` / `WritePageSuccess` / `WriteBusinessError`（底层 `Enc().EncodeSuccess|EncodePage|EncodeFailure`），禁止手写 `c.JSON` 拼业务信封。
> - **具体 JSON 字段、成功判定、分页 total 位置由本服务已注册的 Encoder 决定**；显化文档须写明本服务选用的 Encoder（或指向其契约），不得把预制实现字段抄成全站强制标准。
> - 失败语义：框架哨兵 `Error()` 即为可识别失败身份（通用见 `gitee.com/hq_project/yomi-boot/shared/error`，库私有就近定义）；域错误用业务 `bizerr`；**权限类 code 由业务自定**。前端如何读成败以本服务 Encoder 契约为准。

**执行规则**：

- 列出本次需求涉及的所有 HTTP 接口
- 每个接口明确标注：HTTP 方法、路由、入口 Handler / UseCase、请求参数说明、是否需要认证 / 权限、调用了哪些 Service、响应数据来源
- 若一个接口聚合了多个领域，需说明 BFF `bff/` 内经**领域 client** 的聚合顺序与数据拼装逻辑
- Handler 只调用 UseCase，不将 `*http.Request` 传入 Service；若 UseCase 需要 HTTP 请求信息（如登录 IP），在 Execute 签名中显式声明，由 `BindAndHandleWithRequest` 传入
- **入口编排对外**可用 GET 或 POST（见 [Go架构规范](../knowledge/go/Go架构规范.md) §3.6）；**微服务间**强制 POST/JSON（见 [微服务调用规范](../knowledge/api/微服务调用规范.md) §3）；spec 中入口编排路由列**完整 URL** = `router_prefix`（按端在配置中设置）+ `/v1/{资源}/{动作}`（`{资源}` 为单数名词；**示例**：如管理端/App）；BFF 对外写接口由 `saga/` 提交 DTM，领域对内写接口仅列 Action/Compensate 成对路径（见微服务调用规范 §3.1.1）
- **仅含单个 id 字段的请求结构体统一命名为 `{Action}Input`**（如 `GetConfigDetailInput`），不创建 `IdDTO` 等公共 DTO
- **分页查询 Input 嵌入 `dto.PageInput`**（字段 `page`、`pageSize`），业务分页 Input 额外包含筛选字段；出参直接返回 `*dto.PageOutput[TItem]`
- 响应输出：单条 `WriteSuccess` → `EncodeSuccess`；分页 `WritePageSuccess` / `BindAndHandlePage` → `EncodePage`；失败 `WriteBusinessError` → `EncodeFailure`；实现优先 `BindAndHandle*`；**`total` 等字段摆放由本服务 Encoder 决定**（见 [API编码适配规范](../knowledge/api/API编码适配规范.md)）
- 每个接口至少说明成功路径与关键失败路径；预期业务失败须写出稳定字符串 `code`（如 `USER_NOT_FOUND`）及哨兵落点（`shared/error` / 库内 / `bizerr`）
- 仅将用户可见的业务失败、参数校验失败写入接口错误语义；内部技术异常只说明统一兜底为 `INTERNAL_ERROR`（`shared/error.ErrInternal`），不把堆栈或口语化细节写成前端契约
- 若需求涉及前端国际化，应参考 React 国际化规范，在 §3.8 中说明：前端只按 `code` 做 i18n，**禁止**消费响应 `msg`

**输出格式示例**：

| HTTP 方法 | 路由（示例：`router_prefix`=`/{endpoint}/api`） | 入口 Handler / UseCase | 接口说明 | 请求参数 | 权限要求 | 关联 Service | 响应组装说明 | 错误码说明 |
| --------- | ---- | --------------------- | -------- | -------- | -------- | ------------ | ------------ | ---------- |
| `POST` | `{router_prefix}/v1/config/query` | `ConfigHandler.handlePageConfig` → `PageConfigUseCase` | 后台分页查询系统配置 | Body: `PageConfigInput`（嵌入 `dto.PageInput`） | 入口端已登录（**示例**） | `ConfigService.PageList(ctx, ...)` | `BindAndHandlePage(c, h.PageConfig.Execute)` 输出列表与 `total`（摆放由 Encoder 决定） | 参数错误走 `Validate()` |
| `POST` | `{router_prefix}/v1/config/detail` | `ConfigHandler.handleGetDetail` → `GetConfigDetailUseCase` | 后台按 ID 查询配置详情 | Body: `GetConfigDetailInput` | 入口端已登录（**示例**） | `ConfigService.GetByID(ctx, id)` | 将 Entity 转为 Output，handler 使用 `WriteSuccess` 输出 | 详情不存在返回 `ErrConfigNotFound` |
| `POST` | `{router_prefix}/v1/config/cache/refresh` | `ConfigHandler.handleRefreshCache` → `RefreshConfigCacheUseCase` | 手动刷新系统参数缓存 | Body: `{}`（空结构体） | 入口端已登录（**示例**）；权限由 token 中间件控制 | `ConfigService.RefreshCache(ctx)` | handler 使用 `WriteSuccess` 输出空 data（形状由 Encoder 决定） | 内部技术失败仅说明统一兜底 |

**Handler 注册示例**（`config_handler.go`）：

```go
package handler

import platformhandler "gitee.com/hq_project/yomi-boot/handler"

// ConfigHandler 配置模块 Handler
type ConfigHandler struct {
    PageConfig       *configusecase.PageConfigUseCase
    GetConfigDetail  *configusecase.GetConfigDetailUseCase
    RefreshCache     *configusecase.RefreshConfigCacheUseCase
}

// Routes 注册配置模块路由（相对路径，完整 URL = router_prefix + 路径）
func (h *ConfigHandler) Routes(router *gin.RouterGroup) {
  router.POST("/v1/config/query", h.handlePageConfig)
  router.POST("/v1/config/detail", h.handleGetDetail)
  router.POST("/v1/config/cache/refresh", h.handleRefreshCache)
}

func (h *ConfigHandler) handlePageConfig(c *gin.Context) {
    platformhandler.BindAndHandlePage(c, h.PageConfig.Execute)
}

func (h *ConfigHandler) handleGetDetail(c *gin.Context) {
    platformhandler.BindAndHandle(c, h.GetConfigDetail.Execute)
}

func (h *ConfigHandler) handleRefreshCache(c *gin.Context) {
    platformhandler.HandleVoid(c, h.RefreshCache.Execute)
}
```

### 4.2 单文档原始显化方案

本 Skill 的输出形态固定为**单文档原始需求显化模式**。本地文档只负责把需求讲透，不承担任务编排、验收追踪、自动验收命令、执行证据或结果回写职责。

#### 4.2.1 文档定位

`_feat-doc/{YYYYMMDD}_{需求名称}/spec.md` 是上游原始输入，用于回答以下问题：

- 产品原始需求是什么
- 业务真正要解决什么问题
- 本次范围、非目标和边界在哪里
- SQL、领域、UseCase、Handler / API、前端分别需要如何设计
- 哪些假设、风险、依赖和开放问题需要后续确认

它不是：

- `tasks.md`
- `checklist.md`
- 自动验收脚本清单
- 执行过程状态表
- 证据归档索引

#### 4.2.2 唯一产物

AI 完成分析后，只允许默认输出一个文件：

- 目录：`_feat-doc/{YYYYMMDD}_{需求名称}/`
- 文件：`spec.md`

除非用户明确要求另行输出流程文档，否则禁止默认生成 `tasks.md`、`checklist.md` 或任何带 `REQ-ID`、`AC-ID`、`TASK-ID`、`AUTO-ID` 的执行态配套文档。

#### 4.2.3 字段口径

`spec.md` 文首建议保留以下信息：

| 字段 | 说明 |
| ---- | ---- |
| 生成时间 | 本文档生成日期 |
| 原始需求来源 | 产品需求描述或来源引用 |
| 文档编号 | 当前原始需求显化文档的唯一标识，如 `SPEC-20260429-member` |
| 优先级 | 需求优先级，如 `P0`、`P1` |
| 目标版本 | 计划进入的迭代或版本 |
| 影响模块 | 本次需求直接影响的模块范围 |
| 关联数据库对象 | 受影响 SQL 文件或表名 |
| 关联接口入口 | 关联接口前缀或入口 |
| 最后更新时间 | 最近一次文档更新时间 |

不得默认维护以下执行态字段：

- 需求状态
- 当前阶段
- 最后验证时间
- 最后验证结论
- 自动验收通过率
- 阻断项状态

#### 4.2.4 协同规则

1. `spec.md` 只做需求显化、技术边界说明、场景与规则展开，供后续 spec 工作流工具稳定消费。
2. 设计拆解、任务编排、流程归档、执行证据和验证结果由后续 spec 工作流工具或其他执行体系维护。
3. 当需求边界、业务规则、SQL 方案或领域划分变化时，应先回写对应 `spec.md`，再让后续 spec 工作流工具同步变更。
4. 不得把后续 spec 工作流工具中的任务状态、验证结果、证据路径反向写回 `spec.md`。
5. 当前需求显化体系默认产物为 `_feat-doc/*/spec.md`；该文件可作为后续工具或巡检任务的输入，但不得被其他 Skill 固定登记为知识文档依赖。

#### 4.2.5 最小落地标准

如果一次不需要输出非常完整的技术细节，最小也必须做到：

- 输出单份 `_feat-doc/*/spec.md`
- 写清背景、目标、范围、非目标
- 写清 SQL、领域、UseCase、**事务与一致性**、Handler / API、前端六类核心设计
- 写清待确认项、风险、依赖、开放问题
- 补充“供后续 spec 工作流工具使用的输入摘要”

做到这一层后，这份文档就可以作为后续 spec 工作流工具的上游输入。

## 5. 约束与规范

- 原始需求显化文档**必须保存至 `_feat-doc` 目录**，目录格式为 `{YYYYMMDD}_{需求名称}`，文件名固定为 `spec.md`；不得仅在对话中输出而不写入文件，不得保存至其他目录
- 开始分析前若需加载静态规范，必须先通过 `_prompts/doc/知识库索引.md` 按需装载相关知识文档；若需加载执行型 Skill，必须先通过 `_prompts/doc/Skill技能列表.md` 装载。默认优先关注 Go业务分层规范、Go架构规范、GoBFF规范、Go代码规范、Go数据库规范、Go事务规范、Go文件命名规范、Go选型规范、数据库表设计规范、Redis设计规范、API编码适配规范
- 涉及 Go 基础设施选型或方案设计时，必须遵守 `_prompts/rules/基础库优先使用规则.md`：先阅读 `_prompts/doc/基础库能力索引.md`，有候选库则阅读源码判断是否满足，满足则强制在 `spec.md` 中采用 gitee.com/hq_project/yomi-boot 对应能力库，禁止平行造轮子
- 在设计 SQL 前必须先查找项目内已有的 SQL 表结构设计相关文档或 Skill，并结合 `script/sql/` 目录中的存量 DDL 保持风格一致；本 Skill 不内置 SQL 字段规范，规范以项目已有文档为准
- 领域判断须依据 §3.2 的匹配度标准，优先归入已有领域；新领域必须给出充分的排除已有领域理由，不得凭空臆造业务边界
- 领域模型须区分 **Entity**（`internal/biz/domain/contract/{module}/` 对外领域对象）与 **Model**（`internal/biz/repo/db/{module}/` 包内私有 GORM 持久化模型，内嵌 `db.BaseModel`、包级声明表名常量并实现 `TableName()`）；Entity ↔ Model 映射收口在 `{module}_mapper.go`
- Service 层封装领域规则，不感知 HTTP、数据库、缓存等外部关注点；Repository 层通过 `db.Exec(ctx, r.DB)` 获取 GORM 执行器，使用链式 API 进行数据读写
- Repository 不承载业务校验，只执行 SQL 读写；常规 CRUD 使用 GORM 链式 API（`Create/Where/First/Find/Updates`），复杂查询回退 `db.Exec(ctx, r.DB).Raw(sql, args...)`
- UseCase 编排层是当前项目必需表达的章节：凡涉及后端接口、领域协作或 Input/Output 转换的需求，必须显式说明 UseCase 设计
- Handler 与 Service 的职责必须严格区分：Handler 只做 HTTP 协议适配，Service 只承载领域规则，UseCase 负责两者之间的编排与事务控制
- 每个数据交互流程组的步骤编号必须连续，不得跳步
- 不确定的字段设计需在文档中以 `⚠️ 待确认` 标记，并列出备选方案
- **入口编排对外**可用 GET 或 POST（[Go架构规范](../knowledge/go/Go架构规范.md) §3.6）；**微服务间**强制 POST（[微服务调用规范](../knowledge/api/微服务调用规范.md) §3）；Handler 的 `Routes(router)` 内注册**相对路径**；BFF 写接口经 `saga/` 提交 DTM；领域写接口仅 Action/Compensate 成对，禁止 Facade/Direct 回退
- **事务与一致性**（[Go事务规范](../knowledge/go/Go事务规范.md)）：**所有写数据动作**须先标明是否开启事务及与外部接口的传播关系，再确定事务边界；领域写经 `Guard`/`TxRunner`；Saga 写须同文件 `Execute`/`Compensate`、成对路由、补偿快照由 BFF 喂入；事务闭包仅含本地 DB；禁止假设外部 HTTP 加入本地 GORM 事务；禁止只写「需要事务」三字完事
- **对外文档描述完整 URL**：入口编排对外完整 URL = `router_prefix`（按端在配置中设置）+ `/v1/{资源}/{动作}`（`{资源}` 为单数名词；**示例**：如管理端/App）
- 响应须经 Encoder 适配（`MustRegister` + `Write*`/`BindAndHandle*`），不得设计裸对象返回；**具体 JSON 契约写本服务 Encoder，不写死预制实现字段**
- 涉及业务失败、错误码、参数校验、登录失效等需求，必须显式说明异常边界、关键失败语义与哨兵落点（`shared/error` / 库内 / `bizerr`）；前端消费方式以本服务 Encoder 契约为准
- 示例优先使用当前项目已有业务域与模块语义（**示例域**，以仓库现有域为准），避免使用与仓库无关的订单 / 优惠券类示例；**勿**把示例域名写成强制适用范围
- 文档内容只负责“需求显化”，不得内嵌任务拆解、验收追踪、自动验收设计、证据落点、执行时间等流程态字段
- 如需进入执行和验收阶段，应由后续 spec 工作流工具基于本 `spec.md` 继续做设计拆解与任务编排，不在本 Skill 输出范围内完成
