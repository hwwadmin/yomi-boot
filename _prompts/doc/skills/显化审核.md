# 显化审核

---

## 0. 基础信息

- **Skill 名称**: 显化审核
- **描述**: 对需求显化 Skill 产出的 `spec.md` 执行结构化审核，按问题级别（严重/警告/建议）逐项发现并输出标准 `audit.md` 审核稿；**写数据动作须先审事务决策（是否开事务/传播关系）再审边界**，缺决策或颠倒两步法按严重阻断，作为需求进入实现阶段前的质量门禁
- **作者**: zwei
- **创建日期**: 2026-06-04

---

## 1. 目标

- **做什么**：加载需求显化 Skill 产出的 `spec.md`（位于 `_feat-doc/{YYYYMMDD}_{需求名称}/` 目录下），按本 Skill 定义的审核维度、问题级别和输出格式执行结构化审核，生成同目录下的 `audit.md` 审核稿
- **为什么**：需求显化文档是后续实现、评审和验收的上游输入，必须在进入实现前确保其完整性、一致性和可实现性；本 Skill 通过统一的审核骨架和问题分级标准，消除不同审核者之间的口径偏差，输出可直接用于修正决策的结构化审核报告
- **不做什么**：
  - 不负责修改 `spec.md` 正文
  - 不负责执行代码实现或编译验证
  - 不负责维护任务状态、验收状态或执行证据
  - 不替代 `requirements-audit-agent` 的职责调度，本 Skill 是 Agent 加载并执行的规则集
  - 不把实现层细节（struct tag 拼写、类型装配、cron 精确值等）直接写成需求阻塞问题

## 3. 技术方案

### 3.1 执行流程概览

```text
加载 spec.md
  │
  ▼
阶段 1：文档完整性审核（§3.2）
  │  检查 spec 是否包含所有必选章节、元信息是否完整、章节编号是否连续
  │
  ▼
阶段 2：规范一致性审核（§3.3）
  │  逐项比对项目知识库规范，检查架构分层、DDL、API、事务、事件等口径
  │
  ▼
阶段 3：业务逻辑审核（§3.4）
  │  检查需求覆盖度、边界条件、异常路径、跨域交互
  │
  ▼
阶段 4：问题分级与编号（§3.5）
  │  将发现按严重/警告/建议三级分类并连续编号
  │
  ▼
阶段 5：生成 audit.md（§4 输出文档规范）
  │  按 §4 定义的标准骨架输出审核稿
  │
  ▼
阶段 6：自检（§6 验收标准）
```

### 3.2 阶段 1：文档完整性审核

**目标**：确保 `spec.md` 包含需求显化 Skill 要求的所有必选章节，元信息完整可用，章节编号连续无漂移。

**检查项**：

| 检查项 | 判定标准 | 缺失时的问题级别 |
| ------ | -------- | ---------------- |
| 头部元信息 | 包含需求名称、文档编号、创建日期、优先级、目标版本 | 警告 |
| SQL 表结构设计 | 含 DDL 与表意图说明；若无新增表，已说明原因 | 严重（缺失） / 警告（不完整） |
| 业务领域判断 | 含归属已有领域说明或新领域定义 | 严重 |
| 领域模型定义 | 含 Entity、Service 接口、Repository 接口、Model/Mapper 映射 | 严重 |
| 领域方法清单 | 含变更类型（新增/修改/删除）、是否写数据与设计原因 | 警告 |
| UseCase 编排层设计 | 含 UseCase 文件清单、I/O 类型；写数据动作事务列含「先决策（是否开事务/传播关系）→ 再边界」 | 严重（有写数据动作却缺决策） / 警告（纯读场景列不完整） |
| 事务与一致性设计 | 含 Step 1 写动作事务决策表（覆盖全部写数据动作）+ Step 2 边界；或无写数据已声明不适用；顺序未颠倒 | 严重（缺 Step 1 / 漏列写动作 / 颠倒顺序） / 警告（Step 2 边界不完整） |
| Handler 入口与 API 设计 | 含路由、请求结构、经 Encoder 的响应组装说明、错误码与哨兵落点；领域写须成对 Action/Compensate | 警告 |
| 数据交互流程 | 含域内/跨域交互时序；写操作交互组含 idempotency 进入点与闭包内外步骤 | 严重（有写路径却无事务步骤） / 建议（纯读缺时序） |
| 关键异常路径 | 含异常场景与失败语义（相对本服务 Encoder 契约） | 警告 |
| 前端需求转换 | 含页面/组件、状态管理、API 对接说明（如涉及前端） | 建议 |
| 章节序号连续性 | 全文章节编号是否连续递增、无跳号、无重复序号、无层级错乱 | 警告 |

**执行规则**：

- 逐项检查，缺章或少节如实记录
- 若 spec 明确声明某章节不适用并给出理由，视为合规
- 若章节存在但内容为占位语或空模板，按"不完整"记录

**章节序号校验**（独立于逐项检查的全量扫描）：

- 扫描全文标题层级（`#` / `##` / `###`），确认序号（如 §3.1 → §3.2 → §3.3）连续递增
- 检查是否存在跳号（§3.1 → §3.3）、重复序号（§3.2 出现两次）、序号断裂（§3 → §4.1 缺少 §3.x 定义）

### 3.3 阶段 2：规范一致性审核

**目标**：将 spec 中的设计决策与项目知识库规范逐项比对，发现口径偏差。

**审核维度与规范映射**：

| 审核维度 | 对照规范 | 关键检查点 |
| -------- | -------- | ---------- |
| 业务分层 | `Go业务分层规范.md` | 依赖方向、跨域编排归 usecase、同域编排归 service、usecase 互不依赖（详见规范 §3.3、§3.5、§3.6、§3.8、§5） |
| 项目架构 | `Go架构规范.md` | `internal/bootstrap` 手写装配、yomi-boot 插件化启动（`MustInitInfra` / `AddCustomPlugin`）、多入口编排结构（详见规范 §3.1、§3.3、§3.4、§3.8） |
| DDL 设计 | `数据库表设计规范.md` | 表名是否符合前缀约定；审计字段是否完整；雪花 ID 是否使用 `bigint`；索引命名是否规范 |
| Entity/Model 建模 | `Go数据库规范.md` | Entity 在 domain/contract；Model 包内私有 + `db.BaseModel`；Mapper 收口转换 |
| 领域建模 | `Go业务分层规范.md` | 默认贫血模型，规则归 domain/service；仅在复杂状态机/不变量场景按需充血；Entity 方法不访问 repo、不跨 Entity 编排（详见 §3.1.2、§3.4、§5） |
| Repository | `Go数据库规范.md` | 接口是否在 `internal/biz/repo/contract/{module}/` 定义、实现在 `internal/biz/repo/db/{module}/`；是否通过 `db.Exec(ctx, r.DB)` 获取 GORM 执行器；对外返回 Entity |
| 事务控制 | `Go事务规范.md` | 见下方「事务控制强制检查清单」；不得仅以「写了需要事务」判通过 |
| 跨域写 | `GoBFF规范.md`、`Go事务规范.md` | 跨域写是否由 BFF DTM Saga 编排；领域 Execute/Compensate 是否同文件；Action/Compensate 是否成对独立路由；补偿快照是否由 BFF 喂入；是否存在直调写/Facade 回退 |
| 业务幂等 | `微服务调用规范.md` | `bizId`/`bizSubId` 与 `yomi-boot/idempotency` 是否声明；是否与 DTM barrier 职责混淆 |
| API 设计 | `API编码适配规范.md` + `Go代码规范.md` + `Go异常规范.md` + `Go架构规范.md` + `微服务调用规范.md` | ① 是否 `MustRegister` Encoder；② 是否仅经 `Write*`/`BindAndHandle*` → Encoder；③ 是否实现完整 Encoder（含 `Parse`/`IsSuccess`）；④ 错误哨兵落点；⑤ 入口编排对外方法见架构 §3.6、微服务间 POST 见微服务调用规范 §3；**禁止以预制实现字段冒充强制契约** |
| 文件命名 | `Go文件命名规范.md` | 文件名是否遵循 `_handler`、`_usecase`、`_contract`、`_entity`、`_service`、`_repo`、`_model`、`_mapper` 等后缀约定 |
| 缓存策略 | `Redis设计规范.md` | 缓存键命名、TTL 设置、缓存更新策略是否符合规范 |

**执行规则**：

- 每个维度逐项比对，引用具体规范条目作为判定依据
- 若 spec 中的设计在规范中无明确条款，不得自行推断为"违规"
- 仅当存在规范明确要求且 spec 明确偏离时，才记录为问题
- 严禁把单个现有模块的实现样本当成项目唯一正确口径

**事务控制强制检查清单**（对照 `Go事务规范.md` §3.2–§3.8 与需求显化 §3.4.2 两步法；有写数据动作时逐项核对）：

| 检查点 | 缺失或违反时的级别 |
| ------ | ------------------ |
| **Step 1**：存在写数据动作但未输出事务决策表，或漏列任一写数据动作 | 严重 |
| **Step 1**：写数据动作未标明「是否开本地事务」或「与外部接口的传播关系」 | 严重 |
| **Step 1**：假设外部 HTTP/Redis 加入本服务 GORM 事务（错误传播模型） | 严重 |
| **顺序**：未完成 Step 1 决策就只写闭包/Saga 边界，或颠倒两步法 | 严重 |
| 决策为开事务，但未声明 `idempotency.Execute` + `TxRunner`，或仅写「需要事务」三字 | 严重 |
| 开事务动作未写清幂等 key / 闭包范围 / `Guard`+`TxRunner` 注入（Step 2） | 严重 |
| Saga 写缺同文件 `Compensate`，或 Action/Compensate 未成对独立路由 | 严重 |
| 存在 BFF 可直调领域写路由、`BindAndHandle` 写接口或 Facade/Direct 回退 | 严重 |
| Compensate 设计为领域再 HTTP 查询外服务获取补偿数据 | 严重 |
| 事务闭包设计含 Redis/HTTP 等非 DB IO，或闭包内组装 HTTP Output | 严重 |
| 跨服务写伪装为单库本地事务，未升格 BFF Saga | 严重 |
| 写数据但决策「不开事务」且无强理由 / 未说明失败一致性后果 | 严重 |
| Step 1 已决策，但 Step 2 未说明 `executeCtx` / Output 在闭包外 | 警告 |
| 本地开事务已声明，但未说明 `bizId`/`bizSubId` 幂等 key | 警告 |
| 纯查询 / 不写数据动作误包事务 | 建议 |

### 3.4 阶段 3：业务逻辑审核

**目标**：检查 spec 中的业务描述是否存在逻辑冲突、边界缺失、异常路径遗漏或跨域交互不清晰。

**检查维度**：

| 维度 | 检查内容 |
| ---- | -------- |
| 需求覆盖度 | spec 是否完整覆盖了原始需求中的所有功能点；需求显化中标记的 `⚠️ 待确认` 项是否已在 spec 中收敛 |
| 边界条件 | 关键业务动作是否明确了前置条件、后置结果和边界限制（如"已删除的记录不可操作"） |
| 状态流转 | 若涉及状态机，状态转换路径是否完整、是否存在不可达状态或死循环 |
| 异常路径 | 关键写操作是否覆盖了参数校验失败、业务规则冲突、依赖服务不可用等异常场景 |
| 跨域交互 | 跨领域调用方向是否符合架构分层约束；数据传递方式（同步调用/事件）是否明确 |
| 幂等性 | 写操作是否声明 `bizId`/`bizSubId` + `yomi-boot/idempotency`；是否与 DTM barrier 分工清晰（不得互相替代）；是否另有唯一索引/状态前置等业务层保护 |
| 数据一致性 | ① 是否先完成全部写数据动作的事务决策（开否 + 传播关系）再画边界；② 同服务多表写是否同一 `TxRunner` 闭包；③ 跨服务写是否 BFF Saga；④ 缓存与 DB 失效是否在事务外；⑤ 非 DB 副作用是否未混入领域 DB 闭包 |

**执行规则**：

- 仅审核 spec 中已写明的业务逻辑，不替 spec 补充遗漏
- 若 spec 未覆盖某异常路径，记录为"缺失"，不自行推断"应如何处理"
- 若前后描述存在语义冲突（如同一字段在两处含义不同），记录为"矛盾"

### 3.5 阶段 4：问题分级与编号

**目标**：将阶段 1–3 的所有发现统一分级、连续编号，为输出 audit.md 做准备。

**问题分级标准**：

| 级别 | 图标 | 判定标准 | 典型表现 |
| ---- | ---- | -------- | -------- |
| 严重问题 | 🔴 | 会直接阻断实现、验收或导致关键边界错误 | 关键章节缺失、前后逻辑冲突、核心输入输出约束缺失、架构分层违反项目强制约定；**写数据动作缺事务决策（是否开事务/传播关系）、颠倒两步法、缺完整边界/Saga/Compensate、可直调写、错误传播假设、闭包混 IO** |
| 警告问题 | 🟡 | 不一定阻断实现，但会导致理解偏差、方案分叉或后续返工 | 字段含义不清、规则不完整、默认值与现有口径不一致；**Step 1 已决策但 Step 2 的 `executeCtx`/幂等 key/闭包外 Output 写不清** |
| 建议项 | 🔵 | 不改变主流程，但影响表达精度、一致性或后续维护成本 | 描述不够精确、映射方式未说明、示例格式不统一、文件命名建议；**不写数据动作误包事务** |

**编号规则**：

- 审核稿内所有问题连续编号，格式为「发现 1」「发现 2」「发现 3」……
- 同一编号不得跨级别复用
- 编号顺序强制按严重 → 警告 → 建议排列，同一级别内按发现顺序编号

**常见误报过滤**：

在定级前，必须按以下规则过滤误报，避免把实现细节或项目统一约定误判为需求问题。以下规则同时约束 `audit.md` 的输出内容：

| 误报来源 | 典型误判方式 | 正确处理 |
| -------- | ------------ | -------- |
| 审核层级错位 | 把 Topic 名称、Kafka 容器工厂、消费者类名、`cron` 精确值、驱动层字段适配配置、序列化注册方式等实现装配细节直接写成需求阻塞问题 | 先判断是否已影响业务语义、职责边界或关键输入输出；若只是实现补全项，降级为"实现注意点"或不写入主问题 |
| 将单个实现样本当成规范 | 因某个现有模块使用了某种命名、删除方式或脱敏策略，就直接认定 spec 偏差 | 必须先核对项目知识库规范；若规范未覆盖，至少确认是跨模块复用的稳定模式，否则只能作为参考 |
| 忽略项目统一约定 | 将模块命名规则、统一审计字段口径、存储模型公共字段、ID 对外输出为字符串等项目约定误判为违规 | 先回查对应规范；若规范已允许或要求该写法，视为合规 |
| 把"可补充说明"写成"存在矛盾" | spec 未明确某个实现口径，就直接下结论为"设计冲突" | 只有当前后语义互斥、关键流程断裂或输入输出约束不完整时，才定性为问题；否则写成"口径待明确" |
| 以实现可编译性替代需求审核 | 围绕代码段导包、语法、空格、struct tag 组合、框架使用习惯等实现性问题展开审核 | 只有已改变业务意义、异常口径或边界条件时才保留；纯实现细节不属于审核主问题 |
| 未经授权做代码对照 | 在用户未要求结合现有代码审核时，把"现有代码与 spec 不一致"当作审核主结论 | 默认只审核 spec 本身及其引用规范；只有用户明确要求结合现有代码一起审核时，才展开代码模式对照 |
| 残留模板痕迹 | 输出中保留与本次审核无关的模板占位语、空表格或无效示例 | 定稿前删除所有未使用的章节标题、占位语和示例内容 |

## 5. 约束与规范

### 5.1 行为约束

- 审核对象必须是需求显化 Skill 产出的 `spec.md`，不得自行扩大审核范围
- 审核依据优先使用项目知识库规范；规范未覆盖的领域，以 spec 自身语义一致性为准
- 涉及 Go 基础设施选型时，必须遵守 `_prompts/rules/基础库优先使用规则.md`：对照 `_prompts/doc/基础库能力索引.md`，将「已有基础库可满足却平行造轮子 / 重复引入同类第三方库」列为问题
- 所有问题必须有 spec 中的具体位置引用，不得使用"整体感觉""可能有问题"等模糊表述
- 问题分级必须对照 §3.5 的分级标准，不得随意升格或降格
- 修正建议必须可操作，不得只写"请修改"或"建议优化"

### 5.2 格式约束

- 输出路径固定为 `_feat-doc/{YYYYMMDD}_{需求名称}/audit.md`
- 章节结构必须包含四个必选章节（审核总评、逐项审核发现、审核发现汇总与修正建议、审核结论）
- 问题编号在整份审核稿内连续且唯一
- 汇总表编号与逐项发现编号一一对应
- 标题层级清晰、编号连续，无未删除的模板分支

### 5.3 禁止项

- 禁止在 spec 目录之外生成 audit.md
- 禁止修改 spec.md 原文
- 禁止以"建议参考某现有模块"替代具体修正建议
- 禁止在审核结论中给出"可以直接进入实现"的结论但正文中存在未解决的严重问题（含严重事务问题）
- 禁止把「UseCase 表写了需要事务」或「直接画了闭包」视为事务设计已通过；必须先核对 Step 1（全部写数据动作的开否 + 传播关系），再核对 Step 2 边界
- 禁止把 spec 中标注的 `⚠️ 待确认` 项直接当作审核问题：应先判断 spec 是否已就该待确认项做出合理假设并完成设计闭环；若 spec 已给出假设与设计，不得仅因标记过 `⚠️ 待确认` 就升格为问题；若 spec 仅保留标记而未给出任何设计闭环，应记录为"需求收敛不完整"（建议级别）
