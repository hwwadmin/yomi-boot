# Redis设计规范

---

## 0. 文档信息
- **文档名称**: Redis设计规范
- **描述**: 从 Redis 本身约束 Key、类型、过期、缓存一致性、锁与限流，不绑定语言、框架或业务语义。
- **作者**: zwei
- **创建日期**: 2026-04-15
- **修订日期**: 2026-11-04（改为概念层规范，不绑定项目）

---

## 1. 文档定位

- **用途**：回答 Redis 设计上的问题：它承担什么角色、Key 怎么分层、用哪种结构、何时过期、如何与源数据一致、锁和限流怎样才算正确。
- **边界**：不规定客户端库、部署形态、集群拓扑、监控或运维参数；不规定业务字段名、错误码或配置项。
- **适用对象**：任何把 Redis 当作缓存、协作状态或计数/限流手段来设计或评审的场景。

Redis 在此指：**内存中的键值存储，用 Key 寻址、用类型表达结构、用过期与淘汰管理生命周期**。它是加速与协作手段，不是系统的核心事实来源。

---

## 2. Redis 做什么、不做什么

- **适合**：可重建的读加速、短时会话/凭证、跨实例互斥、窗口计数与限流、有界的集合与排序。
- **不适合**：不可重建的核心业务状态、需要与磁盘库同一事务提交的写、无界增长的日志或大对象仓库。
- 同一场景下，命中、回源、失效、刷新必须是同一套策略，不能多入口各写各的。
- 用了锁只说明做了互斥，不说明缓存设计合理。

---

## 3. Key

Key 是寻址契约。必须能从 Key 读出「谁的、哪一类、哪一条」，并便于按前缀管理。

```text
{命名空间}:{用途}:{对象}:{标识}
```

| 规则 | 说明 |
| ---- | ---- |
| 冒号分层 | 从稳到变：命名空间 → 用途 → 对象 → 实例标识 |
| 小写 | 避免大小写被视为不同 Key |
| 字符集 | 字母、数字、下划线、冒号；禁止空格、中文及其他符号 |
| 长度 | 控制在存储与运维可接受范围内，避免把大段业务内容塞进 Key |
| 标识稳定 | 实例段用稳定 ID，不用易变的展示名或可变排序字段 |

同类数据必须共用同一模式。禁止同一对象用两套前缀或两套分隔习惯。

---

## 4. 数据结构

按「要表达的关系」选类型，不按习惯选。

| 类型 | 表达的关系 | 适合 | 不适合 |
| ---- | ---------- | ---- | ------ |
| String | 一个 Key 对应一个值 | 整包快照、计数、短凭证 | 经常只改其中几个字段的大对象 |
| Hash | 一个对象下多个字段 | 稳定字段集、局部更新 | 字段集不稳定或字段值极大 |
| List | 有序序列 | 有界队列、最近 N 条 | 需要按成员随机删除或去重 |
| Set | 唯一、无序的成员集合 | 去重、标签、成员判定 | 需要顺序或分值 |
| Sorted Set | 唯一成员 + 分值排序 | 排行、延时窗口、按时间滑动 | 不需要顺序的简单去重 |

一条原则：**类型要能覆盖读写方式**。需要按字段改就用 Hash；需要窗口淘汰就用 List 或带分值的 Sorted Set；只是一个可过期的值就用 String。

---

## 5. 过期与容量

过期（TTL）是生命周期决策，不是装饰。

- 能从源数据重建、允许丢失、或本身有时效的数据：**应设 TTL**，让存储自己回收。
- 必须长期保留的少量状态：可以不设 TTL，但必须有明确的更新或删除路径，禁止无限积压。
- TTL 长度由「过期后可接受的不一致窗口」决定，不按类型套固定分钟数。
- 同类 Key 的 TTL、刷新、失效规则必须一致；禁止同一模式有的永不过期、有的极短过期且无说明。

---

## 6. 当作缓存时的一致性

当 Redis 是源数据的副本时：

| 策略 | 含义 | 适用 |
| ---- | ---- | ---- |
| 旁路缓存 | 先写源数据，再删（或失效）缓存，读未命中再回源 | 读多写少 |
| 写穿 | 同一写路径同时更新源数据与缓存 | 写入口唯一且可控 |
| 异步刷新 | 源数据提交后异步重建缓存 | 可接受短暂旧值 |

- 写后必须有对应的失效或刷新，不能只写入源数据、指望 TTL 自己收敛。
- 不存在的数据可短 TTL 缓存空值，避免穿透。
- 热点 Key 失效时要防止同时打穿到源（互斥重建或单飞）。
- 大批量失效要限速，避免雪崩。
- 缓存与源数据不在同一事务里；接受「源已提交、缓存稍后一致」。

---

## 7. 锁

锁只解决**跨实例互斥**，不解决业务正确性。

- 没有跨实例竞争就不要加锁。
- 加锁必须带过期，避免持有者崩溃后死锁。
- 解锁必须核验持有者身份，禁止删掉别人的锁。
- 锁的粒度与持有时间要对齐临界区：范围过大或持有过长等于把并发变成串行。
- 需要可重入、续期、fencing 时，用完整的锁协议，不要只靠一个无校验的 `SET`。

---

## 8. 限流

限流是窗口内的计数与拒绝，必须原子。

- 用 Redis 原子命令或脚本完成「读窗口 + 计数 + 判定」，禁止先读后写下的竞态。
- 窗口时钟以 Redis 服务端时间为准，避免多实例本地时钟漂移。
- Key 按限流维度拆开（调用方、资源、实例等），维度必须在设计里写清。
- Redis 不可用时的策略必须显式选择：放行（可用性优先）或拒绝（保护优先），不能默默换一套客户端再计一次。

---

## 9. 值

- 秘密、口令、未哈希的凭证禁止以明文写入。
- 大对象要拆分、压缩或只缓存热点字段；禁止把无界 JSON / 二进制整包塞进单个 Key。
- 值的序列化格式在同一类 Key 内保持一致。
