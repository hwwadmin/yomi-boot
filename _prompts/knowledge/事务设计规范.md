# 事务设计规范

---

## 0. 文档信息

- **描述**: 从事务概念本身约束写路径：要不要开事务、边界画在哪、事务内放什么/放多久。
- **作者**: zwei
- **创建日期**: 2026-06-17

---

## 1. 文档定位

- **用途**：回答写路径上的三个问题：要不要开事务、边界画在哪、事务内放什么/放多久。
- **边界**：不规定具体语言、框架、编排形态或中间件选型。本文只约束「事务」作为一致性手段时必须满足的判定与边界。
- **适用对象**：任何需要把一组写操作当成同一成败单元来设计或评审的场景。

事务在此指：**同一资源管理器内、要么全部生效要么全部消失的一组写**。它保护的是业务不变量，不是「开了连接」或「包了一层 API」。

---

## 2. 要不要开事务

每个写动作先判定，再说边界。不得默认「凡写必开事务」。

```text
写动作
├─ 只读？ → 不开（除非需要同一快照下的一致性读）
├─ 单次写已被存储引擎保证原子？ → 通常不开
│    └─ 「先读再判断再写」依赖读到的值 → 开，或把判断下推为条件更新 / 版本 / 唯一约束
├─ 同一资源上多条写，失败必须一起消失？ → 开
└─ 跨越不同资源 / 不同服务？ → 单边事务管不了另一边；能接受最终一致就用重试、对账、事件；必须协调回滚再用补偿型流程
```

判定结果要能一句话说清：**这个事务保护哪条业务不变量，失败时哪些写必须一起消失。** 说不清就先不要开。

| 场景 | 建议 |
| ---- | ---- |
| 纯查询 | 不开 |
| 单次插入 / 更新 / 删除 | 通常不开 |
| 单行条件更新（带版本、状态等谓词） | 通常不开 |
| 先读再判断再写 | 开，或把判断下推到存储 |
| 同一库内多对象写，失败必须一起消失 | 开 |
| 跨服务 / 跨资源写 | 不用单边事务去覆盖另一边 |

不开事务的写路径必须能说清失败后果（重试、对账、状态字段、唯一约束）。

---

## 3. 边界画在哪

从业务不变量倒推，不从存储对象、方法或分层倒推。按顺序回答：

1. **失败时哪些写必须一起消失？** 得到最小原子集，这就是边界。
2. **哪些读参与写决策？** 必须与写同事务，或把判断下推到存储。
3. **哪些可以晚一点、差一点？** 缓存、通知、统计、允许异步的审计移出边界。

开启点由「谁拥有这个原子动作」决定，不按分层强制。谁最清楚「失败时必须一起消失的集合」，谁就是开启点。不要在多个地方重复开启同一边界。

跨资源、跨进程的调用不能假设加入本侧事务。各侧各自画本地边界；需要协调回滚时用补偿，而不是把远端写塞进本侧事务。

必须与业务写同生共死的辅助记录（如幂等凭证）放进同一事务；不参与该事务资源的锁、缓存、结果副本不进事务。

---

## 4. 事务内放什么、放多久

事务内只放**本事务资源上的读写**和必要的轻量计算。从开启到提交应短、可预期；出现长时间事务必须说明锁范围与分批 / 续跑方式。

**禁止放进事务**（这些操作不随该事务回滚，只会拉长持锁）：

| 操作 | 替代 |
| ---- | ---- |
| 远程调用 | 事务外调用；失败用补偿 |
| 缓存 | 提交后再更新 / 删除 |
| 消息投递 | 与业务写同资源落库后再投递，或接受提交后发送 |
| 文件 / 对象存储 | 先落库后异步，或设计补偿 |
| 对外响应组装 | 事务外组装 |
| 等待 / 睡眠 / 事务内重试循环 | 事务外重试整个单元 |

一次事务只承载**一次**业务状态迁移。多个独立动作拆成多个短事务；长流程用状态机，事务只包单步；批量写分批提交、记录进度、失败可续跑。

落地要求（与语言、框架无关）：

1. 经明确的事务入口开启与结束，禁止在业务路径上散落裸提交 / 回滚。
2. 调用链已处于同一事务中则加入并复用，提交点归最外层；禁止静默再开一个会独立提交的事务。确需独立提交时必须显式声明：外层回滚不会撤销它，它的失败也不会回滚外层。
3. 事务身份随调用上下文传递，不把连接 / 会话对象当作业务参数层层下传。
4. 事务回调内使用已绑定该事务的上下文访问资源；对外输出在事务外组装。
5. 回调失败即回滚。超时受调用方截止时间约束，禁止另起不受截止时间约束的事务（显式独立事务除外，且必须自带超时）。
