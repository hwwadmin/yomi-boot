# Go基础库检查规范

---

## 0. 文档信息
- **文档名称**: Go基础库检查规范
- **描述**: 定义 gitee.com/hq_project/yomi-boot/ 下各基础库的检查标准，覆盖设计合理性、逻辑正确性、编码质量、注释规范、代码风格统一、优化空间、重复与简化、封装边界八个检查维度，作为逐库执行检查的规范基线。
- **作者**: zwei
- **创建日期**: 2026-06-26

---

## 1. 文档定位

- **用途**：约束 gitee.com/hq_project/yomi-boot/ 下每个基础库（每个子目录为一个库）的静态检查行为，提供统一的检查维度、检查流程、问题分级与输出要求，确保检查过程规范一致、结果可追溯。
- **边界**：不覆盖业务工程 services 下业务服务的分层架构、数据访问、事务等业务维度检查（见 [代码巡检](../skills/代码巡检.md)）；不覆盖 Redis 设计、数据库表设计等专项检查（见对应知识文档）；不替代 golangci-lint 等自动工具的静态分析结果，而是在此之上做人工审查层级的检查。
- **适用对象**：本仓库（`module gitee.com/hq_project/yomi-boot`）下所有基础库的 Code Review、重构评审、定期治理与新人培训场景。

## 2. 适用范围与关联

### 2.1 适用范围

- 适用于本仓库下每个子目录所代表的基础库。
- 不适用于业务工程中的 BFF / 领域业务代码（那些在业务仓巡检）。
- 检查粒度为一个库一次，禁止跨库混检。

- 首次执行基础库检查前，先通读 §3 全部检查维度，理解每个维度的检查意图。
- 执行检查时，按 §3.2 检查流程操作，以目标库为单位逐项覆盖八个维度。

- 需要结合其他规范做判断时，通过关联文档路径加载对应知识文档。

## 3. 技术方案

### 3.1 检查维度总览

对每个基础库从以下八个维度进行检查：

| 维度 | 关注核心 | 典型问题 |
| ---- | -------- | -------- |
| 设计合理性 | API 边界、职责内聚、抽象层次、扩展性 | 接口粒度过粗/过细、职责跨越多个领域、抽象泄漏实现细节 |
| 逻辑正确性 | 控制流、边界条件、错误处理、并发安全 | 空指针解引用、资源泄漏、竞态条件、错误被静默吞噬 |
| 编码质量 | Go 惯用写法、错误传播、资源关闭、测试覆盖 | 错误未检查、defer 未用、命名不一致、缺少编译期断言 |
| 注释规范 | 文件头注释、导出类型/函数 godoc、接口文档 | 缺少导出注释、注释与代码不一致、godoc 格式不规范 |
| 代码风格统一 | 命名一致性、格式化、缩写词约定、函数组织 | 同类命名混用、未使用 gofmt、缩写词大小写不统一 |
| 优化空间 | 性能、内存分配、序列化、并发利用 | 不必要的内存分配、重复计算、锁竞争、反射滥用 |
| 重复与简化 | 重复代码、冗余抽象、可合并逻辑 | 同类函数多处复制、可有可无的中间层、过度提取的接口 |
| 封装边界 | 对外暴露面、依赖方向、内聚程度 | 内部实现被导出、包依赖方向逆流、上帝接口/上帝结构体 |

### 3.2 检查流程

每个基础库的检查必须按以下步骤顺序执行：

```text
开始
  ↓
1. 选定目标库（如 gitee.com/hq_project/yomi-boot/component/core/config/）
  ↓
2. 加载关联知识文档，确认该库的职责边界与规范基线
  ↓
3. 按八个维度逐项检查（§3.3–§3.10），每个维度产出检查记录
  ↓
4. 汇总问题清单，标注问题级别（§3.11）
  ↓
5. 输出检查报告（§3.12）
  ↓
6. （可选）在用户授权下修复问题
  ↓
结束
```

规则：

- 每次只检查一个基础库，不得在一次检查中覆盖多个库。
- 每个维度至少产出一条检查结论（可以是"未发现问题"），不得跳过任何维度。
- 发现问题时须记录到具体文件及行号，不得仅笼统描述。
- 流程步骤 2 仅在首次检查或规范基线发生变更时需要重新加载；同一库被连续检查时可复用已加载的规范内容。

### 3.3 设计合理性检查

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 职责边界 | 该库的公开 API 是否与 Go架构规范中定义的模块职责一致 | 对照 [Go架构规范](./Go架构规范.md) §3.3 gitee.com/hq_project/yomi-boot 模块职责表；生命周期框架为 `plugin/`，内置实现与 YAML 绑定为 `plugin/builtin/{lib}`，插件清单与配置段注册表为 `plugin/registry`；`boot/bootstrap` 只做初始化，`boot/server` 只做 HTTP 装配；组件库不得含 `plugin/` 子包；运行时 `Config` 不得含 `mapstructure`；`SectionKey`/`BootConfig`/`ConfigSection` 仅允许在 `plugin/builtin/{lib}`，例外：`oss` |
| 接口粒度 | 对外接口是否提供了恰当的抽象级别，是否暴露了实现细节 | 接口方法数量是否合理（通常 3–8 个方法）；接口参数类型是否为领域概念而非底层实现类型 |
| 抽象层次 | 是否引入了不必要的间接层，或者缺少应有的抽象 | 是否存在仅转发调用、无任何逻辑增强的包装函数；是否需要接口来支持多种实现 |
| 扩展性 | 新增功能是否需要修改当前库的代码 | 是否需要"开闭原则"判断：当前库是否允许通过新增实现（而非修改现有代码）来扩展能力 |
| 依赖方向 | 该库的 import 依赖是否合理，是否存在反向依赖或循环依赖 | gitee.com/hq_project/yomi-boot 内库是否依赖了业务代码；是否依赖了其他不相关的 gitee.com/hq_project/yomi-boot 库 |
| 零值可用 | 该库的核心结构体是否设计为零值可用，或者显式要求通过构造函数创建 | 导出的结构体被直接零值使用时是否会导致 panic 或静默错误 |

### 3.4 逻辑正确性检查

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 空指针/空值 | 是否存在对可能为 nil 的指针、接口、map、channel 的解引用 | 函数参数未判空即使用；map 未 make 即写入；channel 未初始化即发送 |
| 边界条件 | 循环、递归、切片操作是否正确处理边界值 | 空切片、nil 切片、长度为零的输入；索引越界；递归缺少终止条件 |
| 错误处理 | 错误是否被正确处理，是否误吞或误判 | `if err != nil { return nil }` 吞掉错误信息；`err == io.EOF` 判断不当 |
| 资源泄漏 | 文件、网络连接、goroutine 是否正确释放和关闭 | 打开的资源未 `defer Close()`；goroutine 启动后无退出机制 |
| 并发安全 | 共享数据是否有竞态保护，锁的粒度是否合理 | 多个 goroutine 读写同一变量未加锁；在锁内调用了可能死锁的外部回调 |
| 类型断言 | 类型断言是否进行了安全检查和 fallback | `x.(Type)` 未使用 `x, ok := x.(Type)` 双返回值形式 |
| 零值语义 | 是否依赖了 Go 类型的零值语义而实际行为不符合预期 | `bool` 零值为 `false` 但业务含义可能是"未设置"；`nil` 切片和空切片行为差异 |

### 3.5 编码质量检查

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 错误传播 | 错误是否被正确包装和传播，而非静默丢弃 | 使用 `fmt.Errorf("xxx: %w", err)` 包装错误，而非 `return nil` 吞掉错误 |
| defer 使用 | 资源释放、解锁、计时等是否使用 defer 保证执行 | `Lock()` 后未跟 `defer Unlock()`；文件打开后未 defer close |
| 命名规范 | 导出类型、函数、常量命名是否符合 Go 约定 | 使用 CamelCase 而非 snake_case；缩写词一致性（`HTTP` 而非 `Http`） |
| 编译期校验 | 实现接口的结构体是否添加编译期断言 | `var _ Interface = (*Impl)(nil)` 是否存在于所有接口实现处 |
| 测试覆盖 | 是否存在单元测试，测试是否覆盖主要路径和边界 | 核心函数和导出 API 是否有测试；测试是否包含正常路径和异常路径 |
| 包文档 | 包是否有 `doc.go` 或文件头 `// Package xxx` 注释 | 每个包至少一个文件包含包注释 |
| 导出最小化 | 是否将不必要的内容导出 | 内部辅助函数、不应对外暴露的类型是否被导出（首字母大写） |
| 依赖管理 | `go.mod` 中的依赖是否精确，是否存在未使用的依赖 | `go mod tidy` 后是否有残留；是否依赖了实际未使用的间接依赖 |

### 3.6 注释规范检查

注释规范应严格遵循 [Go注释规范](./Go注释规范.md)，从以下维度进行检查：

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 注释语言 | 注释是否使用中文，是否出现英文注释或中英混写 | 除 Go 指令注释（`//go:embed`、`//nolint`）外，所有注释必须为中文 |
| 注释格式 | 注释是否使用 `//` 双斜线格式，是否紧贴被注元素上方不空行 | 声明级符号统一使用 `// 注释`；注释与被注元素之间不空行 |
| 文件头注释 | 每个源文件是否有符合规范的文件头注释，职责描述是否准确 | 包声明 `package xxx` 前必须有注释块，使用 `// Package xxx ...` 格式描述包的整体职责；至少一个文件保留包注释 |
| 类型注释 | 所有导出类型（结构体、接口、类型别名）是否有注释 | 以 `// 类型名 描述` 格式写在类型声明上方；导出字段在名称不自解释时需行尾注释 |
| 函数/方法注释 | 所有函数（不区分导出/非导出）是否有 `// 函数名 功能描述` 格式的注释 | 以函数名开头，描述契约（参数语义、返回值含义、副作用、nil 等特殊约定）；非导出函数与导出函数同等对待 |
| 接口声明注释 | 接口本身及接口方法是否有注释，是否符合"契约聚焦"原则 | 接口必须有注释；接口中每个方法建议有注释，描述"做什么"而非"怎么做"，不暴露实现细节 |
| 常量注释 | 同组常量是否有块前注释，行尾注释是否必要 | 同组常量使用 const 块 + 块前注释，不重复逐行注释；常量名无法自解释时在行尾补充简短说明 |
| 关键步骤注释 | 方法体内关键业务步骤、边界判断是否有行内注释 | 关键步骤、复杂逻辑、语义不直观的分支条件上方需有行内注释；自解释的标准库调用不需要 |
| 特殊标记 | TODO/FIXME/HACK 是否附带原因或期限，nolint 是否附带忽略原因 | 禁止裸写无上下文的 TODO/FIXME；`//nolint` 必须附带注释说明忽略原因 |
| 注释准确性 | 注释内容与实际代码行为是否一致 | 检查注释描述的逻辑是否与代码实现匹配；是否存在已过时的注释 |
| 作者信息 | 作者标识是否仅出现在文件头注释中 | 函数/方法级注释和 type/interface 声明级注释不得出现 `@author` 等作者标识 |
| 禁止冗余 | 是否存在为自解释代码添加的冗余注释 | 禁止为显而易见的代码（如 `return nil`、简单字段赋值）添加注释；禁止用注释掩盖混乱结构 |

### 3.7 代码风格统一检查

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 命名一致性 | 同类概念是否在库内使用统一命名 | 同类对象命名模式一致（如都用 Client 而非混用 Client/Conn/Proxy）；同一语义字段在不同结构体中命名一致 |
| 格式化规范 | 代码是否经过 gofmt/goimports 格式化 | 缩进、括号位置、空格、import 分组是否符合 gofmt 标准输出 |
| 缩写词约定 | 缩写词大小写风格是否统一 | HTTP/https、ID/Id、URL/Url 等缩写词在导出/非导出场景下大小写一致 |
| 错误处理模式 | 错误处理风格是否统一 | 同一库内错误传播方式一致（统一使用 `%w` 包装或统一自定义错误类型）；错误变量命名风格一致 |
| 函数组织 | 函数/方法的组织顺序是否有一致规则 | 是否按构造函数→导出方法→非导出方法的顺序排列；接收器方法是否集中在一起 |
| Go 惯用法 | 代码是否符合 Go 语言惯用法 | 包名简洁小写无下划线；getter 无 `Get` 前缀；接口名合理使用 `-er` 后缀；接收器命名遵循单字母/双字母缩写惯例 |

### 3.8 优化空间检查

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 内存分配 | 是否存在可避免的堆分配 | 热点路径中是否有不必要的 `fmt.Sprintf`、`string([]byte)` 转换、装箱操作 |
| 重复计算 | 是否存在可缓存的计算结果 | 循环内重复计算不变量；每次调用都重新计算的开销且结果可缓存 |
| 序列化开销 | JSON 序列化/反序化是否可优化 | 是否可使用 `json.Marshaler`/`json.Unmarshaler` 自定义实现减少中间分配 |
| 并发利用 | 是否可引入并发处理提升吞吐 | 独立任务是否可并行执行；是否需要 worker pool 控制并发度 |
| 反射使用 | 反射是否可被泛型或代码生成替代 | `reflect` 包使用场景是否符合 Go1.18+ 可用泛型替代的原则 |
| 锁粒度 | 锁的范围是否可缩小 | 大范围锁是否可拆分为细粒度锁或读写锁 |
| 字符串拼接 | 大量字符串拼接是否使用了高效方式 | 循环内 `+=` 拼接是否可改为 `strings.Builder` |

### 3.9 重复与简化检查

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 重复代码 | 同一库内是否存在结构相同、仅参数不同的重复代码 | 相同逻辑在三处以上出现时，是否可提取为通用函数 |
| 样板代码 | 是否存在可被 Go 1.18+ 泛型消除的重复实现 | 为不同类型重复实现相同的 `Find`、`Map`、`Filter` 等操作 |
| 冗余包装 | 是否存在仅转发调用、无额外逻辑的包装函数 | 函数体仅一行调用另一个同名函数且无参数转换 |
| 可合并逻辑 | 多个相似处理分支是否可合并 | 多个 `if`/`switch` 分支执行相似操作时是否可用表驱动或策略模式 |
| 过度提取 | 是否提取了只有一个实现、且短期内无第二个实现计划的接口 | 接口仅有一个实现且无 mock 或替换需求时，接口是否增加了理解成本 |
| 不必要的抽象 | 接口定义是否导致了调用方和实现方双方都需要 import 同一包 | 接口定义在消费者包中而非实现者包中是否合理 |

### 3.10 封装边界检查

| 检查项 | 检查内容 | 判断口径 |
| ------ | -------- | -------- |
| 导出面过大 | 是否暴露了不应对外开放的类型和函数 | 仅在本库内部使用的辅助类型、转换函数是否被导出 |
| 内部泄漏 | 内部实现细节是否泄漏到了外部 API | 返回类型是否为内部结构体、是否暴露了底层实现（如 `*redis.Client`） |
| 构造函数 | 需要初始化才能使用的结构体是否提供了构造函数 `NewXxx` | 导出结构体未提供构造函数，或构造函数未做必要的初始化 |
| 包依赖 | 该库是否依赖了不应依赖的其他 gitee.com/hq_project/yomi-boot 库 | 基础设施层库是否依赖了更上层的库；是否存在隐式耦合 |
| 全局状态 | 是否使用了包级可变全局变量，是否影响测试和并发安全 | `var` 包级变量在测试间是否可隔离；并发访问是否有保护 |
| 接口内聚 | 接口是否只包含高度相关的功能 | 一个接口是否同时包含"读写配置"和"发送邮件"等无关职责 |
| 配置泄漏 | 是否直接读取环境变量或配置文件，而非通过参数注入 | 库内部是否直接调用 `os.Getenv` 或读取 `config` 包 |

### 3.11 问题分级

| 级别 | 标签 | 说明 | 示例 |
| ---- | ---- | ---- | ---- |
| 🔴 严重 | bug / design-flaw | 必定导致运行时错误或从根本上违背设计原则 | 空指针解引用、并发写无锁、需要 Close 但未导出 Close 方法 |
| 🟡 警告 | logic-warning / code-smell | 在特定输入下可能出错，或可维护性明显受损害 | 边界条件未处理、错误被静默吞掉、过度封装导致调用复杂 |
| 🔵 建议 | optimization / simplification | 不影响正确性但可改进的部分 | 可提取公共函数、可减小锁粒度、可添加测试覆盖 |

### 3.12 输出要求

检查完成后必须输出以下内容：

- **目标库**：本次检查的基础库名称与路径
- **检查依据**：加载的关联知识文档列表
- **各维度检查结论**：每个维度的检查结果，格式为 `维度名称：[未发现问题 / 发现 N 个问题]`
- **问题清单**（有问题的维度）：
  - 问题编号
  - 问题级别
  - 问题维度
  - 文件路径与行号
  - 问题描述
  - 判断依据（引用的规范条款或逻辑推理）
  - 修复建议
- **人工确认项**（可选）：需要人工确认的边界问题或不确定项
- **总体评价**：该库的健康度评级（健康 / 轻微问题 / 需重构）

## 4. 检查清单

执行每个基础库的检查前，请确认：

- [ ] 已明确本次检查的目标库，只检查该库不混入其他库的代码
- [ ] 已加载该库职责对应的关联知识文档，确认职责边界
- [ ] 已按八个维度（设计合理性、逻辑正确性、编码质量、注释规范、代码风格统一、优化空间、重复与简化、封装边界）逐项覆盖检查
- [ ] 每个维度均产出了检查结论，未跳过任何维度
- [ ] 已记录发现问题的文件路径与行号，而非笼统描述
- [ ] 已按问题分级标准为每个问题标注级别
- [ ] 已给出修复建议，而非仅指出问题
- [ ] 检查报告中包含了目标库、检查依据、各维度结论、问题清单、总体评价
- [ ] 声明了需要人工判断的边界问题或不确定项

## 5. 禁止项

- 禁止在一次检查中同时混检多个 gitee.com/hq_project/yomi-boot 基础库。
- 禁止跳过任何检查维度（每个维度必须产出明确结论）。
- 禁止在问题描述中只写"有问题"而不指明具体文件、行号和判断依据。
- 禁止将推测写为确认事实；不确定的问题必须标注为"待确认"。
- 禁止在没有用户授权的情况下修复不在本次检查范围内的问题。
- 禁止在检查报告中遗漏对全局状态、并发安全性、导出面的判断。
- 禁止以"这段代码一直如此"为由放过明显问题。
- 禁止直接复制其他基础库的检查结论作为当前库的检查结果。
