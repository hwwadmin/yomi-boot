# 微服务调用规范

---

## 0. 文档信息
- **文档名称**: 微服务调用规范
- **描述**: 定义 BFF 调用领域微服务时的 HTTP 契约：强制 POST/JSON、Header 链路 ID、请求/响应信封（bizId、bizSubId）、业务幂等与 DTM 边界。

- **创建日期**: 2026-06-17
- **修订日期**: 2026-07-21（适用范围改为平台抽象服务角色；示例路径改 `{resource}`）

## 1. 文档定位

- **用途**：约束 **入口编排（BFF）→ 领域服务**、**DTM → 领域分支** 的内部 HTTP 调用格式；与面向前端的 [API编码适配规范](./API编码适配规范.md) 区分。
- **权威定位**：微服务间契约（POST/JSON、Header 链路 ID、信封、`bizId`/`bizSubId`、业务幂等、`gitee.com/hq_project/yomi-boot/component/common/idempotency`）以**本文 §3 为唯一权威**；其他 Go 规范仅引用本章，不重复展开。
- **边界**：
  - **本规范**：微服务间调用（BFF `saga/` 经 DTM 回调领域 `/internal/v1/...` Action/Compensate；**领域 client** 仅直调领域**读**接口）。
  - **API编码适配规范**：HTTP 出口 Encoder 适配与显式注册；对外具体 JSON 由已注册 Encoder 决定（BFF 可按 CDN/SEO 选用 GET 或 POST）。
- **适用对象**：**领域 client**（业务工程独立模块，非 gitee.com/hq_project/yomi-boot）、各领域服务 `handler/`、`gitee.com/hq_project/yomi-boot/component/cloud/rpc`、`gitee.com/hq_project/yomi-boot/component/common/idempotency`、各领域库 `sys_biz` DDL、DTM 分支实现。

## 2. 适用范围与关联

### 2.1 适用范围

- 入口编排服务（BFF）可部署单元内的**领域 client**（路径惯例 `{client}/{domain}`）调用下游**各领域服务**；多入口时按端拆分部署。
- DTM Server 回调领域服务 Action / Compensate 端点（POST/JSON，携带信封字段）。
- 领域服务对内暴露的 `/internal/v1/...`：**读**接口供领域 client 直调；**写**接口仅 Action/Compensate 成对暴露，供 DTM 回调。
- **不适用于** BFF 对浏览器/前端的公开 API。

## 3. 技术方案

### 3.1 通信方式

| 调用方 | 被调方 | HTTP 方法 | 说明 |
| ------ | ------ | --------- | ---- |
| BFF 领域 client | 领域**读**接口 `/internal/v1/...` | **POST** | profile、query、verify-credentials 等；JSON Body |
| BFF `saga/` → DTM | 领域**写** Action `/internal/v1/...` | **POST** | DTM 回调；`dtm.BindAndHandleAction` + barrier |
| DTM Server | 领域**写** Compensate `.../compensate` | **POST** | DTM 回调；`dtm.BindAndHandleCompensate` |
| 前端 | BFF 对外 `router_prefix`（按端在配置中设置；**示例**：如管理端/App） | GET / POST | 见 [API编码适配规范](./API编码适配规范.md) |

- 微服务间**禁止**使用 GET Query 传参、禁止 gRPC。
- **链路 ID 经 HTTP Header `X-Trace-ID` 传播**（`gitee.com/hq_project/yomi-boot/component/core/traceid` 入站中间件 + `gitee.com/hq_project/yomi-boot/component/cloud/rpc` 出站注入）；**不在** JSON Body 中传递。
- **BFF 禁止**以 HTTP 直调领域写接口；**所有写**（含单域）必须经 `saga/` 提交 DTM Saga。
- **领域 service 禁止**暴露可被 BFF 直调的非 Saga 写接口（如**示例** `/internal/v1/{resource}/status` 与 `/internal/v1/{resource}/update-status` 并存、或同一 URL 按 `IsCallback` 分流）。

### 3.1.1 领域写接口形态（Action / Compensate 成对）

每个写用例在领域 `handler/` 注册**成对**路由，且**仅**接受 DTM 回调：

| 类型 | 路径示例（示例） | Handler 绑定 | 调用方 |
| ---- | ---------------- | ------------ | ------ |
| Action | `POST /internal/v1/{resource}/update-status` | `dtm.BindAndHandleAction` → `usecase.Execute` | DTM |
| Compensate | `POST /internal/v1/{resource}/update-status/compensate` | `dtm.BindAndHandleCompensate` → `usecase.Compensate` | DTM |

常见写用例路径约定（资源段单数；下表为**示例**）：

| 用例（示例） | Action | Compensate |
| ------------ | ------ | ---------- |
| 创建资源 | `/internal/v1/{resource}/create` | `/internal/v1/{resource}/create/compensate` |
| 更新资源状态 | `/internal/v1/{resource}/update-status` | `/internal/v1/{resource}/update-status/compensate` |
| 注册资源 | `/internal/v1/{resource}/register` | `/internal/v1/{resource}/register/compensate` |
| 角色 CRUD / 分配 | `/internal/v1/{resource}/{create\|update\|delete\|assign}` | 对应 `/compensate` |

- `{client}/{domain}/url.go` 中写路径常量供领域 handler 与领域 client 写方法共用。
- 领域 client **写**方法（如**示例** `CreateResource(ctx, saga, payload)`）经注入的 `dtmClient.AddSagaStep` 向 Saga 追加分支，**禁止** POST 直调 Action URL。
- 领域 client **读**方法（如**示例** `GetProfile`、`QueryResources`）可直接 POST 调用领域读接口。

### 3.2 请求信封（Envelope）

所有微服务间请求 Body 为 JSON 对象，**顶层固定包含信封字段 + 业务字段**（默认**同级平铺**）。

#### 3.2.1 信封字段

| 字段 | 类型 | 读接口 | 写接口 | 说明 |
| ---- | ---- | ------ | ------ | ---- |
| `bizId` | `string` | 省略 | **必填** | **业务全局 ID**；一次 BFF Saga/业务意图一个；**Saga 内所有分支复用** |
| `bizSubId` | `string` | 省略 | **必填** | **业务子 ID**；**每次**调用领域写接口不同；与 `bizId` 组成幂等键 |

> **链路 ID**：经 HTTP Header `X-Trace-ID` 传播，**不属于** JSON Body 信封字段。
>
> **`operationType` 不在信封中传递**：由领域写接口在内部写入 `sys_biz.operation_type`（通常为用case级常量），调用方**无需、禁止**传入。
>
> **`operatorId` 等身份/业务字段不在信封中统一定义**：各下游接口在 Request DTO 中**按需**声明（如 `operatorId`、`targetId`）；BFF 从 token Claims 解析后填入对应业务字段，与信封字段同级平铺。

#### 3.2.2 bizId 与 bizSubId 分工

```text
一次 BFF Saga（含单分支单域写）
  bizId      = 整个业务意图唯一（如一次「禁用资源」）
  bizSubId-1 = 第 1 次调领域（如 {resource}.update_status Action）
  bizSubId-2 = 第 2 次调领域（如另一领域 revoke Action）
  bizSubId-3 = 某步 Compensate（与对应 Action 的 bizSubId 不同）
```

| 场景 | bizId | bizSubId |
| ---- | ----- | -------- |
| 同一 Saga 内第 N 次调领域写接口 | **相同** | **每次不同** |
| 同一写接口重试（超时、5xx 重放） | **相同** | **相同** |
| 不同业务意图（新 Saga） | **新的** | 新的 |
| 读接口 | 省略 | 省略 |

- `bizId`、`bizSubId` 均由 **BFF `saga/` 生成**（`idempotency.BizID()`）。
- 领域服务**禁止**自行生成或改写二者。

#### 3.2.3 读请求示例

```json
POST /internal/v1/{resource}/profile
Content-Type: application/json
X-Trace-ID: a1b2c3d4-e5f6-7890-abcd-ef1234567890

{
  "resourceId": "1945123456789012345"
}
```

> 上为**示例**路径与字段；`{resource}` 替换为具体领域资源名。

#### 3.2.4 写请求示例（Saga 分支）

```json
POST /internal/v1/{resource}/update-status
Content-Type: application/json
X-Trace-ID: a1b2c3d4-e5f6-7890-abcd-ef1234567890

{
  "bizId": "1987654321098765432",
  "bizSubId": "resource-update-status-action-001",
  "operatorId": "1945123456789012345",
  "targetId": "1945123456789012346",
  "status": "DISABLED",
  "previousStatus": "ENABLED"
}
```

其中 `operatorId`、`targetId`、`status` 等为**该接口业务字段**（非信封）；是否需要 `operatorId` 由接口 DTO 定义决定。

同一 Saga 内下一步调另一领域服务（**示例**）：

```json
{
  "bizId": "1987654321098765432",
  "bizSubId": "revoke-token-action-002",
  "resourceId": "1945123456789012346"
}
```

#### 3.2.5 BFF 职责

| 层级 | 职责 |
| ---- | ---- |
| `saga/` | 生成**一个** `bizId`；为每个 Saga 分支预分配 `bizSubId`；写入各分支 payload |
| 领域 client | 读方法 POST 业务字段；写方法经注入的 `dtmClient.AddSagaStep` 追加 Saga 分支 |
| `gitee.com/hq_project/yomi-boot/component/cloud/rpc` | POST JSON + EndpointResolver 端点解析（Consul 场景用适配器）+ Header `X-Trace-ID`；只做传输与反序列化，不解析业务信封；业务信封由领域 client 自行解析并通过 `BizHookFunc` 判定成功 |

### 3.3 响应格式

微服务间响应按**调用类型**区分，不可混用：

#### 3.3.1 读接口（BFF 领域 client 直调）

微服务间**读**响应信封由本规范自行约定（与对外 [API编码适配规范](./API编码适配规范.md) 的 Encoder **解耦**）；`gitee.com/hq_project/yomi-boot/component/cloud/rpc` 只负责端点解析、传输与反序列化（端点解析通过 `EndpointResolver`，Consul 场景使用适配器），业务信封由领域 client 按本规范自行解析，并通过 `rpc.BizHookFunc` 判定业务成功（非 `OK` 业务码映射为 `BizError`），**不**调用 Encoder。HTTP 状态码固定 **200**：

```json
{
  "code": "OK",
  "msg": "success",
  "timestamp": 1713072000000,
  "data": {}
}
```

分页读接口额外含顶层 `total` 字段。

#### 3.3.2 写接口（DTM Action/Compensate 回调）

领域写 Handler 经 `gitee.com/hq_project/yomi-boot/component/cloud/dtm.BindAndHandleAction` / `BindAndHandleCompensate` 输出 **DTM 分支响应**，**不是** §3.3.1 的标准 envelope：

**成功（HTTP 200）：**

```json
{
  "dtm_result": "SUCCESS",
  "data": {
    "bizId": "1987654321098765432",
    "bizSubId": "resource-update-status-action-001",
    "id": "1945123456789012345"
  }
}
```

**失败（HTTP 409）：**

```json
{
  "dtm_result": "FAILURE",
  "message": "错误详情",
  "code": "RESOURCE_NOT_FOUND"
}
```

| 字段 | 说明 |
| ---- | ---- |
| `dtm_result` | `SUCCESS` / `FAILURE`；DTM 据此判断分支成败 |
| `data` | 成功时可选；业务字段 + 由 usecase Output 嵌入的 `MsWriteResponseEnvelope`（`bizId`、`bizSubId` 回显在 `data` 内） |
| `message` / `code` | 失败时可选；`code` 来自 `BizError` |

- `bizId` / `bizSubId` **不在** DTM 响应顶层；由各领域写 usecase 在 Output 中嵌入 `gitee.com/hq_project/yomi-boot/component/core/shared/dto.MsWriteResponseEnvelope` 后写入 `data`。
- BFF **不**经 HTTP 直调写接口，因此领域 client 读路径仍只解析 §3.3.1 标准 envelope。

### 3.4 业务幂等（bizId + bizSubId + sys_biz）

#### 3.4.1 与 DTM 的边界

| 机制 | 键 / 标识 | 职责 |
| ---- | --------- | ---- |
| **bizId + bizSubId + sys_biz** | 调用方生成，Body 传入 | 防止**同一次领域写调用**被重复执行（重试、超时重放） |
| **DTM gid + barrier** | DTM 分配 | 防止 Saga **分支回调**在 gid 内重复执行；**不替代**业务幂等 |

- 幂等唯一约束：**`(biz_id, biz_sub_id)`**。
- DTM 重试同一分支时，`bizId`、`bizSubId` 均须与首次一致。

#### 3.4.2 sys_biz 表与 gitee.com/hq_project/yomi-boot/component/common/idempotency 封装

**职责拆分**：

| 层级 | 职责 |
| ---- | ---- |
| **`gitee.com/hq_project/yomi-boot/component/common/idempotency`** | 封装 `sys_biz` 模型、仓储与幂等守卫（`sys_biz` 为真源，Redis 结果缓存为快路径，分布式锁串行同键）；`Execute[T]` / `ExecuteInTx[T]` 编排：缓存快路径 → 锁内 double-check → DB 查证回放（纯读）→ 事务抢占执行 → 回写缓存（仅 `Execute`） |
| **各领域服务库** | **各自**执行 DDL，在本服务数据库中建 `sys_biz` 表（表结构一致，数据隔离） |
| **领域 usecase** | 注入 `idempotency.Guard`，调用 `idempotency.Execute(guard, txRunner, ctx, key, fn)` |

**gitee.com/hq_project/yomi-boot/component/common/idempotency 包结构（落地参考）**：

| 文件 | 职责 |
| ---- | ---- |
| `model.go` / `repository.go` | `sys_biz` GORM 模型与仓储 |
| `guard.go` | `Guard` 结构与编排（缓存快路径 → 锁 → DB 查证 → 事务抢占）；`Execute[T]` / `ExecuteInTx[T](guard, txRunner, ctx, key, fn)` 泛型入口 |
| `key.go` | `Key{BizID, BizSubID, OperationType}`；`BizID()` 生成函数 |

领域 usecase 示例：

```go
return idempotency.Execute(uc.idemGuard, uc.txRunner, ctx, idempotency.Key{
    BizID: input.BizID, BizSubID: input.BizSubID, OperationType: operationTypeCreateResource,
}, func(innerCtx context.Context) (*CreateResourceOutput, error) {
    // 业务写逻辑
})
```

- BFF **不**建 `sys_biz` 表，**不**依赖 `gitee.com/hq_project/yomi-boot/component/common/idempotency`（仅生成并传递 `bizId` / `bizSubId`）。
- **禁止**各领域服务复制一套幂等 INSERT/UPDATE 逻辑；统一走 `gitee.com/hq_project/yomi-boot/component/common/idempotency`。
- `Execute` 必须是写路径**最外层事务边界**：传入的 ctx 不得已绑定同源事务（含 `RunAutonomous` 派生上下文），否则「事务提交后才写缓存」的时序承诺失效，回滚后会残留假成功缓存；运行时对嵌套形态 fail-fast（返回 `ErrNestedTx`）。
- 调用方 ctx **已处于事务内**时改用 `ExecuteInTx`（返回 `ErrNotInTx` 即用错入口）：抢占、业务与完成标记全部**跟随外层事务**提交，**不写结果缓存**（嵌套形态没有提交点，回写会跑在真实提交之前，外层回滚会留下假成功缓存；快路径由后续请求 DB 查证回放自愈）。语义边界：外层回滚则幂等记录随之消失，重试重新执行业务——与 `Execute` 失败重试语义一致；MySQL REPEATABLE READ 下并发提交的完成记录对冲突回退反查不可见时返回 `ErrDuplicateWithoutRecord`（fail-closed，下次请求自愈）。DTM 分支回调（barrier ctx）两个入口都不可用，分支幂等由 `sys_barrier` 承担。
- `T` 的 JSON 形状须**向后兼容**：结果快照按 JSON 往返（Redis 5 分钟 + DB 永久），发布迭代中改字段类型/删除字段会使存量 key 的快照反序列化失败。

**DDL 约定**：

- 权威 DDL：`gitee.com/hq_project/yomi-boot/sql/mysql/sys_biz.sql`（与 `gitee.com/hq_project/yomi-boot/sql/mysql/barrier.sql` 等平台表**统一维护在根目录 `sql/` 下，按数据库分 `mysql/` 与 `pgsql/` 两个目录，每个文件单一来源，修改时须同步两份**）。
- 各领域库初始化时，在业务工程可部署单元目录（惯例示例 `services/{unit}/script/sql/`）执行建库与本服务业务表后，**须额外**在本库执行上述两个平台 DDL；**禁止**复制到 `services/{unit}/script/sql/`。
- 与 [数据库表设计规范](./数据库表设计规范.md) 审计字段对齐时，须直接修改 `gitee.com/hq_project/yomi-boot/sql/mysql/sys_biz.sql`。

```sql
-- 摘自 gitee.com/hq_project/yomi-boot/sql/mysql/sys_biz.sql（与 GORM 模型 gitee.com/hq_project/yomi-boot/component/common/idempotency/model.go 一致）
CREATE TABLE IF NOT EXISTS `sys_biz` (
    `id` bigint NOT NULL COMMENT '主键ID',
    `biz_id` varchar(100) NOT NULL COMMENT '业务全局ID（一次 Saga/业务意图）',
    `biz_sub_id` varchar(100) NOT NULL COMMENT '业务子ID（单次领域写调用）',
    `operation_type` varchar(32) NOT NULL COMMENT '操作类型（如 UPDATE_RESOURCE_STATUS）',
    `status` tinyint NOT NULL DEFAULT 1 COMMENT '1-处理中 2-已完成',
    `response_data` json DEFAULT NULL COMMENT '成功时的返回结果缓存（用于重试直接返回）',
    `create_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
    `create_by` bigint DEFAULT NULL COMMENT '创建人ID',
    `update_time` datetime NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
    `update_by` bigint DEFAULT NULL COMMENT '更新人ID',
    `delete_time` datetime DEFAULT NULL COMMENT '删除时间',
    `delete_by` bigint DEFAULT NULL COMMENT '删除人ID',
    PRIMARY KEY (`id`),
    UNIQUE KEY `uk_biz` (`biz_id`, `biz_sub_id`),
    KEY `idx_operation` (`operation_type`),
    KEY `idx_create_time` (`create_time`),
    KEY `idx_status_update_time` (`status`, `update_time`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='业务幂等记录表';
```

DTM 屏障表权威 DDL 为 `gitee.com/hq_project/yomi-boot/sql/mysql/barrier.sql`，表名 **`sys_barrier`**（代码常量 `dtm.DefaultBarrierTableName`）。

| 字段 | 说明 |
| ---- | ---- |
| `biz_id` | 对应 Body `bizId`；同一 Saga 内各步骤相同 |
| `biz_sub_id` | 对应 Body `bizSubId`；每次领域写调用不同 |
| `operation_type` | 领域 usecase 内部写入；与接口语义对应（非调用方传入） |
| `status` | `1` 处理中；`2` 已完成 |
| `response_data` | 成功结果 JSON；幂等命中时直接返回 |

#### 3.4.3 写 usecase 执行顺序

在 `Execute`（及 DTM barrier 内）通过 **`idempotency.Execute`** 执行：

```text
1. 校验 bizId、bizSubId 非空；operationType 由 usecase 常量提供
2. Redis 快路径：命中结果缓存直接返回
3. 分布式锁串行化
4. DB 事务（含 DTM barrier）：
   - INSERT sys_biz（uk_biz: biz_id + biz_sub_id）
   - 唯一冲突 → 查已有记录并幂等返回
   - 执行业务写闭包（domain/repo）
   - UPDATE sys_biz SET status=2, response_data=...
5. 提交后写 Redis 结果缓存
```

`Compensate`：**复用同一 Saga 的 `bizId`**，使用**新的 `bizSubId`**，同样走 `idempotency.Execute`。

#### 3.4.4 读接口

- **不要求** `bizId`、`bizSubId`。
- 链路 ID 经 Header `X-Trace-ID` 传播。

### 3.5 DTM 分支请求

- 仍为 **POST + JSON**。
- Body 含 `bizId`、`bizSubId` 及业务字段（**不含** `operationType`）。
- Header 含 `X-Trace-ID`。
- 同一 Saga 共享 `bizId`；每个 Action/Compensate 回调使用各自 `bizSubId`。
- DTM `gid`/barrier 管流程；**业务幂等只认 `(biz_id, biz_sub_id)`**。

## 4. 检查清单

- [ ] BFF → 领域读接口仅 POST/JSON；写路径不经领域 client 直调
- [ ] 领域写接口成对暴露 Action + Compensate，Handler 使用 `dtm.BindAndHandleAction` / `BindAndHandleCompensate`
- [ ] 不存在可被 BFF 直调的非 Saga 写路径（无 `/status` 与 `/update-status` 并存、无 `IsCallback` 分流）
- [ ] BFF 写编排仅经 `saga/` 提交 DTM；DTM 未配置时返回错误，禁止 Facade/Direct 回退
- [ ] 写请求 Body 含 `bizId`、`bizSubId`（**不含** `operationType`）；链路 ID 经 Header `X-Trace-ID`
- [ ] 领域写 usecase 内部为 `sys_biz` 写入 `operation_type`
- [ ] 同一 Saga 内 `bizId` 不变；每次领域写调用 `bizSubId` 不同
- [ ] 重试同一调用复用相同 `bizId` + `bizSubId`
- [ ] 领域写服务库内已建 `sys_biz` 与 `sys_barrier`（执行 `gitee.com/hq_project/yomi-boot/sql/mysql/sys_biz.sql`、`gitee.com/hq_project/yomi-boot/sql/mysql/barrier.sql`）
- [ ] 写 usecase 通过 `gitee.com/hq_project/yomi-boot/component/common/idempotency.Execute` 做幂等，未在各服务重复实现 INSERT/UPDATE
- [ ] 读响应为标准 envelope；写（DTM 回调）响应为 `dtm_result` 格式，`bizId`/`bizSubId` 回显在 `data` 内
- [ ] DTM gid 与业务幂等键职责分离

## 5. 禁止项

- 禁止微服务间 GET 或在 JSON Body 中传递链路 ID（统一 Header `X-Trace-ID`）。
- 禁止领域 client 绕过 DTM POST 直调领域写 Action URL。
- 禁止领域 service 暴露非 Saga 写接口，或在同一写 URL 上按 DTM 回调参数分流 Action/直调。
- 禁止 BFF 在 DTM 未配置时以 Direct/Facade 等方式绕过 Saga 执行写操作。
- 禁止调用方（BFF / DTM payload）传入 `operationType`。
- 禁止写接口省略 `bizId` / `bizSubId` 或由被调方生成。
- 禁止同一 Saga 内不同领域调用复用相同 `bizSubId`。
- 禁止不同 Saga 复用相同 `bizId`。
- 禁止在未建 `sys_biz` 表或未使用 `gitee.com/hq_project/yomi-boot/component/common/idempotency` 的情况下假设写接口幂等。
- 禁止各领域服务各自实现一套 `sys_biz` 读写逻辑（须复用 `gitee.com/hq_project/yomi-boot/component/common/idempotency`）。
- 禁止将 DTM gid 当作 `bizId` 或 `bizSubId` 使用。
