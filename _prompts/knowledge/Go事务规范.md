## 1. 文档定位

- **用途**：回答写路径上的三个问题：要不要开事务、边界画在哪、事务闭包内放什么/放多久。
- **边界**：Saga 编排、BFF 写入口、领域分层见 [Go架构规范](./Go架构规范.md) 与 [Go业务分层规范](./Go业务分层规范.md)。本文不展开 DTM 分支契约。
- **适用对象**：领域写 usecase / service / repository 的设计与评审。

## 2. 要不要开事务

每个写动作先判定，再说边界。不得默认「写路径都开事务」。

```text
写动作
├─ 只读？ → 不开（除非需要一致性快照读）
├─ 单条语句 / 单行条件更新，数据库已保证原子？ → 通常不开
│    └─ 「先读再判断再写」依赖读到的值 → 开，或改成条件更新 / 乐观锁 / 唯一约束
├─ 同数据源多条写，失败必须一起消失？ → 开
└─ 跨服务 / 跨库？ → 本地事务管不了；能最终一致就不上 Saga，必须协调回滚才由 BFF 编排 Saga
```

判定结果要能一句话说清：**这个事务保护哪条业务不变量，失败时哪些写必须一起消失。** 说不清就先不要开。

| 场景 | 建议 |
| ---- | ---- |
| 纯查询 | 不开 |
| 单条 INSERT/UPDATE/DELETE | 通常不开 |
| 单行条件更新（`WHERE version = ?` / `WHERE status = ?`） | 通常不开 |
| 先读再判断再写 | 开，或把判断下推到数据库 |
| 同库多表写，失败必须一起消失 | 开 |
| 跨服务 / 跨库写 | 不用本地事务覆盖 |

不开事务的写路径必须能说清失败后果（重试、对账、状态字段、唯一约束）。

---

## 3. 边界画在哪

从业务不变量倒推，不从表、方法或分层倒推。按顺序回答：

1. **失败时哪些写必须一起消失？** 得到最小原子集，这就是边界。
2. **哪些读参与写决策？** 必须与写同事务，或把判断下推到数据库。
3. **哪些可以晚一点、差一点？** 缓存、通知、统计、允许异步的审计移出边界。

开启点由「谁拥有这个原子动作」决定，不按层强制。usecase 最常见，repository 的自包含单写也可以开；BFF 不操作领域 DB。谁最清楚「失败时必须一起消失的集合」，谁就是开启点。不要在多层重复开启。

跨服务写不能假设外部 HTTP 加入本服务 GORM 事务。各侧各自画本地边界；需要协调回滚时由 BFF `saga/` 编排。

幂等记录若必须与业务写同生共死，放进同一事务；Redis 锁 / 结果缓存不进闭包。

---

## 4. 闭包内放什么、放多久

事务内只放**本地 DB 往返**和必要的轻量计算。从开启到提交应短、可预期；出现秒级事务必须说明锁范围与分批 / 续跑方式。

**禁止放进闭包**（这些操作不随数据库回滚，只会拉长持锁）：

| 操作 | 替代 |
| ---- | ---- |
| RPC / HTTP | 事务外调用；失败用补偿 / Saga |
| Redis | 提交后再更新 / 删除缓存 |
| MQ | outbox 与业务写同事务落库，提交后投递 |
| 文件 / 对象存储 | 先落库后异步，或设计补偿 |
| HTTP Output 组装 | 闭包外组装 |
| 等待 / 睡眠 / 重试循环 | 事务外重试整个闭包 |

一次事务只承载**一次**业务状态迁移。多个独立动作拆成多个短事务；长流程用状态机，事务只包单步；批量写分批提交、记录进度、失败可续跑。

落地契约（所有开启点都要满足）：

1. 经 `tx.Runner.Run` 开启，不裸用 `Begin` / `Commit` / `Rollback`；独立提交用 `tx.Executor.RunAutonomous`。
2. ctx 已绑定同源事务则复用，提交点归最外层；禁止静默另开会独立提交的事务。
3. 不传 `*gorm.DB`；repository 用 `tx.Exec(ctx, root)` 取当前连接。
4. 闭包内用传入的 `executeCtx` 写库，不用外层 `ctx`；Output 在闭包外组装。
5. 闭包返回 error 即回滚。超时跟调用方 ctx，禁止用 `context.Background` / `WithoutCancel` 绕过（自治事务除外，且必须自带 timeout）。
